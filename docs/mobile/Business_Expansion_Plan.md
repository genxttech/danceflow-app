2026-11-20. Owner direction APPROVED: Business becomes a daily-operations app for owners, admins, front desk and instructors. Sources: reuse inventory of `origin/main` (read-only), `Staff_API_Contract.md`, `Staff_API_Proposals.md`, `Business_Release_Readiness.md`, the Master Roadmap. ## 1. Where we are (V)

- Mobile today: Today, studio-day Schedule, Pulse, Clients (search, detail), appointment detail, class attendance (the only write), push scaffolding (off). v0.1 RC6 is in Play internal testing (version code 1).
- Server today: 8 routes under `src/app/api/staff/**`: `me`, `today`, `schedule`, `pulse`, `appointments/{id}`, `PUT .../attendance/{clientId}` (idempotency key), `clients`, `clients/{id}`. Guard: `requireStaffApi` (bearer JWT, membership, account status, rate limits, RLS via the caller's client). Libs: `src/lib/staff/{classAttendance,clients,instructorToday,studioSchedule,studioPulse}.ts`.
- Roles and capabilities are already centralized: `src/lib/auth/permissions.ts` (`can*`) and `staffCapabilities.ts` (served by `/me`). Owner/admin/front desk: clients, payments, sales, appointments; owner/admin only: rooms, instructors, settings, ARIA; instructors: appointments and attendance but only the RPC-scoped client reads; independent instructors: floor-rental only; events: organizer roles plus studio owner/admin (NOT front desk).
- The hard fact: almost all write logic lives inside `"use server"` action files (appointments 5,678 lines, memberships ~1,900, event registrations ~2,400, ARIA ops 7,500+) coupled to FormData, cookies and `redirect()`. Reports and dashboard queries live inline in `page.tsx`. Reuse therefore means **extract a pure lib function from the action, make the web action call it, then wrap it in a bearer route**. That is how class attendance was done and it is the pattern for everything below.

## 2. Architecture rules (apply to every phase)

1. **Extract, do not fork.** The web server action becomes a thin caller of the new `src/lib/staff/<x>.ts` function; the mobile route calls the same function. One source of truth; the web action tests are the regression net.
2. **Server-side enforcement only.** Route = `requireStaffApi` -> `can*` check -> lib. RLS applies through the caller's client; any place an action used `createAdminClient` must be redesigned or gets a narrow, reviewed, tested admin seam (CODEOWNERS, independent security review). Refusal test per role per route (existing pattern `staffApiSlice2Refusals`).
3. **Writes are idempotent and audited.** `Idempotency-Key` on every write (as attendance); every write records actor, studio, source `mobile` in the existing audit/ledger paths (A: confirm which audit tables each action already writes; list in each slice's design note).
4. **Money is last and web-first for risky parts.** No Stripe refunds, membership sales or package sales on mobile until a financial design gate passes (OWNER).
5. **No offline write queue in v0.2.** Reads keep the stale banner (`keepStale`); writes fail with a clear retry using the same idempotency key. Revisit offline writes after Phase 1.
6. **Server kill switch before write routes ship.** Business has none today (release readiness). Add a per-capability switch and a minimum-version gate, reusing the Student design (`Student_Min_Version_And_Kill_Switch_Design.md`), before the first write beyond attendance.
7. **Mobile UX rule.** One obvious next action per screen, bottom sheets for confirm/edit, no desktop forms, 2.0 font and TalkBack from day one (existing a11y harness).
8. **Ship from one line.** Production runs `release/website-embeds`; `main` is ~350+ commits ahead (#445 reconcile is on hold). Every extraction in a file that differs between the two lines needs a path-checked backport like #673. See dependency D1.

## 4. Phases (bounded, independently testable)

**Phase 0: foundations (about 1 week, server + mobile frame).** Live-line parity check (diff the target action files between `main` and the live line), kill switch + min-version gate for Business, write-route scaffolding (idempotency helper, audit conventions, error vocabulary), mobile mutation framework (confirm sheet, optimistic update with rollback, retry with the same key, conflict states), write-capable local-stack test world, PROD write-smoke policy (D3). Exit: framework proven by one new write (client note) end to end.

**Phase 1A: front-desk day, the recommended FIRST release = v0.2 (about 2 weeks after Phase 0).** Private-lesson attended / no-show / reset with correct package deduction; client notes; quick-add client; class roster drop-in enroll and cancel; Today/Schedule polish for one obvious next action (check in -> attended). Roles: owner, admin, front desk; instructors for their own appointments' attendance once the instructor SQL gate is cleared (D4). Smallest useful release: a front desk person can run the floor from a phone.

**Phase 1B: appointment engine (about 3-4 weeks).** Create, reschedule, cancel 1:1 appointments with conflict detection, package/membership validation and notifications. Single writer on `schedule/actions.ts` (conflict risk). Heavy regression gate on the web actions.

**Phase 1C: setup (about 2 weeks).** Rooms, instructor availability/blocks, client edit/archive, instructor "My day" workflows (depends on D4).

**Phase 2A: group classes (about 3 weeks).** Create/edit/cancel single and series using the existing RPCs.

**Phase 2B: events (about 2-3 weeks).** Registration list, ticket-code check-in, attendance, capacity view. Organizer/owner/admin only (front desk access is a product decision, D5).

**Phase 2C: balances (about 2 weeks).** Package balances read, manual payment record, balance adjustment. No Stripe movement.

**Phase 2D: sales and refunds (financial gate).** Package sale, membership sale/cancel, refunds: only after a written financial design, server-side controls review and explicit owner approval. Until then the mobile app deep-links to the web.

**Phase 3A: ARIA and needs-attention (about 3 weeks).** A "Needs attention" queue (schedule gaps, cancellations, follow-ups, package depletion) from existing libs and `automation_actions`; approve/dismiss for owner/admin; contextual actions that open the right screen. ARIA never executes from the device; execution stays server-side behind the existing approval and policy. **3B:** staff push (sender lib exists), per-client messaging through the compliance path. **3C:** reporting KPIs extracted from the web pages.

## 10. Phase 1A design notes (design only; nothing implemented, awaiting APPS confirmation)

Common rules (all slices): route = `requireStaffApi(request, studioId)` (bearer JWT, membership, account status, rate limits; platform admins refused) -> role check with the existing `can*` -> lib. The lib receives `supabase` (the guard's bearer-scoped anon-key client, so RLS applies exactly as for the cookie client: both are the `authenticated` role with `auth.uid()` = the caller), `studioId`, the caller's `userId` and role, and returns a typed result union that both the web action (mapped to its redirect codes) and the route (mapped to flat `{error, code}`) consume. Errors stay flat; unknown refusals collapse as today (`not_found` for "not yours"). The server-side kill switch and minimum-version gate (section 2 rule 6) must exist before any of these routes ships.

**Role matrix (from `permissions.ts`, V):** `canEditClients` = platform_admin, studio_owner, studio_admin, front_desk. `canMarkAttendance`, `canEditAppointments`, `canCreateAppointments`, `canViewStudioSchedule` = those four plus `instructor`. `independent_instructor`, organizer roles and `student` are in none. For appointment slices an instructor is further restricted by `requireAppointmentRelationshipAccess` to appointments currently assigned to them (`own-instructor`) and, for enrolment, by the RPC's own broad-or-own-instructor check. The platform admin never reaches the API.

### 10.1 Private-lesson attended / no-show (reset is NOT a web capability)

- **Web today:** `markAppointmentAttendedAction`, `markAppointmentNoShowAction` (`schedule/actions.ts:4171`, `:4531`). **There is no reset/undo action.** Both outcomes are terminal for `private_lesson`, `intro_lesson`, `coaching` by a recorded product decision (an attended lesson cannot become no-show and vice versa), backstopped in the database by the trigger `enforce_private_lesson_attendance_lifecycle`. "Reset" would need a new, explicit Attendance Correction workflow with its own product and financial design (credit return); **recommendation: drop reset from Phase 1A**.
- **Extraction:** new `src/lib/staff/appointmentOutcome.ts`:
  `markAppointmentOutcome(params: { supabase; studioId: string; userId: string; studioRole: string | null; isPlatformAdmin: boolean; appointmentId: string; outcome: "attended" | "no_show"; missedAppointmentCharge?: "none" | "package" | "membership" }): Promise<{ ok: true; status: "attended" | "no_show"; alreadyApplied: boolean; usageSyncPending: boolean; chargeApplied: "none" | "package" | "membership" } | { ok: false; code: "not_found" | "payment_required" | "outcome_conflict" | "write_failed" | "charge_failed"; message: string }>`.
  Moves out of the `"use server"` file into libs: `syncPackageUsageForAttendedAppointment`, `syncMembershipUsageForAppointment`, `clearMembershipUsageForAppointment`, `applyMissedAppointmentCharge`, `canMarkAppointmentAttendedWithoutPaymentWarning`, `packageHasAvailableCreditForAttendance`. Side benefit: `syncPackageUsageForAttendedAppointment` is currently an `export`ed function in a `"use server"` file, i.e. registered as a server action endpoint (its parameters make it uncallable in practice, A); moving it to a lib removes that exposure. The web actions become callers; `stageInstructorEarningForAppointment` (lib) stays best-effort after the commit.
- **Route:** `PUT /api/staff/workspaces/{studioId}/appointments/{appointmentId}/attendance` (the existing class route is `.../attendance/{clientId}`, so no clash). Body `{ "status": "attended" | "no_show", "missedAppointmentCharge"?: "none" | "package" | "membership" }`, header `Idempotency-Key` required. Only `private_lesson`, `intro_lesson`, `coaching` (anything else `409 not_markable`; group classes keep the per-client route). 200 `{ appointment: { id, status, attendanceMarkedAt }, alreadyApplied, usageSyncPending, chargeApplied }`.
- **Errors:** 400 `invalid_request`; 401; 403 `role_not_permitted` / `workspace_paused` / `not_a_member`; 404 `not_found` (missing, other studio, or an instructor's non-assigned appointment, indistinguishable as today); 409 `not_markable` (wrong type or cancelled), **new** 409 `payment_required` (pay-as-you-go unpaid, membership entitlement invalid, no package credit), **new** 409 `outcome_conflict` (attended <-> no-show); 503 `service_unavailable` only when nothing was committed. When the status committed but the package or membership sync failed (the web's `attendance_sync_failed`) the route answers **200 with `usageSyncPending: true`**, never an error that would make the app roll back a committed status; a retry with the same key is safe (below).
- **Idempotency:** the action is idempotent for attended by design (the status write is skipped when already attended, the deduction RPC `deduct_package_credit_for_appointment` re-checks its own `lesson_transactions` marker under a row lock, and a replay completes a previously failed sync). Same stance as the class route (S2): the key is validated, not stored; last write wins on the status. **Gap to fix in the shared lib (a small web behaviour change, with a test):** a replayed no-show today inserts a second `client_activity_notes` row and re-runs the missed charge; the lib must short-circuit when the status is already `no_show` (no second note; the charge RPC is already idempotent).
- **Writes / audit rows today (V, by reading the action and libs):** `appointments` (status, `attendance_marked_at`, `updated_at`); by trigger `deduct_package_credit_when_appointment_attended` and the RPC: `lesson_transactions` (`lesson_deduction`), `client_package_items.quantity_remaining`, the legacy `client_packages.lessons_*` mirror, and the package lifecycle reconcile (`client_packages` active/status via `reconcileClientPackageLifecycle` and its trigger); `client_membership_usage` (delete then insert, only for non-private types); `instructor_earnings` (staged best-effort); `client_activity_notes` (no-show only: "Appointment marked no-show ... Charge policy ..." with `created_by`). **No row records the actor or a `source = mobile`** on `appointments`; section 2 rule 3 therefore needs a decision: (a) append "(mobile)" to the no-show note body and rely on the API access log, or (b) a column on `appointments` (SQL, owner gate). Recommendation (a) for 1A.
- **Admin client:** none in either action or any helper (all on the session client). So the bearer client behaves the same under RLS. Two silent-degrade points to test, not to fix: `stageInstructorEarningForAppointment` reads `instructor_compensation_rules` and `instructor_payroll_profiles`, which a front-desk caller may not be able to read, so it returns `staged: false` (identical on the web today); and the membership path reads `studio_settings` and `client_membership_periods` under the caller's RLS.
- **Tests:** unit per outcome and role (owner/admin/front desk allowed; instructor allowed only on an own appointment, refused on another's; independent instructor, student, no membership, other studio, paused workspace refused); conflict matrix (attended -> no-show, no-show -> attended, replay of each); `payment_required` for PAYG unpaid, membership invalid, package empty; replay completes a failed sync (`usageSyncPending` then clear); the no-show replay writes one note, not two; local-stack with real RLS and the trigger (package credit deducted exactly once under double submit and under two concurrent callers); the existing web action tests (`attendedAppointmentLifecycleGuards`, `appointmentRelationshipScoping.fc1b5d2`) stay green as the regression net; refusal and tenant-isolation suites in the `staffApiSlice2Refusals` pattern.

### 10.4 Class roster enroll / cancel (drop-in)

## 11. Phase 2B design note: front-desk event check-in (owner decision D5, 2026-11-20; design only, no code)

**Direction approved by the owner:** authorized front-desk staff may check in attendees for **their own studio's events**. It is a scoped, auditable capability, **not** organizer tooling, Competition, payments, scoring or event management. Any permission or security migration is separately gated (owner approval by hash).

**Today (V, by reading the code):** `canCheckInEventAttendees` is defined as `canManageEventTickets`, i.e. platform admin, studio owner, studio admin and the organizer tiers; **front desk is excluded** (`permissions.ts`). The web check-in lives in `checkInEventTicketCodeAction` and `checkInEventRegistrationAction` (`src/app/app/events/[id]/registrations/actions.ts`, ~2,400 lines that also hold ticket sales, refunds and settlement). They use the cookie-session client for check-in (the same file uses `createAdminClient()` for other seams: terminal sales and the Organizer Suite entitlement check, which check-in does not need, A). The check-in reads the attendee by ticket code, refuses cancelled or refunded registrations and unpaid ones (`shouldBlockAttendanceForPayment`), requires a session for group-class events, and writes the attendee and registration status plus an attendance row (`status: checked_in`).

**Why `canCheckInEventAttendees` must not simply include front desk:** it is the same predicate as `canManageEventTickets`, which also gates selling tickets, payments and refunds in the same file. Widening it would hand front desk those. The change is a **new, separate** capability.

**Design**
- **Capability:** new `canCheckInStudioEventAttendees(role)` = studio owner, studio admin, front desk (and organizer roles keep their existing path). It authorizes exactly: look up an attendee by ticket code or name, see the check-in roster of a **studio-hosted** event (names, check-in state, counts: no email, phone, prices or payment details), check one attendee in (and for group-class events, into a named session). It authorizes nothing else: no sales, payments, refunds, edits, capacity, settlement, no Competition entries, heats or scoring. `/me` capabilities gain `checkInEventAttendees` for shaping navigation; the server enforces.
- **Scope = the caller's own studio:** `events.studio_id = caller's studio`. Events run by an organizer entity (`organizer_id` set) are excluded unless the owner decides otherwise (open question Q1). A staff member of studio A cannot touch studio B's events.
- **Authority in the database, not the app:** a narrow `SECURITY DEFINER` function `check_in_event_attendee(p_attendee_id uuid, p_session_id uuid default null)` that derives the caller from `auth.uid()`, requires an active studio role in {owner, admin, front_desk} for the event's studio, enforces the same rules as the web action (registration active, not cancelled/refunded, payment gate, session required for group classes, not already checked in), and updates **only** the check-in columns and the attendance row, recording `checked_in_by = auth.uid()`. Revoke from `public`/`anon`, grant to `authenticated`. This avoids loosening RLS on `event_registrations` / `event_registration_attendees` for front desk (a broad policy change) and gives one reviewed seam. **This is the security migration: it needs the SQL, a rollback file, a SQL test, an independent review and the owner's hash approval; nothing is applied by the build.**
- **Routes:** `GET /api/staff/workspaces/{studioId}/events/{eventId}/check-in?q=&cursor=` (minimal roster) and `POST .../events/{eventId}/check-ins` with `{ attendeeId | ticketCode, sessionId? }`, `Idempotency-Key`, behind `requireStaffWrite(..., "eventCheckIn")` (a fifth write capability key; separate kill switch, default off). Idempotency is state-based: an attendee already `checked_in` returns `200 { alreadyApplied: true }` with the original time and writes nothing. Errors (flat): `404 not_found` (event or attendee not in this studio), `409 payment_required`, `409 registration_inactive`, `409 session_required`, `409 session_cancelled`, `403 role_not_permitted`. **No undo** in the app (a wrong check-in is corrected on the web), same stance as lesson attendance.
- **Audit:** the attendee/registration status change, the attendance row, `checked_in_by` and timestamp (columns to be confirmed on PROD before the migration is written, A), plus the API access log. No other tables.
- **Mobile:** an "Events" entry for roles with the capability: today's studio events, a search/scan field for ticket code or name, one obvious action per attendee (Check in), a final state "Checked in at 6:42 PM". Same mutation framework, flag `eventCheckIn` default off, device smoke on iso-qa, evidence gate in the build script like the other write words.
- **Tests:** role matrix (front desk allowed; instructor, independent instructor, student, no membership refused); tenant isolation (studio A staff cannot read or check in studio B's attendees or events; an organizer-hosted event is refused if Q1 stays "excluded"); payment-blocked, cancelled/refunded, session-required, already-checked-in replay; the function's grants (anon refused, authenticated only, no direct table write for front desk); the existing web check-in tests as the regression net; no field beyond name and check-in state in any response.

**Open questions for the owner:** Q1: should studio front desk also check in attendees of events run by an organizer hosted at their studio (default: no)? Q2: should front desk see attendee email or phone on the check-in list (default: no; names and status only)? Q3: may front desk check an unpaid attendee in after a payment warning, as the owner/admin path can (default: no; the payment gate stands).
