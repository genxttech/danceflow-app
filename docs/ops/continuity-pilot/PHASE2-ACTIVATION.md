## How the executor works
`driver.mjs` (deterministic code, not a model) claims one item, writes that item's settings file, and launches an isolated `claude -p` child:
`--restricted --strict-mcp-config --tools "Bash,Read,Edit,Write,Glob,Grep" --permission-mode dontAsk --permission-prompts none --settings <item settings> --add-dir <item directories> --max-budget-usd <cap> --no-session-persistence --disable-slash-commands`.
`--restricted` ignores the user, project and local settings files, so the child sees only the item's own settings. `dontAsk` plus no one to answer prompts denies everything not on the item's allowlist. The allowlist comes from the owner-authorized policy template (part of its scope hash), restricted to a few reviewed command shapes, with the 130-rule pilot deny list and shell-smuggling denies (`;`, `&&`, `|`, `>`, `<`, `$()`, backticks, `..`, `--output`...) as a second layer. File tools are confined to the item's directories. The child environment carries no GitHub, Supabase, Vercel, database or model-API tokens (the CLI uses its stored login). The model cannot claim, schedule or complete items, and it cannot run `git add` or `git commit`: the child never writes into a repository: its only writable location is a stage directory `C:/Dev/cpilot-out/<item>/`. After a successful item the DRIVER checks that the repository (including ignored files) is exactly as before and that HEAD did not move, validates the staged files (plain regular files, safe names, allowed extensions, size/depth/count limits, none named like git internals), copies them into the template's commit path as NEW files only (never overwriting), verifies the staged set, and makes one local commit with repository hooks disabled (`core.hooksPath` empty, `--no-verify`); any refusal leaves the repository untouched. Edits to `.git`, hooks, `.gitattributes`, `.gitmodules`, `.husky`, `package.json`, `.github` and the pilot's own run files are denied. The helper scripts run only from the verified code directory (`{CODE}` in the policy resolves to the directory `claim` checked byte-for-byte against the reviewed copy) and their contents are part of the child-configuration hash. The disposable database container runs with `--network none` (no other container, host port or internet is reachable) and the driver removes it after every item, including after a timeout kill. Git and `psql` argument escapes that could read arbitrary files, run programs or reach another host (`--no-index`, `--pathspec-from-file`, `--ext-diff`, `-F`, `--amend`, psql meta-commands, `PROGRAM`, a second `-h`, connection strings) are denied by pattern.

   - 3 authorization scope: the live queue holds exactly the authorized class-A items, no class-G authorization, no unauthorized item, advisory local-only screen on commands, no class-A template touching a protected path.
   - 4 stop controls and fail-closed behavior, exercised against the real `claim`/`complete` code on the live queue: STOP and resume, unreachable source, wrong worker, missing or stale attestation, child-configuration drift, duplicate ids, remote disable, claim limit, class-G parked by the gate (mutation-tested), forged owner-done.

## Stop conditions (the driver stops and reports; it never retries around them)
Any permission denial; any timeout; STOP file; protected source unreachable or invalid; missing, expired, mismatched or drifted attestation (including code or child-configuration drift); untested `claude` version; any limit; an item reporting a protected path (parks BLOCKED-OWNER); an owner message in chat.

## Recovery and manual controls
State is local (`queue.json`, `log/execution.jsonl`, per-item `stream.jsonl`, `PREFLIGHT_REPORT.json`, `ISOLATION_REPORT.json`). A dead runner is requeued once, then NEEDS-REVIEW. After a restart nothing resumes by itself: re-run the preflight if the attestation expired, then the driver. Stop: chat, or `node orchestrator.mjs stop --root C:/Dev/continuity-live/COMPETITION`, or end the driver process. Inspect: `status`, `log`. Remote kill: `pilot.enabled=false` via an owner-approved PR.

## Honest limits
- The isolation report is evidence produced by a cooperative coordinator on the same machine; the attestation is a local file. The hard gates are the protected policy and CODEOWNERS.
- Allowed commands (`git`, `docker`) run as the owner's OS user, unconfined. Safety rests on the reviewed command shapes, the deny layer and the abuse probes; the isolation test is the evidence, and a new `claude` version requires a new test (the version is pinned).
- The child bills the owner's plan. Probe runs use a cheaper model; enforcement is the harness's, independent of the model.
- Inside the disposable container the child can run arbitrary SQL and shell commands; the container has no network, no secrets and no host mounts. Outside it, the child can read the item's own repositories through the reviewed `git_read.sh` helper (argv-level allowlist per subcommand: no `--no-index`, `-O`, `--ext-diff`, `--textconv`, `--output`, `config`, `..` or absolute paths; the deny layer is a second layer, not the only one) (no raw `git` is allowed at all). Git in the child and in the driver ignores the owner's global and system git config (aliases, pager, fsmonitor, url rewrites, credential helper). Abuse shapes against the Bash/Read tools outside the tested set remain a residual.
- An independent review (2026-11-15) found four P1 issues in the first version of this layer (container network reach, git argument escapes, repository hooks on commit, scripts not pinned at the executed path); all were fixed and the isolation test re-run. Later reviews of the fixes found three P2 (round 2), two P1 (round 3: a planted nested repository the driver would have committed, and an implicit git `--no-index` through drive-relative arguments) one P1 (round 4: a planted bare-repository layout without any .git name) and two P1 (round 5: plants in git-ignored paths, a refused plant accepted on retry, edits to existing gate scripts); all were fixed, round 5 by staging the child's output outside every repository, and the isolation test re-run each time. The round-5 design has not itself been reviewed.
- The credential helper used by `claim` to read `main` can mint a write-capable token; it is run by git, not by the child.
