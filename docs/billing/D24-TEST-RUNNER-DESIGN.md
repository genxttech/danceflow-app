# D24 engineering-operated Stripe TEST runner: design

Status: **implemented locally, never executed against Stripe.** Code: `scripts/qa/d24-test-runner/` (outside the hashed proof folder `scripts/qa/d24-m3d-proof/`, which this change does not touch). No `src/` change, no migration, no Stripe API call, no credential used while building it.

## 1. Purpose and non-goals

The owner no longer runs test scripts or handles credentials. The coordinator (engineering) must operate TEST runs of the merged proof harness (main b1a91b58, manifest `b94706f4...`, 30 files) safely. The runner wraps `run.ts --live` with gates the proof cannot enforce on itself: which code runs, under whose written authority, how many times, with which credential, and what is checked afterwards.

Non-goals: it does not widen the proof's allow-list or call cap (the proof enforces both; the runner re-verifies them), it does not create Stripe resources itself, it cannot mint an owner authorization (a detached **owner Ed25519 signature** is required for every live run, section 3), and it does not make the credential safe against other processes of the same Windows user (see section 5).

## 2. Run pipeline (order is deliberate)

`cli.ts run --envelope E [--signature S] [--dry]` ->  `runner.ts runEnvelope`. Any failed gate = **BLOCKED**, exit 2, nothing sent, no run consumed. `runEnvelope` also requires `dry === true` <=> the executor is the dry fake created in `fakeChild.ts` (a WeakSet brand; a real or look-alike executor with `dry:true` throws before any gate, and a dry fake cannot be used as a live executor), so the `dry` flag cannot skip the signature/credential/ledger gates. A live run accepts no `--repo`, `--ledger-dir` or `--home`: the checkout is the clone this runner lives in and the ledger location comes from the owner trust file.

| # | Gate | Source of truth |
|---|---|---|
| 1 | envelope readable, schema + policy valid, approval terms (incl. the `terms=` digest), canonical hash | `envelope.ts` |
| 2 | envelope window (not expired, not future, key not past its expiry) | clock |
| 2b | **owner signature**: Ed25519 over `D24-TEST-ENVELOPE-V1\n<envelopeSha256>` verifies against the pinned owner public key (live only; dry is exempt because it can reach nothing) | `ownersig.ts` + owner trust file |
| 2c | **runner pin**: the runner folder (excluding `__tests__`) is `scripts/qa/d24-test-runner` of the verified clone and its manifest hash equals `envelope.runner` | `runnerpin.ts` |
| 3 | **ledger pinned**: ledger dir and anchor equal the locations in the owner trust file; runs consumed < `maxRuns` for this envelope **hash**, per-key cap, no unfinished run, no lock | `ledger.ts` |
| 4 | evidence dir `<evidenceRoot>/<envelopeId>/run-N` outside every git checkout (real paths) | proof `evidenceDirProblem` |
| 5 | clean clone: `HEAD == code.commitSha`, toplevel == repo dir, `status --porcelain --untracked-files=all` empty, `diff-index HEAD` clean, no assume-unchanged / skip-worktree files, `package-lock.json` sha256 (CRLF-normalised) equals `code.lockfileSha256` (now mandatory), then `npm ci --ignore-scripts` and the tree still clean | `gitverify.ts` |
| 6 | proof manifest: runner recomputation == proof `--print-hash` == envelope (hash and file count) | `manifest.ts` + proof CLI |
| 6b | **ceiling pin**: envelope `apiCallCeiling` == the proof's enforced `HARD_CALL_CAP` (read from the manifest-verified source) | `runner.ts` |
| 7 | allow-list: proof `--allow-list` rule-id set == envelope `permittedRuleIds`, and every id is a known rule | proof CLI |
| 8 | proof `--dry-run` (fake client) ends `OUTCOME: OK` | proof CLI |
| 9 | **credential store is touched here, not earlier**: stored key is `rk_test_` shaped, sha256 prefix equals the envelope's approved fingerprint | `credstore.ts` |
| 10 | sanitised child environment built and re-validated with the proof's own `checkEnvironment` | `childenv.ts` |
| 11 | proof `--preflight`: no FAIL; every MANUAL id must have an attestation in the (signed) envelope (never guessed) | proof CLI + envelope |
| 12 | last tree re-check (TOCTOU) and **envelope window re-check at the moment of consumption** | git, clock |
| 13 | **ledger `run-start` written (run consumed)** under the exclusive lock, with every blocker re-evaluated while holding it, then `--live` | `ledger.ts` |
| 14 | post-run: evidence analysis, cleanup verification, hashing, redaction scan, report, ledger `run-end` (not written after a timeout, see 6) | `postrun.ts` |

The ledger entry is written before the first live call, so a run that fails, aborts, crashes or is killed still counts. A `run-start` with no `run-end` blocks all further runs until a human `reconcile`s it after checking the Stripe dashboard (reconcile does not give the run back).

## 3. Authorization envelope

A JSON file; `envelope.ts` holds the schema, validator and canonical hash (`sha256` of the key-sorted JSON without `envelopeSha256`). Any post-creation edit fails the hash. Fields: exact `code.commitSha` and **mandatory** `lockfileSha256`, `proof.manifestSha256` + `fileCount`, **`runner.manifestSha256` + `fileCount`** (this enforcement code), sandbox and connected account ids, `permittedRuleIds`, `apiCallCeiling` (1..40 including the 8-call cleanup reserve), credential store/label/`keyKind: rk_test`/fingerprint prefix/`keyExpiresUtc`, `cleanup` (required, must verify empty), `forbidden` (fee-bearing, financial mutation, LIVE: all must be `true`), `stopConditions` (must include any-abort, livemode-true, identity-mismatch, cleanup-unverified, secret-in-output, call-ceiling), `maxRuns` (1..5), `evidenceRoot`, `manualAttestations`, `ownerApproval` (verbatim text, its sha256, reference), `expiresUtc`.

Refused: expired or future envelope; lifetime > 30 days (a standing envelope is never unlimited); `maxRuns` outside 1..5; ceiling > 40 or <= 8; unknown rule ids (any name containing finalize/send/pay/refund/payout/charge/live/... is reported as fee-bearing/financial/LIVE); `mode != TEST`; relaxed `forbidden`; a key kind other than `rk_test`; a key that expires before the envelope; unknown or missing fields; hash mismatch.

**What is covered by the signature.** `envelopeSha256` is the canonical hash of *every* field except itself, including accounts, credential label/fingerprint/expiry, permitted rule ids, ceiling, cleanup reserve, evidence root, lockfile pin, proof pin, runner pin, stop conditions, max runs, lifetime, all manual attestations and the approval record. Editing any of them changes the hash and invalidates the signature (tests edit each field and assert the hash changes). The approval *text* must additionally contain `terms=<16 hex>`, a digest over all those material fields, so a stale text cannot be paired with changed terms; this is a typo-guard and an audit record, not the control.

**The control: owner signature (review P1-1).** Anything that can write a file can write the approval text, so the text is not an authorization. A live run requires a **detached Ed25519 signature over `envelopeSha256` made by a private key only the owner holds**:

* `ownermain.ts owner-keygen --commit <reviewed sha>` (owner's machine; a separate entry point the runner CLI never imports; interactive TTY only, refuses piped input): first verifies it is running from a **pristine checkout** (HEAD == the named commit, clean tree, no hidden edits, via an absolute git path), then generates the keypair, stores the private key as PKCS8 encrypted with AES-256-GCM under a scrypt-derived key from the owner's passphrase (min 12 chars) in `d24-owner\owner-key.enc.json`, and registers the **public** key, the **pinned ledger directory and anchor path**, the Windows account that ran it, the commit, and a **hash of the owner-side tool files** in `owner-trust.json` (read-only attribute). It **refuses if a trust file or key already exists**: there is no silent re-registration. DPAPI is deliberately *not* used for this key: DPAPI CurrentUser lets any same-user process decrypt, which would turn the signature back into self-approval.
* `ownermain.ts owner-sign --envelope E --commit <sha> [--out S]` (owner, TTY only): refuses unless it runs from the same kind of pristine checkout **and** the owner-tool files still hash to the value recorded at keygen; validates the envelope (control characters rejected); **recomputes the canonical hash with its own local canonicaliser** (not the runner's `canon.ts`) and signs/displays that value; prints **every** material term with each dynamic value JSON-escaped and non-ASCII `\u`-escaped (no ANSI/CR/bidi byte can reach the terminal); requires the owner to type `SIGN <first 12 hex of the recomputed hash>`, prompts for the passphrase, and writes a signature file that contains no secret. `owner-rotate --commit <sha> [--new-key]` is the only way to change the registration (re-bind tools after a reviewed change, or replace the key): it needs the **old** passphrase and stores a rotation statement signed by the old key.
* The runner verifies the signature against the pinned public key (`owner-signature` gate). No registered key, a missing/garbage signature, a signature for another hash or by another key => BLOCKED; `run` without `--dry` exits 2 before anything else. `run --dry` needs neither.
* The runner and coordinator tooling contain **no signing path and no trust-file writer**. The runner and `cli.ts` import only `ownerverify.ts` (read the trust file, verify a signature, warn). `signEnvelopeHash` / `writeTrust` / key generation / rotation live in `ownersig.ts`, imported only by `ownercli.ts` and `ownermain.ts`; a test scans every source file's imports to keep it so. `create-envelope` still produces an envelope from a spec plus the owner's text, but that envelope cannot run live without a signature (the review's `approval-template | create-envelope` reproduction is a test).
* **How the owner verifies the commit and the fingerprint out of band (P3-1).** The `--commit` the owner types must come from the merged PR, not from the engineer's message alone: open the merged PR #417 on GitHub in the owner's own browser, read the merge commit / head SHA on the PR page (or `git ls-remote https://github.com/genxttech/danceflow-app refs/pull/417/head` from the owner's own machine), and compare all 40 characters with the SHA the engineer quotes before running `owner-keygen --commit <sha>` from a fresh clone checked out at that SHA (`git rev-parse HEAD` must print it and `git status` must be clean; the command refuses otherwise). After keygen, the owner reads the printed **public-key fingerprint** and records it somewhere the engineer cannot edit (own notes, a phone photo, a message to themselves); `owner-show` reprints it at any time. Later, `run` output and `owner-sign` both show the key fingerprint prefix: a mismatch with the owner's own record means the trust file was replaced. Per envelope, the owner signs only after reading the printed approval text and terms, and compares the first 12 hex characters of the canonical hash with the hash the engineer announces in chat.
* **Key file hardening (P3-7).** scrypt N = 2^17 (r = 8, p = 1, about 134 MB) is the floor, enforced when the key file is read (a lowered cost in the file is refused); AES-256-GCM with a 16-byte tag, 12-byte IV and 16-byte salt, all lengths validated before key derivation; the passphrase must be at least 16 characters with at least 6 distinct characters, not only digits and not a short repeated pattern. `owner-rotate` checks that the decrypted old key *is* the registered public key, writes the new trust/key files as `.new`, copies the old ones to `.bak`, swaps with renames, restores from the backups on any failure and deletes the backups only after both swaps succeeded.
* **The same-user warning (P3-8)** reads `icacls` output (absolute path, neutral cwd; a write-class right for the current account or for Users/Everyone/Authenticated Users counts, DENY entries are skipped) instead of `accessSync`, and is printed once per live run only when no separate-account marker exists (key registered by a *different* account and no write right for this one).
* **Envelope input limits (P3-2, P3-3).** Strings are capped at 2000 characters, arrays at 64 entries, objects at 64 keys, nesting at 6 levels; unknown keys inside nested objects and attestations are refused, not ignored. `owner-sign` prints the approval text first, then the recomputed hash and the terms.
* Owner-only cost: one-time `owner-keygen` plus one `owner-sign` (type a confirmation and the passphrase) **per envelope**. This is the minimal unavoidable authorization act. It protects against **coordinator/agent self-approval**: the tooling cannot mint an authorization. It does **not** protect against a process that captures the owner's passphrase or runs inside the owner's interactive session while they sign (keylogger, shared terminal), and **the trust file is only as strong as the file permissions on it**: it is read-only by attribute, but a process running as the same Windows user can replace it with its own public key and then sign with its own private key. The signature therefore stops the *tooling as written* and any actor that does not write outside it, not a hostile same-user process. To make it a real boundary, run `owner-keygen` / `owner-sign` under a Windows account (or on a machine) that the coordinator agent does not use, and grant the engineering account read-only access to the owner directory (`icacls <owner-dir> /inheritance:r /grant <owner>:(F) /grant <engineer>:(R)`); then replacing the trust file requires the owner's account. This is the same-user residual risk stated for the credential store in section 5.
* Trust-file location: a **fixed** directory `<OS user profile>\AppData\Local\DanceFlow\d24-owner`, where the profile directory comes from the operating-system user record (`os.userInfo().homedir`), **never** from `LOCALAPPDATA`, `HOME`, `USERPROFILE` or any other environment variable (a test sets them all and asserts nothing changes). It holds `owner-trust.json` (public key, pinned ledger directory, anchor path, registering account, tool hash, commit), the encrypted private key and the ledger anchor. There is no command-line override (tests inject a directory through a function argument only). **Honest limit:** a process running as the same Windows user can still write that directory (replace the trust file with its own key, or drive the owner commands in a pty before the owner does). `run` prints a loud one-line WARNING on stderr when the directory is writable by the current user or the key was registered by this very account (best effort; it never refuses, and dry runs print nothing). **Open owner decision:** the real separation is either owner-keygen/owner-sign from a **separate Windows account or machine** (grant the engineering account read-only on the owner directory) or a **hardware / WebAuthn-held key**; until one is chosen the signature stops the tooling as written, not a hostile same-user process.

## 4. Environment sanitisation

The child receives an **allow-listed** environment (PATH, SystemRoot, TEMP, USERPROFILE, ... nothing else), not a filtered copy of ours, so unknown variables are dropped by default: `NODE_OPTIONS`, `NODE_USE_SYSTEM_CA`, `NODE_EXTRA_CA_CERTS`, `SSL_CERT_*`, all proxy variables, `NODE_TLS_REJECT_UNAUTHORIZED`, every hosted-DB variable, any variable holding a live key. Only then are `D24_PROOF_STRIPE_KEY`, `..._EXPECT_PLATFORM_ACCT`, `..._EXPECT_CONNECTED_ACCT`, `..._PINNED_SHA256` (from the envelope), `..._AUTHORIZATION` and `D24_PROOF_EVIDENCE_DIR` added; the result must pass the proof's `checkEnvironment` (imported, so the two cannot drift). The key is only in the `--preflight` and `--live` children; git, npm, `--print-hash`, `--allow-list`, `--dry-run` get the base environment. Tests assert this per call.

## 5. Credential storage

Interface `CredentialStore`; implementations in `credstore.ts`, driven through Windows PowerShell 5.1 with `-EncodedCommand` (script text only; the secret goes over **stdin** on write and stdout on read, never argv, never a file in clear, never an env var of the runner).

1. **Windows Credential Manager** (advapi32 `CredReadW/CredWriteW` via P/Invoke, type GENERIC, persistence LOCAL_MACHINE, target `DanceFlow/D24-TEST/<label>`). Preferred.
2. **DPAPI file** (`ProtectedData` scope CurrentUser, label as entropy, base64 file, ACL reduced to the current user with `icacls /inheritance:r`). Fallback.

**What was verified on this machine (2026-11-07, Windows 11, Windows PowerShell 5.1, Node 24).** A write/read/missing-read/delete round trip with a dummy non-Stripe string succeeded for **both** back ends when run from the agent harness's non-interactive Bash tool (no console prompt, stdin piped): Credential Manager about 12 s and DPAPI file about 5 s per full round trip on a loaded machine (each PowerShell call recompiles the P/Invoke type). The dummy entries were deleted. **Not verified:** behaviour under a Task Scheduler task configured "run whether user is logged on or not" or any logon type other than interactive/session-attached. Credential Manager entries with LOCAL_MACHINE persistence are normally readable by the same user in other logon sessions, but CredRead can fail in a non-interactive batch session whose profile/vault is not loaded; DPAPI CurrentUser has the same profile dependency. If a scheduled run is wanted, test with a dummy value in that exact task configuration first. The agent-run path (a logged-in user session) is the one shown to work.

**Threat model (both back ends).** Protects against: the key appearing in git, logs, chat, argv, `ps` listings, shell history, disk images/backups taken without the user's profile, other Windows users. Does **not** protect against: any process running as the same Windows user (Credential Manager has no per-application ACL; DPAPI CurrentUser decrypts for any process of that user, including another agent session), malware in the user session, a user-level admin. Mitigations that actually bound the damage are the key's own properties: `rk_test_`, three permissions (Invoices Write, Customers Write, connected-account Read), a dedicated sandbox with a Stripe-issued test connected account, a short expiry, and expiring it after the run. Keep the key's lifetime to days, not months. `cli provision --check` shows only a fingerprint.

`provision` (`cli.ts`): reads the key from a hidden prompt on a TTY (raw mode, no echo) or from stdin, refuses anything not matching `rk_test_...` (the refusal never echoes the input), refuses positional arguments, writes, reads back, and prints only the fingerprint prefix to put in the envelope. Positional secrets are rejected by the argument parser.

## 6. Post-run

* **Cleanup verification** from the evidence JSON only: `cleanup.verifiedEmpty`, nothing skipped/stopped early, no remaining or unverifiable objects, `outcome OK`, `calls <= ceiling`, nothing refused by the allow-list, manifest in the evidence equals the envelope.
* **Hashing**: SHA-256 of every evidence/transcript file as written by the proof plus the sanitised child output, listed in the report.
* **Redaction scan** over evidence, transcript, child stdout/stderr and the gate log: Stripe key shapes (`sk/rk/pk_test/live`), `whsec_`, bearer/Authorization, emails, and the exact key value held in memory (any form). Findings report kind and count, never the text. A secret finding forces **FAIL** and the report tells the operator to expire the key now. Unmasked account ids are a warning.
* **Decision**: `PASS` (all evidence conditions hold), `FAIL` (abort, failed check, over ceiling, allow-list refusals, remaining objects, secret in output, non-zero exit), `UNVERIFIABLE` (lost create responses, no/unreadable evidence, cleanup not verified), `BLOCKED` (refused before running). The report lists check PASS/FAIL counts, verdict counts, request counts used/ceiling/refused, unverifiable count, cleanup disposition, abort cause with a diagnosis, safety findings, evidence hashes, the key-expiry reminder, and always states that the ledger half of V4/V7 is **NOT TESTED** by this proof revision.

## 7. `--dry` / `dry`

`cli dry` and `run --dry` use `fakeChild.ts` (emulates git, npm and every proof flag, writes fake evidence), a throw-away ledger in a temp dir and a store factory that throws if called. Tests assert the store is never reached in dry mode, and that earlier gate failures never reach the store in real mode.

## 8. Stripe CLI login, restricted keys, owner-only steps (Stripe documentation only; no API call was made)

Sources read: docs.stripe.com `stripe-cli/keys`, `cli/login`, `keys`, `keys/restricted-api-keys`.

**Does `stripe login` yield a key?** The documented flow is browser device pairing: the CLI shows a pairing code, the Dashboard opens, and the user "confirm[s] the code and configure[s] the CLI's access to accounts, sandboxes, and live mode". Credentials are stored in the OS credential store and refreshed automatically; `stripe login list` shows authorized accounts/sandboxes, `stripe reauth` changes permissions, `stripe logout` revokes. For CLI versions newer than 1.50.0 an Administrator or IAM Admin must first enable CLI access (Settings -> Team and security -> MCP and CLI access). `--non-interactive` prints a URL, code and a `--complete` command (it activates automatically when stdin is not a terminal), so a human approval in a browser is still required.

**What the docs do not say (could not verify):** the exact credential type the browser flow stores (a refreshable session, not documented as an `rk_test_` key), its permission scope (only "configure the CLI's access" is stated; whether it can be limited to Invoices+Customers+connected-account read is **not documented**), and its lifetime. `stripe login --interactive` and `STRIPE_API_KEY` / `--api-key` accept a manually supplied key, so the CLI is only a transport for a key that already exists. **Do not assume the CLI grants scoped permissions.** The proof does not use the CLI and requires an `rk_test_` key; a CLI session is not usable for it, and a session with broader scope than the restricted key would be a larger risk, not a smaller one.

**Can a restricted key be created without the Dashboard?** Per the docs, restricted keys are created in the Dashboard ("Create restricted key", set each resource to None/Read/Write, "complete the two-factor verification we send you", copy once). I found no documented API or CLI command to create a restricted key for a sandbox (the Stripe Apps RAK flow generates a key when a user installs an app, which does not fit). **Could not verify** that no such endpoint exists; treat creation as Dashboard-only with 2FA. The docs do not mention an expiry chosen at creation: expiry is manual ("Expire key") or via rotation with an optional scheduled expiry (grace up to 7 days). Plan the key's end date at the envelope level and expire it by hand after the last run. In a sandbox, all keys including restricted ones remain revealable later. Keys can be tagged as an autonomous-agent key, which attaches approval rules; whether that interacts with this proof's calls is **not verified** and would be a decision for the owner (do not enable it unless wanted).

**Owner-only (cannot be delegated):**
1. Create the new sandbox `DanceFlow D24-M3 TEST` and its single Express (or controller-equivalent) test connected account; tell engineering the two `acct_` ids.
2. In that sandbox, create the restricted key (Invoices Write, Customers Write, connected-account Read, everything else None), pass the 2FA prompt, and put it into `provision` via the hidden prompt (or have the coordinator do so at the owner's terminal session; the key must not be typed into chat).
3. Record the key's intended expiry date and, after the last run, expire it in the Dashboard.
4. Once: `owner-keygen`. Per envelope: read the printed terms, run `owner-sign`, type the confirmation and passphrase, hand over the signature file. Also confirm the MANUAL facts (sandbox identity, key permissions, no webhook endpoints, account default API version): they are signed as part of the envelope, so the owner is attesting them by signing. The `approval-template` line is kept as the audit text.
5. Optionally enable CLI access only if a CLI is wanted (not needed).

## 9. Limitations

* Same-user processes can read the credential (section 5). PowerShell module/script-block/transcription logging, if enabled by machine policy, can write the credential-read helper's stdout (`SECRET:<value>`) to a log even though the value is never in argv or in the script text: check the logging policy before provisioning, and use a machine without it. Credential Manager/DPAPI stores are readable by any same-user process.
* The ledger lives in the user profile. Detection, not prevention: the hash chain catches edits and middle removal; the **anchor** (count + head hash, in the owner directory, a second location) catches tail truncation, deletion of the ledger and replacement; a missing anchor with entries present also fails closed. A same-user process that deletes *both* the ledger and the anchor, or rewrites both consistently from scratch, is not detected (it can equally read the credential). Counts are bound to the envelope hash (a re-hashed envelope with the same id gets no budget) and a per-credential cap of 5 runs spans all envelopes.
* **Ceiling**: the proof enforces only its own `HARD_CALL_CAP` (40), which cannot be lowered without editing the hashed proof folder, so the runner requires `apiCallCeiling == HARD_CALL_CAP`; a smaller envelope ceiling is refused rather than enforced after the fact. The post-run check against the ceiling remains as a second layer.
* **Timeouts**: on timeout the whole process tree is killed (`taskkill /T /F` by absolute path; process group elsewhere). The result is **UNVERIFIABLE**; the run stays open and the lock stays in the ledger. `reconcile` refuses while the lock-holder PID is alive and never gives the run back.
* Not hardened (accepted, P3): a same-user `.git/config` clean/textconv filter or global git config could in principle mask edits from the git gates (only `core.fsmonitor` is neutralised); `recheck-tree` does not rehash `node_modules` (the proof's pinned-manifest check and `npm ci` integrity cover the dependency side); a reconciler exit code of 0 for CONSISTENT is a #415 matter.
* **Ledger writers** (`endRun`, `reconcile`, `startRun`) append under a short `append.lock` (exclusive create, retry 5 s, stale after 60 s), so two writers cannot produce the same `seq` and brick the chain; `reconcile` also holds it while it checks the run lock.
* **Input hygiene**: `validateEnvelope` rejects C0/C1 controls (ESC, CR, LF, NUL), DEL, soft hyphen, zero-width, bidi and line-separator characters in every string and every object key of the envelope, before any other check, and the refusal text never echoes them.
* **System paths**: the Windows directory is the fixed `C:\Windows` (verified to contain System32); `SystemRoot` and drive letters from the environment are ignored; the git fallback path is `C:\Program Files\Git\cmd\git.exe`.
* Accepted (N-7, N-10): the ledger chain has no secret, so a same-user process can rewrite ledger and anchor consistently (detection only; the owner could additionally sign anchor heads in a future change); the store kind is read from a second read of the envelope file after validation (it only selects wcm versus dpapi for a label the validated envelope supplies). N-8 and N-9 concern the #415 reconciler, which is not part of this branch.
* The runner pin means any edit to `scripts/qa/d24-test-runner/` (other than `__tests__`) needs a new envelope and a new signature.
* `npm ci` needs the npm registry (not Stripe). Dependency integrity is lockfile integrity hashes; the manifest covers only the proof folder (not tsx or `node_modules`) as the proof README states.
* The runner trusts the proof's evidence format; a changed proof means a new manifest and a new envelope.
* Nothing here was run against Stripe; the fake child proves control flow only.
