# D24 M3-C — studio-owned one-off client invoice (draft creation/editing only)

Status: **local only, dark, DRAFT PR stacked on M3-A (PR 394). NOT applied to any hosted database.** Migration `20270209090000_d24_m3c_client_invoice.sql` (rollback in `rollback/`). `D24_HOSTED_INVOICE_CREATION` stays OFF. No Stripe call (live or test) is made or wireable from this package; no merge, no deploy, no env change.

## 1. Owner decisions implemented
| | Decision | Where |
|---|---|---|
| D1 | A studio-issued **one-time** invoice to one of the studio's own clients, on the studio's connected account. Not a DanceFlow platform subscription invoice, not a Checkout payment, not a membership invoice, not a DanceFlow payment record. | Type name `studio_client_invoice` (M3-A refuses any type containing `subscription`); no FK to `payments` / `hosted_invoice_payments`; nothing here writes either. |
| D2 | Business object separate from subscriptions: studio, existing client (same-studio in the DB), creating staff member, itemized lines, currency, lifecycle, optional originating reference, trusted Stripe registration once created. | `studio_client_invoices`, `_lines`, `_audit`, `_limits` |
| D3 | Only `studio_owner` / `studio_admin`. One SQL helper + one TS function; granular permissions later change neither the callers nor the interface. | `public.studio_billing_permission(studio, permission)`; `authorizeClientInvoiceActor("draft"\|"view")` |
| D4 | First slice = DRAFT create/edit. `draft` and `provider_draft_created` modeled; finalize / hosted payment link / send / collect / reminders / void are DESIGNED (§6) but have no status value, column, function or grant. A draft has no payment URL and the UI says so. | `sci_status_chk`; UI copy; contract test |
| D5 | USD, integer cents, positive amounts, quantity bounds, bounded lines, stored total = sum of lines (DB-enforced), configurable **fail-closed** limits, seeded with the owner-approved initial values (§5); no platform fee. | `studio_client_invoice_limits` seeded 500/500000 |

## 2. Data model
- `studio_client_invoices(id, studio_id, client_id, request_key, status, currency='usd', total_cents, line_count, version, reference_type/id/note, created_by, last_edited_by, …registration…)`.
  - `client_id`: FK to `clients` **plus** a trigger requiring `clients.studio_id = studio_id` (the existing `clients` table is not altered).
  - Optional reference: `appointment | event | payment` (id, same-studio checked in the trigger against `appointments` / `events` / `payments`) or `other` (free-text note, no id). It is a *reference only* — it never creates, links or settles a payment row.
  - Registration columns (`intent_id, registry_id, stripe_account_id, stripe_customer_id, stripe_invoice_id, livemode, provider_draft_created_at`) are NULL for a draft and all-set for `provider_draft_created` (CHECK). They are written only by `studio_client_invoice_link_registration` (service_role) from a **registered** M3-A intent whose registry row matches studio + account + invoice + object; nothing client-supplied except the Stripe customer id (format-checked, set once).
  - `request_key` (uuid per form render) + unique `(studio_id, request_key)`: double submit returns the existing invoice, no second row, no second audit row.
  - `version`: optimistic concurrency token; a stale edit is refused with `40001`.
- `studio_client_invoice_lines(invoice_id, studio_id, position 1..100, description 1..200 no control chars, quantity 1..100000, unit_price_cents, line_total_cents)`; composite FK `(invoice_id, studio_id)`; `line_total = quantity × unit` (CHECK). Lines are replaced (delete + insert in one call), never updated.
- **Total consistency:** deferred constraint triggers on both tables require `total_cents = sum(lines)` and `line_count = count(lines)` at COMMIT, so no code path (including a hand-written owner-role statement) can leave them disagreeing.
- `studio_client_invoice_audit`: append-only (update/delete/truncate refused), FK to the invoice, records actor (`auth.uid()`), role at the time, AAL (`aal1|aal2|unknown`, recorded **not required**), version, client, total, line count and a SHA-256 of the canonical content. The registration link is audited with no human actor and the intent id. Only *successful* writes are audited (a refusal rolls back, taking its own audit row with it); refusals are visible as the PostgREST error.
- `studio_client_invoice_limits`: singleton; NULL `min/max` ⇒ every draft refused (`55000 client_invoice_limits_not_configured`). Also `max_lines` (default 25, hard ≤100) and `max_quantity` (default 1000, hard ≤100000). CHECKs: min ≥ 50¢ (Stripe's USD minimum), max ≤ $999,999.99 (below Stripe's maximum). No API role can write it; changing it is an owner-run SQL statement (§5).

## 3. Authorization
- `studio_billing_permission(p_studio_id, p_permission)` — SECURITY DEFINER, pinned `search_path`, EXECUTE only to `authenticated` (RLS policies call it as the querying role). It takes **no user id**: it reads `auth.uid()`, requires `role = authenticated`, and checks an **active** `user_studio_roles` row for that studio. Permissions `client_invoice.draft` and `client_invoice.view` both map to `studio_owner`/`studio_admin` today. **No platform-admin branch**: a platform admin without a studio role is refused (acting across studios is a separate, deliberate decision). Unknown permission ⇒ false.
- `studio_client_invoice_save_draft(...)` — the only content write path; `authenticated` only. Every call: verified JWT (`sub`, `role=authenticated`, unexpired `exp`) → permission for **the studio passed in** → validation (limits first, fail closed) → advisory lock on `(studio, request_key)` → writes under the trigger writer flag → audit row.
- Another studio's invoice and a missing invoice are indistinguishable (`42501 client_invoice_not_found`); a studio the caller is not in is `client_invoice_forbidden`.
- RLS: staff with `client_invoice.view` read invoices, lines and audit of their studio; **no insert/update/delete grant or policy** exists for any API role. Read is deliberately the same (owner/admin) set as write for now — widening "view" to other staff is a one-line change in the helper (decision for the owner; not made here).
- TS: `authorizeClientInvoiceActor()` asks the helper and returns the exact `AuthorizedBillingActor` shape M3-B expects (`verified, studioId, userId, canManageBilling`). Studio and user come from the verified session, never from the request; the form's `studioId`/`total`/`stripe_*` fields are ignored (tested).

## 4. M3-A / M3-B integration (contract)
- **Registered with M3-A exactly as documented:** `public.d24_owns_studio_client_invoice(uuid, text) returns boolean`, STABLE, SECURITY DEFINER, pinned path; `d24_register_business_object_type('studio_client_invoice', 'public.d24_owns_studio_client_invoice(uuid,text)'::regprocedure)` runs in the migration. True only when the invoice id (uuid text) exists in that studio (draft **or** registered, so a replayed `register` still passes); malformed/NULL ⇒ false, never an error.
- `studio_client_invoice_creation_spec(invoice, studio)` (service_role): the orchestrator's trusted content source — returns lines/total/currency/client for a **draft that is consistent and inside the current limits**, else NULL. `src/lib/billing/clientInvoices/resolver.ts` maps it to M3-B's `InvoiceSpec` (`customerProfile` from the studio's own `clients` row, quantity folded into the line description, `daysUntilDue` 30). It is exported but registered nowhere.
- `studio_client_invoice_link_registration(invoice, studio, intent, expected_version, customer?)` (service_role; `expected_version` = `creation_spec.version` read before the provider call, refused with `40001` if the draft changed since): called by the (future) orchestrator wiring **only after** `createHostedInvoice` returns `registered`. Moves `draft → provider_draft_created` (content frozen forever), copies account/invoice/livemode/registry from the ledger, audits it.
- **The seam:** `creationPort.ts` — `getClientInvoiceCreationPort()` returns `null` in this package. The UI action `requestClientInvoiceProviderDraftAction` refuses *before any authorization or database call* unless `D24_HOSTED_INVOICE_CREATION === "on"`, and then still refuses because no port exists. Coordination note for d24-m3b: the wiring package should map the verified actor straight onto `AuthorizedBillingActor`, call `createHostedInvoice({ businessObjectType: "studio_client_invoice", businessObjectId, requestKey })` with `CLIENT_INVOICE_SPEC_RESOLVERS`, then call the link function with the service-role client. M3-B's `PRODUCTION_INVOICE_SPEC_RESOLVERS` stays empty until that package.
- **Edit vs creation race (review P1):** `save_draft` refuses (`not_editable`) while any live M3-A intent (`pending|provider_created|registered`) exists for the invoice, and the link refuses a version that differs from the one the provider invoice was built from, so the frozen content always equals what Stripe holds.
- Immutability once registered: the invoice trigger refuses every update unless the old status is `draft`; line insert/delete refuse unless the parent is `draft`; the save function refuses with `55000 client_invoice_not_editable`.

## 5. Monetary policy (OWNER APPROVED initial launch limits, not permanent pricing)
- **USD only; minimum finalized payable invoice $5.00 (500¢); maximum $5,000.00 (500,000¢)**; ≤25 lines, quantity ≤1000. Seeded by the migration into `studio_client_invoice_limits`; changeable only by the migration owner (no API role can write). A NULL/blank configuration or a missing row refuses every draft (fail closed). The table's hard CHECKs stay: min ≥ 50¢ (Stripe's USD minimum) and max ≤ $999,999.99.
- **Where each bound applies.** The **maximum** is a hard stop on draft save (any single line, any running total) *and* at provider-spec time. The **minimum** applies where a provider spec is produced (`studio_client_invoice_creation_spec` returns NULL below it), not at draft save: an incomplete draft below $5.00 (e.g. 499¢) can be saved and edited, but can never become a provider spec. Every saved amount is still at least 1¢.
- **No adjustments exist or may be added:** no tax, discount, fee or credit line. Negative and zero amounts are refused by the function and by CHECKs on the lines table; the stored total must equal the sum of lines at commit.
- **No new platform fee, no automatic collection, no automatic sending.** Creation stays OFF behind `D24_HOSTED_INVOICE_CREATION`.
- Reasoning (kept for the record): Stripe's USD minimum is $0.50 and card fees are 2.9% + 30¢, so a $5 floor avoids fee-dominated amounts; existing DanceFlow ceilings ($100,000 direct payment `MAX_DIRECT_PAYMENT_AMOUNT`, $100,000 event ticket `MAX_TICKET_PRICE_CENTS`) serve staff-present flows, while an emailed, card-payable invoice carries more dispute and mistaken-send exposure, so the initial ceiling is $5,000 and is raised only on evidence.
- To change later (owner decision; migration owner only): `update public.studio_client_invoice_limits set min_total_cents = <n>, max_total_cents = <n>;`. Lowering the maximum makes `creation_spec` return NULL for saved drafts above the new ceiling (they stay readable and editable down).

## 6. Designed, NOT implemented (separately gated)
Finalize (Stripe `finalize`), hosted payment-link display, sending, collection/auto-advance, reminders, void/uncollectible, credit notes. Design constraints for those packages: each is a new status value (extending `sci_status_chk` by migration), each a service-role/orchestrator transition with its own audit action, each behind its own switch; the payment link is read from Stripe only after finalize and never stored as authority; settlement continues to arrive only through the D24 webhook/ledger path (M1) — never inferred from creation, finalize or send.
