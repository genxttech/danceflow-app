# D24 M3-B — inactive hosted-invoice creation orchestrator

Status: **draft, dark, TypeScript only. No SQL, no UI, no route/action call site, no Stripe client constructed, no Stripe call of any kind (live or test), nothing applied to any hosted database.** Stacks on the M3-A SQL (`d24_intent_*`, hardened `d24_register_invoice`); M3-A must be applied before anything here could ever be activated.

## What shipped
`src/lib/payments/hostedInvoice/create.ts` (server-only):
- `createHostedInvoice(request, deps)`, `resumeIntent(intentId, actor, deps)`, `sweepRecoverableIntents(deps, opts)` (bounded, unscheduled), `createSupabaseIntentStore(supabase)` (the only place the M3-A function signatures appear), `deriveIdempotencyKey`, `livemodeFromSecretKey`, `isHostedInvoiceCreationEnabled`.
- Flag `D24_HOSTED_INVOICE_CREATION`: only the exact string `on` enables it; checked before any database or Stripe access in all three entry points.
- The Stripe client is an injected interface with exactly two operations (`createDraftInvoice`, `addInvoiceLines`). No finalize / send / pay / void exists in the interface. Drafts use `collection_method: send_invoice`, `auto_advance: false`; Stripe sends nothing for a draft.
- `PRODUCTION_INVOICE_SPEC_RESOLVERS` is **empty** (decision D1 pending). A resolver returns the customer / currency / lines from trusted server records (or `null` for "not this studio's object"); nothing about the invoice content comes from the request.

## Flow
authorize (caller-verified `AuthorizedBillingActor`; studio/user derived from it only) → resolve spec (ownership) → resolve account from `studios.stripe_connected_account_id` + `stripe_connect_charges_enabled` (fail closed) → `d24_intent_begin` (key derived from studio+type+object+requestKey+content fingerprint; SQL re-resolves the account and re-checks ownership, and its account must equal ours) → Stripe create + lines with the intent key (and `:lines` suffix) in the connected account → validate the response (draft, send_invoice, customer, currency, no subscription markers, total equals spec) → **id and livemode taken from the response**; livemode must equal the deployment key mode (`sk_live_`/`rk_live_` ⇒ true, `sk_test_` ⇒ false, anything else refuses everything) → `d24_intent_mark_provider_created` (SQL re-checks the key mode, account and studio) → `d24_intent_register`. The caller must not finalize or send unless the result is `registered`.

## Recovery
- `resumeIntent`: `provider_created` ⇒ register only (never a Stripe call). `pending` ⇒ re-derive the spec from trusted records; refuse if the content fingerprint (key suffix) changed, if the account changed, or if the intent is older than 20 h (Stripe forgets idempotency keys after ~24 h and would create a second invoice) — otherwise re-issue the create with the same key. A studio actor can only resume its own intents; foreign and unknown ids both return `intent_not_found`. The system actor is the exact object `{ system: "d24_recovery" }`.
- Because the ledger stores no payload, a changed spec under the same `requestKey` yields a different key and is then refused by the ledger's one-live-intent-per-object rule (`intent_payload_conflict`). A second invoice for one object requires the first to be `failed`/`abandoned` (M3-A policy).
- Retryable Stripe failures (connection, 5xx, 429, key-in-use) leave the intent `pending`; permanent ones mark it `failed`. Messages from Stripe or the database are never returned.

## Owner decisions D1–D6 (applied)
- **Draft only.** The injected Stripe interface has exactly `ensureCustomer`, `createDraftInvoice`, `addInvoiceLines` (pinned by a contract test; no finalize/send/pay/void exists to call). `auto_advance` must be `false` in responses. A `hosted_invoice_url` in a draft response is unexpected: refused (`stripe_response_invalid`), never returned or reported as a payment link. Results carry no URL.
- **Crash rule.** `pending` is never assumed to have advanced: after a crash between Stripe success and `mark_provider_created`, resume re-issues the create with the SAME key, Stripe returns the same invoice, then mark + register (tested: crash before the Stripe call, after create before lines, and after create before mark).
- **Customer.** A spec carries either `stripeCustomerId` or `customerProfile {clientRef, name, email?}` (exactly one), resolved by the trusted resolver from the DanceFlow client record. A profile is materialized via `ensureCustomer` in the connected account with key `<intent key>:customer` (idempotent; livemode and id validated; metadata informational only). Persisting the resulting Stripe customer id back on the client record is the M3-C resolver's concern.
- **M3-C contract.** A resolver `(supabase, studioId, businessObjectId) => InvoiceSpec | null` must prove the object belongs to that studio and supply USD-only lines with its own fail-closed limits (this module also caps at 25 lines / 10,000,000 cents). Nothing is registered in `PRODUCTION_INVOICE_SPEC_RESOLVERS`. Authorization is an `AuthorizedBillingActor` minted by M3-C's owner/admin check; granular billing permissions can replace the check without changing this interface.

## Idempotency-key retention integrity (owner requirement; supersedes the earlier local 20 h window and key-suffix fingerprint)
Stripe idempotency keys are not retained forever, so replaying an old key can create a duplicate invoice. The orchestrator therefore never decides replay itself:
- **Fingerprint:** `deriveRequestFingerprint` (sha256 hex of studio, type, object, customer/profile, currency, terms, lines) is computed before the first provider call and passed to `d24_intent_begin`. Same key + different fingerprint ⇒ the ledger raises 23505 `d24_request_fingerprint_mismatch` ⇒ `request_fingerprint_mismatch`; nothing is created and Stripe is not called. The idempotency key itself is `d24inv_<32 hex scope>`, independent of content; a replacement key is never generated.
- **Ambiguous end ⇒ stop:** timeout / connection / 5xx / unclassified errors record `d24_intent_record_outcome(outcome_unknown=true)` and return `outcome_unknown` (not retryable). A later `createHostedInvoice` on that pending intent refuses without calling Stripe. Definite non-processing (429, key-in-use) is retryable with the same key; definite rejection (4xx) terminates the intent (or escalates to review if the ledger refuses because the outcome is unknown).
- **Recovery only through the DB claim:** `resumeIntent` on a `pending` intent re-derives the spec from trusted records and calls `d24_intent_claim_recovery` with the recomputed fingerprint. Only `replay_permitted` (inside the safe window, fingerprint match, same account, exclusive lease) replays, with the ORIGINAL key and account; `lease_held` ⇒ `recovery_in_progress` (retryable); `register_only` ⇒ register without Stripe; `needs_review` ⇒ stop, nothing else. Recovery never finalizes, sends or collects (no such capability exists).
- **Verify before trusting:** a returned invoice/customer that does not match the trusted record (customer, currency, total, draft, send_invoice, auto_advance false, no hosted URL, no subscription markers, livemode = deployment key mode) ⇒ the invoice id is kept (`mark_provider_created`, when livemode allows) and the intent is flagged `needs_review` via `d24_intent_flag_review`; it is never registered. A ledger `needs_review` outcome from register, or a permanent registration refusal, also ends in `needs_review`. Metadata is never read back for ownership.
- **Offline fake models pruning:** `FakeStripe` forgets keys after a configurable retention (default 24 h); the unit tests prove a replay past retention would create a second invoice and that the 12 h ledger window refuses to replay it.
- **Operator path:** `d24_op_flag_creation_review / d24_op_attach_creation_invoice / d24_op_abandon_creation / d24_op_list_creation_reviews` are authenticated-JWT (platform_admin + AAL2) functions for the future admin action layer, not service_role; they are not called here. The orchestrator's own review escalation uses the service-role `d24_intent_flag_review`.
- **Evidence:** scenarios 1–10 in `create.d24.test.ts` (unit) and `create.d24.pg.test.ts` (real M3-A Postgres: 4 fingerprint mismatch, 5 concurrent recovery, 6 unknown timeout, 7 recovery after the window (created_at aged via the QA trigger bypass), 9 account changed, 10 flagged review not resumed/listed; 1/2/3/8 in the unit suite and the existing PG crash tests).
