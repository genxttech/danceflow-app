# Retrospective rulebook audit: competition formats, disciplines and divisions

Status: **draft for review**, docs only. Built against `origin/release/website-embeds` at `ba970a67f` (2026-11-22). Part of the retrospective rulebook audit (owner directive 2026-11-22). No code, migration or behavior was changed and nothing below has been silently corrected: every proposed correction needs an owner decision.

**Scope.** Competition formats (offerings), disciplines/styles and the division structure (levels, age categories, contest types) that the Competition Setup Wizard builds from the `studio_simple@3` profile, for NDCA (ballroom), UCWDC (country) and WSDC (west coast swing) structures and the Studio/Custom additions. Age *thresholds and calculation*, amateur/professional status, and registration/partner mechanics are in the sibling files (`inventory-age-eligibility.md`, `inventory-classifications.md`, `inventory-registration-partners.md`); this file keeps only the offering and division *structure*. Scoring, results, scratches, organizer authority and appeals belong to other audit sessions.

## Material discrepancies and decisions in this file

- **FD-18 inconsistent (material):** NDCA Formation/Team Match are offered as 2-100 member teams with one open division; the rule book requires four to eight couples (XII.D), age/grade categories (XII.C), and a Team Match of at most five teams from one school (I.G.1.e).
- **FD-32 inconsistent (material):** UCWDC Country Team accepts 2-member teams; UCWDC Teams divisions require 3 or more competing members (ShowTime excepted) and offers defined Team divisions (II.E).
- **FD-27 inconsistent (material):** UCWDC divisions have a gender/Mixed-Role dimension that the Country schemes omit.
- **FD-30 inconsistent:** Spotlight is for ProAm/ProPro pairs but is built as an unconstrained two-person entry.
- **FD-11 requires interpretation:** youth Student/Student is blocked because NDCA II.A.6.b and II.B.8 conflict (already recorded in the profile).
- **FD-29 / FD-39 requires interpretation:** where UCWDC Showcase belongs (offering vs level) and whether organizer-added subdivisions need advance publication.

## How to read this inventory

**Row = one rule-dependent behavior.** Columns: ID | behavior (what the software does) | where implemented | decision or spec reference | automated tests | governing source | classification | proposed correction | owner decision needed.

**Classification (exactly one per row)**

| Value | Meaning in this inventory |
|---|---|
| verified compliant | The cited rulebook section was read in the actual source document (SHA-256 verified, see below) and the software behavior matches it. |
| inconsistent | The software does something that differs from, or conflicts with, a rule that was read. A proposed correction is given; nothing has been changed. |
| unsupported | No provided governing source supports the behavior (it is DanceFlow or organizer policy, or the source says nothing: NOT SPECIFIED IN PROVIDED SOURCE, "NSPS"), **or** the rule exists in a provided source but the software does not implement it. The Behavior cell is tagged **[POLICY]** (no governing-body basis, labelled Studio/Custom) or **[GAP]** (rule exists, software does not enforce it) so the tracker can tell the two apart. |
| requires interpretation | The source is ambiguous or two sections conflict, or the source could not be used. Fails closed until the owner decides. |

**Definition rows vs enforcement rows.** A row that records a stored definition (a label, a threshold, a role set) is judged on whether the stored values match the source, so a matching definition is *verified compliant*. Whether anything enforces that definition when someone registers is recorded in its own row, and a rule that exists only as an advisory note or not at all is **unsupported [GAP]** (or **inconsistent** when the product offers a structure that the rule contradicts).

(2) The per-value division `eligibility` metadata (`min_age`, `under_age`, `note`) in the profile is neither displayed nor read by any code (search of `src/` for `min_age`, `under_age` and `.eligibility`: only the profile and type files, the two profile seed migrations and tests contain them). What the wizard does display is the axis-level `note` and the format-level `eligibility_note` (`src/app/app/events/[id]/competition/new/CompetitionSetupWizard.tsx` lines 212 and 584); neither gates anything. (3) Registration validation is the shared TypeScript/SQL quote path (`registrationPricing.ts` / `_comp10c_quote`, `participantRoles.ts` / `_comp10c4_participant_shape_errors`); it checks participant counts, relationship roles and lead/follow shape, not age, classification, membership or registry status.
