# Retrospective rulebook audit: age and eligibility calculations

Status: **draft for review**, docs only. Built against `origin/release/website-embeds` at `ba970a67f` (2026-11-22). Part of the retrospective rulebook audit (owner directive 2026-11-22). No code, migration or behavior was changed and nothing below has been silently corrected: every proposed correction needs an owner decision.

**Scope.** Age categories and thresholds as the profile stores them, age reference dates and couple-age rules, birth-date capture, and the eligibility checks the rulebooks require (proficiency, level, membership-linked eligibility), against NDCA X / II, UCWDC II.D-F and WSDC Definitions / 3.1-3.2. **Headline finding: DanceFlow stores the right numbers but nothing calculates or enforces age or eligibility** (AE-19). Division values (labels and structure) are in `inventory-formats-divisions.md`; status classifications (amateur/professional/Pro-Am) are in `inventory-classifications.md`; partner and membership requirements at registration are in `inventory-registration-partners.md`.

## Material discrepancies and decisions in this file

- **AE-19 inconsistent (most material):** no registration or check-in logic compares a participant's age with the division's age category for any body; division age metadata is never displayed or read, and date of birth is optional. Owner decision needed on enforcement versus an organizer verification gate before public activation.
- **AE-02 requires interpretation:** Senior I-IV need two thresholds (older and younger partner) but are stored with one.
- **AE-16 / AE-17 requires interpretation:** the sources do not say whose age counts in ProAm/Pro-Am and UCWDC Couples age-restricted divisions, and the three bodies use different reference dates.
- **AE-21 [POLICY]:** `unverified` entries can be scheduled and placed although readiness counts only eligible/waived.
- **AE-08 inconsistent (minor):** the UCWDC Couples Masters note omits the 16-and-over-partner exception.

## How to read this inventory

**Row = one rule-dependent behavior.** Columns: ID | behavior (what the software does) | where implemented | decision or spec reference | automated tests | governing source | classification | proposed correction | owner decision needed.

**Classification (exactly one per row)**

| Value | Meaning in this inventory |
|---|---|
| verified compliant | The cited rulebook section was read in the actual source document (SHA-256 verified, see below) and the software behavior matches it. |
| inconsistent | The software does something that differs from, or conflicts with, a rule that was read. A proposed correction is given; nothing has been changed. |
| unsupported | No provided governing source supports the behavior (it is DanceFlow or organizer policy, or the source says nothing: NOT SPECIFIED IN PROVIDED SOURCE, "NSPS"), **or** the rule exists in a provided source but the software does not implement it. The Behavior cell is tagged **[POLICY]** (no governing-body basis, labelled Studio/Custom) or **[GAP]** (rule exists, software does not enforce it) so the tracker can tell the two apart. |
| requires interpretation | The source is ambiguous or two sections conflict, or the source could not be used. Fails closed until the owner decides. |

**Definition rows vs enforcement rows.** A row that records a stored definition (a label, a threshold, a role set) is judged on whether the stored values match the source, so a matching definition is *verified compliant*. Whether anything enforces that definition when someone registers is recorded in its own row, and a rule that exists only as an advisory note or not at all is **unsupported [GAP]** (or **inconsistent** when the product offers a structure that the rule contradicts).

(2) The per-value division `eligibility` metadata (`min_age`, `under_age`, `note`) in the profile is neither displayed nor read by any code (search of `src/` for `min_age`, `under_age` and `.eligibility`: only the profile and type files, the two profile seed migrations and tests contain them). (3) Registration validation is the shared TypeScript/SQL quote path (`registrationPricing.ts` / `_comp10c_quote`, `participantRoles.ts` / `_comp10c4_participant_shape_errors`); it checks participant counts, relationship roles and lead/follow shape, not age, classification, membership or registry status.
