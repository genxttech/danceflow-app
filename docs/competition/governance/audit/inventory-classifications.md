# Retrospective rulebook audit: amateur / professional / Pro-Am / Pro-Pro classifications

Status: **draft for review**, docs only. Built against `origin/release/website-embeds` at `ba970a67f` (2026-11-22). Part of the retrospective rulebook audit (owner directive 2026-11-22). No code, migration or behavior was changed and nothing below has been silently corrected: every proposed correction needs an owner decision.

**Scope.** How the software represents amateur, professional, Pro/Am student, Pro/Am, Pro/Pro, Mixed, Student/Student and equivalent classifications, against NDCA II.A/II.B, UCWDC II.A/II.F and the WSDC competitor model. The structure (which roles an entry may hold) is audited in the rows below; where the rule is about a person's *status* (who counts as professional or amateur) the software has no status concept, so those rows are gaps. Age rules are in `inventory-age-eligibility.md`; partner counts, lead/follow and membership at registration are in `inventory-registration-partners.md`; division structure is in `inventory-formats-divisions.md`.

## How to read this inventory

**Row = one rule-dependent behavior.** Columns: ID | behavior (what the software does) | where implemented | decision or spec reference | automated tests | governing source | classification | proposed correction | owner decision needed.

**Classification (exactly one per row)**

| Value | Meaning in this inventory |
|---|---|
| verified compliant | The cited rulebook section was read in the actual source document (SHA-256 verified, see below) and the software behavior matches it. |
| inconsistent | The software does something that differs from, or conflicts with, a rule that was read. A proposed correction is given; nothing has been changed. |
| unsupported | No provided governing source supports the behavior (it is DanceFlow or organizer policy, or the source says nothing: NOT SPECIFIED IN PROVIDED SOURCE, "NSPS"), **or** the rule exists in a provided source but the software does not implement it. The Behavior cell is tagged **[POLICY]** (no governing-body basis, labelled Studio/Custom) or **[GAP]** (rule exists, software does not enforce it) so the tracker can tell the two apart. |
| requires interpretation | The source is ambiguous or two sections conflict, or the source could not be used. Fails closed until the owner decides. |

**Definition rows vs enforcement rows.** A row that records a stored definition (a label, a threshold, a role set) is judged on whether the stored values match the source, so a matching definition is *verified compliant*. Whether anything enforces that definition when someone registers is recorded in its own row, and a rule that exists only as an advisory note or not at all is **unsupported [GAP]** (or **inconsistent** when the product offers a structure that the rule contradicts).

**Page numbers** are printed page numbers: NDCA = number at the foot of the page, UCWDC = "Page n of N" footer, WSDC = footer number. Section references follow the numbering printed in each document (for example NDCA II.B.7.c). Paraphrases only; no long quotations.

**Standing facts that frame every row.** (1) The only rules profile a new setup can use is `studio_simple@3` (Studio / Custom Rules, `sanction: none, claimable: false`); NDCA, UCWDC and WSDC profiles are listed in the wizard but not selectable (FD-01). Offerings named `ndca_*` and the UCWDC/WSDC offerings are therefore Studio/Custom implementations *of* a governing body's structure, not a sanctioned event. (2) The per-value division `eligibility` metadata (`min_age`, `under_age`, `note`) in the profile is neither displayed nor read by any code (search of `src/` for `min_age`, `under_age` and `.eligibility`: only the profile and type files, the two profile seed migrations and tests contain them). What the wizard does display is the axis-level `note` and the format-level `eligibility_note` (`src/app/app/events/[id]/competition/new/CompetitionSetupWizard.tsx` lines 212 and 584); neither gates anything. (3) Registration validation is the shared TypeScript/SQL quote path (`registrationPricing.ts` / `_comp10c_quote`, `participantRoles.ts` / `_comp10c4_participant_shape_errors`); it checks participant counts, relationship roles and lead/follow shape, not age, classification, membership or registry status.
