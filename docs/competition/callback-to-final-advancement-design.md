## 1. Advancement record, RPC, trigger, audit, immutability

### 1.1 Rule (K0 §6, D-CT-10)

Next-round heats are created **only** from a round in `approved` or later, by `apply_competition_round_advancement`. D-CT-10: nothing is carried into the Final (the tally is staff information); the Final starts clean, from the advanced *set* only.

**Who triggers:** an explicit manager action ("Advance to Final") from the results review, after approval. Not automatic at approve (keeps F2's approve a single-purpose writer, one writer per transition, and lets the manager see the preview first); not coupled to publication (F3 does not exist and K0 §6 says `approved or later`). Recommendation; OD-4.

**Preconditions (all raise a stable `COMP_ADVANCEMENT_*` error; first failure wins):**

1. Caller is a manager of the event; request id present.
2. Source round: `status in ('approved','published')`, `round_type = 'preliminary'`, program `advancement_method = 'promote_callback'`, scoring pin = `studio_callback_tally@1`. A source round in any other status, including a callback that cannot lock because its cut is at or above the couple count, raises `COMP_ADVANCEMENT_SOURCE_STATE` (§1.3, "Callback cut").
3. `p_result_version_id` is the round's **latest `approved`** version, and its `input_hash` still equals the hash rebuilt from current ballots (`COMP_RESULT_STALE`, same check as F2 approve).
4. **No result row has `advanced is null`.** This is the SQL-checkable form of "blocked" (the engine never sets `advanced` when blocked). Refused with `COMP_ADVANCEMENT_BLOCKED` (see §2: such a version should never reach `approved`; this is the second layer).
5. Target round = the division's round with `sequence_number = source + 1`, `round_type = 'final'`, same program/division/event (**read from the round row, never from a heat id**), status `draft` or `scheduled` (otherwise `COMP_ADVANCEMENT_TARGET_ROUND_STATE`). There is a live schedule version (otherwise `COMP_ADVANCEMENT_NO_LIVE_VERSION`) and it is **floor-mode**, i.e. it has numbered floor heats (otherwise `COMP_ADVANCEMENT_FINAL_PLACEMENT_MODE`). **Heat scope is O1's: the live version only** (§3.2.1). The target round has **no non-cancelled heat in the live version and no unplaced non-cancelled heat** (`schedule_version_id` null); otherwise `COMP_ADVANCEMENT_FINAL_HEATS_PRESENT`. Heats in a `draft`, `review`, `superseded` or `archived` version (abandoned drafts, copies) and cancelled heats are ignored. **Revision 11: the shell-reuse path of revisions 9 and 10 is removed** (§3.2.1, "Why shell reuse is removed"): CF1 creates the one Final heat or refuses; it never fills, repairs or reuses an existing heat. Competing writers: §5 and Appendix A.2.
6. Advanced count `> 0` and `≤` the target's **live** capacity (`configuration->>'max_entries_per_heat'`, default 8), re-read at apply, not trusted from the calculation. Capacity is **not** freely editable: it changes only within B1–B7 and the F1 exemption (§3.4.1, §3.4.3), and a change after calculation makes the version stale (capacity is in the hashed evidence), so apply's live read is a second layer, not the main control. Otherwise `COMP_ADVANCEMENT_OVER_CAPACITY`. This also covers `T > capacity` with no tie, which D-CT-4 does not address and the engine does not check (callback spec §11); it is required by F-6 (single-heat Final). OD-2.
7. Every advanced entry is still `confirmed`, not `ineligible`, still in the source round's event, program and division, and has no unresolved competitive-affecting exception (K0 §4.1). Otherwise **apply refuses** with `COMP_ADVANCEMENT_ENTRY_UNAVAILABLE` listing the entries. It never drops the couple and never substitutes another. The **only** route is a correction and deterministic recalculation (§4.1), which is not a manager pick and not a backfill. **Revision 11 note:** after approval every callback heat is certified, and the registration sync skips entries on locked or certified heats (Appendix A.2 row 9), so this status check cannot see a registration cancelled or refunded after approval; the K0 §4.1 exception check (R2, not in this stack) is the second layer.

**Entry rows at apply (revision 12, P2-3; static reading, not runtime proof).** Apply reads the advanced entries' status and eligibility (precondition 7) without locking them, so an update could land between the read and the commit. Evaluation of the reviewer's proposal (lock the advanced entry rows `FOR SHARE` in id order after the rounds, then revalidate):

* **Who writes entry rows, and how.** `sync_competition_entries_from_registration` (a plain `UPDATE … WHERE registration_id = …`), `change_competition_entry_lifecycle` (a plain `UPDATE … WHERE id = …`, then its heat entries), `mark_competition_entry_late` and any direct write through the `competition_manage` policy all take **`FOR NO KEY UPDATE`** on the entry row (non-key updates). The audit trigger `audit_competition_entry_change` (AFTER UPDATE) only inserts history rows and `validate_competition_entry_registration_links` only validates; neither takes a round lock, and no round lock is reachable from an entry update in the tree (U22). Nothing locks entry rows `FOR UPDATE` or `FOR SHARE` today. `change_competition_entry_lifecycle` does **not** lock before its locked/certified check (a plain `EXISTS`).
* **Conflicts.** `FOR SHARE` conflicts with `FOR NO KEY UPDATE` and `FOR UPDATE`, so it serializes apply against every writer above. `FOR KEY SHARE` (what the FK check of the new heat entries takes) conflicts only with `FOR UPDATE` and would **not** stop a status update, so it is the wrong lock; `FOR NO KEY UPDATE` is unnecessary and would block entry readers that lock.
* **Lock, order, revalidation.** After step 5 (the live version `FOR KEY SHARE`) apply runs `select 1 from event_competition_entries where id = any(advanced ids) order by id for share` (**unfiltered**: a `WHERE status …` filter would lock only the matching rows), then runs precondition 7 as a **separate statement**: in READ COMMITTED it takes a fresh snapshot and sees any update that committed while the lock waited. That is sufficient for the apply window: an update that starts after the lock waits for apply's commit. Entry writers take the registration or entry row first and never a round, so there is no cycle with apply's round-then-entry order; waits are bounded by the local `lock_timeout`, and a timeout is the retryable `55P03` (`COMP_ADVANCEMENT_CONCURRENT_CHANGE`). A concurrent entry writer that already holds the row makes apply wait, then revalidate and refuse (`COMP_ADVANCEMENT_ENTRY_UNAVAILABLE`) if the committed state is unavailable. Unverified at runtime: U23.
* **What the named paths really do (corrected in revision 13).** Revision 12 claimed that after apply the sync and `change_competition_entry_lifecycle` can withdraw or scratch an advanced couple on the open Final heat. **That claim is withdrawn.** Both test for a heat entry in a `locked`/`certified` heat, and every advanced couple's callback heat is certified for good, so **both are blocked before and after apply**: a registration cancel or refund leaves the registrant `confirmed`, and the lifecycle RPC (which no app code calls) refuses. The only unguarded writer of an advanced entry is a **direct write**, including the eligibility screen `updateCompetitionEntryEligibilityAction` (`registrations/actions.ts` l.40), which can set an advanced couple `ineligible`. Details, the roster defect that follows, and the alternatives are §4.3; the consolidated writer matrix is Appendix A.2c.
* **Database enforcement and residual (revision 13).** (i) `FOR SHARE` plus revalidation at apply, above. (ii) **Race-safe roster validation at the Final's first start** inside `cf1_guard_final_start` (§5): the roster entries locked `FOR SHARE` in id order under the event and round locks, then revalidated in a separate statement; `COMP_ADVANCEMENT_ROSTER_STALE` on failure. It is fail closed with **no remedy** other than reverting the change, or the withdrawal of §4.3 and §4.4 if the owner adopts it; it protects only the start transaction, and nothing protects after the start. (iii) The revision 12 reason for rejecting a guard on entry changes ("it would make a refund fail") is **withdrawn**: the sync's own `WHERE` excludes advanced entries, so such a guard never fires from the sync; it is alternative B of §4.3. **Residual gaps, stated:** a registration cancelled or refunded between approval and apply, and at any later time, is not detected (sync skipped), except through R2's exception check, which is not in this stack; a change after the Final has started is not caught by (ii) but, with the owner's OD-17 D, at ballot locking, calculation and approval (§4.6 a); an app-level check does not stop a direct database write, which is why (i) and (ii) are in the database; **10D.1 does not cover later changes** (A.2d).
* **Revalidation scope (revision 13).** After the lock, the separate statement checks for every advanced entry: `status = 'confirmed'`, `eligibility_status <> 'ineligible'`, **and that the entry still belongs to the advancement's event, program and division** (those of the source round). `move_entry` exists as an audit change type (June l.298, 10A l.783) but no function writes it. **A division move is also refused by the database for any entry that has a heat entry:** the composite FK `event_competition_heat_entries_entry_fk` on `(entry_id, division_id, event_id)` has no ON UPDATE action (foundation `20260620` l.217–220), so updating `entries.division_id` while a heat entry references the old tuple fails, and every advanced entry has a callback heat entry. The division check is therefore **defence in depth only** (U35). A mismatch lists the entries (`COMP_ADVANCEMENT_ENTRY_UNAVAILABLE`).
* **Multi-row writers and deadlocks (revision 13).** Apply locks entries in id order. A multi-row entry writer (a direct bulk UPDATE) locks rows in scan order, not necessarily id order, so a cycle is possible (the writer holds A and wants B; apply holds B and wants A). PostgreSQL aborts **one** of the two after `deadlock_timeout`: **either side can be the victim**, and which one is not controllable. The exposure is narrow: the sync's `WHERE` excludes advanced entries so it neither locks nor waits on them, the lifecycle function and the app screens update one entry each, so only a direct multi-row write can form the cycle (U31). **Caller-visible behaviour:** if apply is the victim it gets `40P01` (or `55P03` from the local `lock_timeout`), both retryable: CF1-B retries once server-side, then shows "try again", and never retries a permanent `COMP_ADVANCEMENT_*` validation error (`ENTRY_UNAVAILABLE`, `FINAL_HEATS_PRESENT`, …); if the writer is the victim, its caller sees `40P01` and that is outside CF1 (whether the registration and webhook paths tolerate it is unverified, U31). A `FOR SHARE NOWAIT` variant would make apply never wait and so never form a cycle, but it fails apply whenever any advanced entry is mid-update (even an entry-number edit); not adopted, offered as an option.
* **Pre-migration active Finals (revision 13).** A Final round already `active` or later with no advancement (built before CF1): precondition 5 refuses it (`COMP_ADVANCEMENT_TARGET_ROUND_STATE`); apply and the start guard never run for it; the revive guard's locking branch **does not exist** for it (the branch is limited to `draft`/`scheduled` rounds, §5), so it cannot meet `lock_competition_round_ballots`; the entry and dance guards treat it as a callback Final and refuse **new** roster inserts, leaving the existing roster untouched; nothing is rewritten. Unverified: U33.

**Callback cut at or above the eligible-couple count (revision 12, P3d).** E2's readiness marks a callback round `callback_not_danced` when `T` is no longer below the number of eligible couples (E2 l.770, 792), and `lock_competition_round_ballots` then refuses with **`COMP_CALLBACK_NOT_DANCED`** (E2 l.1194–1196): such a round cannot lock, so it stays `active`, never reaches `calculated` or `approved`, and **never reaches apply**. Apply's precondition 2 (source status `approved` or `published`) raises **`COMP_ADVANCEMENT_SOURCE_STATE`** for it. The organizer sees E2's message today; the CF1-B preview reports state `blocked`, reason `callback_not_danced` (read through the E2 blocker function), with the text "Every couple would advance because the cut is at or above the number of couples; this round is not danced and cannot be locked, so no Final can be built from it automatically." **Gap, not solved here:** E2's message says advancement "is applied in results (F2)", but no F2 or HL1 code handles a not-danced round (the identifier occurs only in E2), so in this stack there is no route that builds the Final for "everyone advances"; nobody is picked by hand (D-CT-4). Recorded as G-1 in Appendix A.5 for a decision. Unverified: whether app code outside SQL handles it.

**Immutability.** An advancement never changes. Its only end is a revocation row (§4). The Final's **roster rows** (heat entries): in the HL1 stack **no supported route scratches or withdraws an advanced couple before the Final starts**, because `change_competition_entry_lifecycle` and the registration sync both refuse or skip any entry that has a heat entry in a locked or certified heat and every advanced couple has one (its permanently certified callback heat); NS1 marks a no-show only in an `active` round, and SC1 is not in the stack (§4.3). Once the Final is `active`, NS1 can exclude a couple from the Final calculation (X-5). A scratched couple is **not replaced** by the next-ranked couple (that would be a manager-style selection that D-CT-4 rejects, and D-CT-10 carries nothing forward).

## 2. Tie at the cut-off (SCN-11.4)

Approved (D-CT-4, 2026-10-24): advance **all** tied couples when the Final can safely accommodate them (count ≤ the Final's 10D capacity); if it would exceed that capacity, **no manager-picked advancement**, a separately approved, auditable tie-break process is required, and advancement stays **blocked** until that process is specified and completed. A callback runoff is a **candidate only**. Manager decision (c) is **rejected**.

So there are two sub-cases:

* **2a. Tie, count ≤ capacity: approved, automatic.** All tied couples advance (F-CT-02, `cap ≥ 5`). Final has more than `T` couples. No new rule.
* **2b. Tie, count > capacity: no approved rule.** Options:

| Option | What happens | Consequence for SCN-11.4b | Verdict |
|---|---|---|---|
| A. All tied advance anyway | Final heat holds `> capacity` couples | Contradicts D-CT-4 ("if that would exceed the approved floor capacity…"); the single-heat Final then breaks F-6 (`COMP_ORDINAL_MULTI_HEAT`) or needs a bigger floor than approved | **Not permitted** by D-CT-4 |
| B. None of the tied advance (only couples strictly above the cut) | Final has `< T` couples | Penalizes every tied couple equally but silently under-fills; it is an invented rule (no source, not in D-CT-4), and shrinks the Final below the organizer's `T` | Needs owner approval; not recommended |
| C. Runoff among tied couples | Judges rank/recall only the tied set in an extra step, then advance by the runoff result | Possible, but requires a new ballot format, a new tie-break engine step or version (`callback_tally@2`), panel/judge availability rules, a rule for a tie *inside* the runoff, and a place in the round sequence (frozen after lock, F-7). Needs its own spec, K1 verification and owner approval | **Candidate only**; a separate slice (CF2) after approval |
| D. Fail closed (current behavior, kept) | Calculation completes with no `advanced` flags; the round **cannot be approved**, nothing advances; the manager sees `tie_over_capacity` and the tied entries | SCN-11.4b becomes a **negative acceptance test**: the system refuses and no manager pick exists. SCN-11.4a (within capacity) is a positive test | **Recommended for CF1**, because it is exactly the approved state ("advancement remains blocked") |

**Decision (owner, 2026-10-30, OD-1): option D.** CF1 ships with it. Options A and B are not permitted; C (runoff, CF2) is a separate, unapproved candidate that needs its own spec, K1 verification and approval. Nothing below adds a manager override, an elimination rule or an automatic over-capacity advance. CF1 must make "blocked" actually blocking:

* **2.4 Approval gate.** Today a calculated callback result with every `advanced` null can still be approved (and then completed, since F2's completion check looks only for `advanced is true`). That would let a round "finish" with nobody advancing. CF1 adds a BEFORE UPDATE OF `status` trigger on `event_competition_result_versions` (calculated → approved): for a round with `round_type='preliminary'` and program `advancement_method='promote_callback'`, refuse with `COMP_ADVANCEMENT_BLOCKED` when any row has `advanced is null`. Additive trigger; no redefinition of F2 `approve_competition_round_result`.
* **Ways out of a blocked tie that are not manager picks:** a corrected ballot version through the correction path (CX1/K0 P1) if a judge made an error. Changing the Final capacity is **not** a way out (OD-1): the approved freeze B5 (§3.4.2, with only the F1 exemption of §3.4.3, which cannot dissolve a tie) closes that route.

Mapping: SCN-11.4 splits into **11.4a** (tie within capacity → all advance, Final holds `T+k` couples) and **11.4b** (tie over capacity → `tie_over_capacity`, approve refused, `apply` refused, no manager override control exists in UI or RPC).

### 3.2 The running-order problem and the approved controlled exception (OD-8, decided 2026-10-30)

Because of F-5(c)(d), the only ways to give the Final a heat in the live published version are (i) a new CF1 definer path that inserts into the live version under an explicit audited authorization, or (ii) relaxing the 10D freeze or the O1 run guard generally. (ii) is rejected: it weakens guards that protect every other round. Option (iii), pre-creating empty "shell" Final heats at planning time and reusing them, is not adopted: assigning entries to a heat of a published version is frozen (F-5c), so it needs the same OD-8 exception anyway; the planner would have to be redesigned; and (revision 11) the only planner that creates such heats is the block-mode planner, whose heats cannot be danced (§3.2.1). CF1 never fills or reuses an existing heat.

**Approved approach (i)**, scoped as the owner stated: only the CF1 advancement operation may do this, and every ordinary 10D and O1 restriction stays in force for every other writer. `apply_competition_round_advancement` inserts, in one transaction: one `event_competition_floor_heats` row appended at `max(heat_number)+1` of the live version, one `event_competition_heats` row (`round_id` = Final, `status 'scheduled'`, `schedule_version_id` = live version, `floor_heat_id` = the new floor heat, `heat_number` = `max(heat_number over the round, including cancelled)+1`), the `event_competition_heat_dances` copied from the callback round's heats (X-6: one dance per result, so a multi-dance callback round fails closed `COMP_ADVANCEMENT_MULTI_DANCE`, OD-9), and `event_competition_heat_entries` for each advanced entry. The 10D freeze guards are **three functions serving four triggers** (revision 11 naming correction): `_comp10d_guard_floor_heat` (trigger `comp10d_guard_floor_heat`), `_comp10d_guard_heat_child` (one function shared by triggers `comp10d_guard_heat_entry` and `comp10d_guard_heat_dance`) and `validate_competition_heat_schedule_placement` (function and trigger share the name; it raises `Heats may only be placed into an editable draft schedule.` for any heat INSERT into a non-draft version). The create path meets all three and they need a **narrow authorization** (this is the exception OD-8 approves), using the codebase's existing pattern: the guard allows the write only if an `event_competition_round_advancements` row with `transaction_id = txid_current()` for that heat's round exists (same idea as `event_competition_heat_lock_events` and NS1/`result_events` `transaction_id` checks). **Revision 9 correction:** a second BEFORE trigger cannot authorize anything, because it cannot cancel the exception another trigger raises; the authorization therefore has to be written **inside** the guard functions, so they are **redefined by pinned md5 text-replace** (HL1 pattern), each adding one `or exists (an advancement row with transaction_id = txid_current() ...)` clause. P-5 now verifies this and the reuse-path guard coverage instead of assuming a second trigger works. Then the 10D deferred integrity triggers run at commit.

Consequences that need acceptance:

* The published **snapshot** (`event_competition_schedule_publications.snapshot`, checksummed) is point-in-time and will not contain the Final heat. Public/entrant schedule readers that render from the snapshot will not show it; those that read live heats will. **OD-12:** add a supplemental publication record, or document that the Final is a day-of addition shown by the live floor/day-of views only. This interacts with OD-6: the roster must not appear to non-officials before publication.
* Appending at the end of the order is the only option without renumbering a published version. **OD-11:** the owner may want the Final placed after the callback heat; that needs renumbering and is not proposed.
* **Shell reuse removed (revision 11).** The older block-mode planner can create empty later-round heats (`heatPlanner.ts` l.192/195; `apply_competition_heat_plan`), but a block-mode heat cannot be danced on any supported path, so the callback round that must precede apply cannot complete there (evidence in §3.2.1). Revisions 9 and 10 specified filling such a shell; it is removed. Apply refuses any existing non-cancelled Final heat in the live version (§3.2.1).
* The heat is a normal `scheduled` heat after creation; `schedule_competition_round` (draft → scheduled) and `start_competition_round` remain the only writers of the Final round's status, unchanged. CF1 does not add an edge.

### 3.2.1 Heat scope, why shell reuse is removed, placement, locks (revision 11; each fact below was read in the HL1 tree `ca6c0b8d`)

**What was verified, and what was not.** Verified by reading the migrations of the chain (10A `20261107`, 10D `20261111`, June `20260620/21/22`, O1 `20270106`, E2 `20270102`, F2 `20270114`, NS1, SS1 `20270116`, HL1 `20270119`) and `heatPlanner.ts` / `floorPlanner.ts`: every claim in this subsection. This is **static reading, not runtime proof**; what must still be run is Appendix A.4. **Revision 11 simplification (a recommendation applied in this draft, not an approved decision):** revisions 9 and 10 specified a *shell reuse* path that filled an empty Final heat a planner had already created. Revision 11 found that the only planner that creates such heats is the block-mode planner and that a block-mode heat cannot be danced by any supported path (below), so the callback round that must precede apply cannot be completed in a block-mode schedule. The reuse path, its nine shell conditions, the dance-copy rule, and the reused-shell audit and snapshot text are therefore removed. If the reviewer or owner wants reuse back, the revision 10 text is in git history (`053bd535`). OD-8 (approved) covers only "insert its Final heat", which is the create path.

**Heat scope: one rule, live version only, as O1 does (revision 10, kept in revision 11).** Everything is computed under the apply locks (§6) from the **target round row**, never from a heat id supplied by the caller. The earlier text said it reused `_compo1_round_heat_state` and then refused heats in draft or superseded versions; those two statements disagreed, and the refusal would have let an abandoned draft copy or an old superseded copy block apply forever (publish supersedes a version without cancelling its heats; `create_competition_schedule_version` copies floor-mode heats as `scheduled` through `_comp10d_copy_floor_plan`). **The single rule now is O1's: only the live version counts.** `_compo1_round_heat_state(round)` returns `live_heats` (non-cancelled heats whose `schedule_version_id` is the live version) and `unplaced_heats` (non-cancelled heats with `schedule_version_id` null); a heat in any other version is counted by **neither**, and O1's `schedule_competition_round` / `start_competition_round` ignore it the same way (they refuse only `unplaced_heats > 0`, `COMPO1_HEATS_NOT_PUBLISHED`, and `live_heats = 0`). The heat status set is `draft, scheduled, staging, active, complete, cancelled` (`event_competition_heats_status_check`), so a `draft` heat is a non-cancelled heat.

**How each schedule-version status is treated** (`event_competition_schedule_versions_status_check`: `draft, review, published, live, superseded, archived`; `_compo1_live_version` picks the latest `published` or `live` by `published_at` then `created_at`):

**Why shell reuse is removed, and block-mode reachability (revision 11, item 6; static evidence).** The question: can a block-mode callback round (the only place a planner leaves an empty later-round heat) ever reach apply? Evidence, in order:

1. The block planner is reachable: `apply_competition_heat_plan` (June `20260621`) is called from `app/events/[id]/competition/generation/[runId]/actions.ts`, and `heatPlanner.ts` l.192/195 emits later-round heats with no entries. Such a heat has `floor_heat_id` NULL and a `schedule_block_id`.
2. The only writer of a running heat status is `advance_competition_floor_heat(p_floor_heat_id, …)` (O1 l.484): it reads `event_competition_floor_heats` by id and moves only the scoring heats whose `floor_heat_id` equals that id. A block-mode heat has no floor heat, so it cannot be moved to `staging`, `active` or `complete`.
3. No other writer can: `_compo1_guard_heat_status` (O1 l.219–263) refuses any direct write of a running status from `authenticated`, and refuses any move to or from a running status that lacks a same-transaction `round_transition_events` row; `_compo1_record` (the only writer of those rows) is called only by the O1 round and heat functions (the name occurs in no migration other than the O1 file).
4. The only other thing HL1 accepts as "danced" is an entry placement of `danced` or `disqualified` (`_hl1_heat_is_danced`, HL1 l.53–61; E2 `lock_competition_round_ballots` now requires every ballot heat to pass it, `COMP_HL1_HEAT_NOT_DANCED`). The check constraint allows those values (foundation l.222), but **no migration function and no app code writes them**: a search of all migrations finds the value only in the check constraint and in NS1/HL1 readers, and a search of the app finds only reads (`ballots/actions.ts` l.197). So a block-mode callback round can reach `ballots_locked` only if a manager hand-writes `event_competition_heat_entries.status = 'danced'` through the API (the 10D child guard allows status-only updates; the `competition_manage` policy allows the write).
5. The floor planner never creates a later-round heat: `floorPlanner.ts` l.136 plans only the **first** round of each division. A floor-mode Final heat can exist only through a crafted `apply_competition_floor_plan` call or a manual move.

**Conclusion.** On every supported path a block-mode callback round cannot be danced, locked or approved, so apply is unreachable there; it is reachable only with a forged "danced" status. The reuse path was written for a state the product cannot reach, and it carried most of the complexity (nine conditions, dance rules, placement pinning, a heat row lock, reused-shell audit and snapshot text). It is removed. Cost: a pre-existing live Final heat of any kind makes apply refuse (`COMP_ADVANCEMENT_FINAL_HEATS_PRESENT`) and the remedy is support, not a self-service repair; this state needs a crafted call or a forged status to exist. **Not confirmed:** whether any other app code path (a dynamic call this search missed) writes `danced`, and whether production data contains such rows; both are U18.

**Create path placement.** The create path exists only in a floor-mode live version (`exists floor_heats for the live version`): CF1 appends one floor heat at `max(heat_number)+1` and one scoring heat whose `floor_heat_id` is that floor heat. A block-mode live version is refused `COMP_ADVANCEMENT_FINAL_PLACEMENT_MODE`: creating a floor heat there would mix modes, and a block-mode Final needs a block, a floor and timing this design does not choose. **v1 limitation, reported as such.**

**`heat_dances`.** The create path copies the callback round's single dance onto the new heat (X-6, OD-9: a callback round whose heats carry more than one distinct dance fails closed `COMP_ADVANCEMENT_MULTI_DANCE`).

**10D integrity checks.** The 10D checks are deferred constraint triggers (`comp10d_heat_floor_integrity`, `…_entry_floor_integrity`, `…_dance_floor_integrity`: `deferrable initially deferred`), so their raw `COMP10D_*` errors would surface at COMMIT, outside the apply function. Because the create path puts the Final heat alone on a **new** numbered floor heat, every row `_comp10d_floor_heat_problems(new floor heat)` returns is attributable to CF1's own heat (revision 11: the revision 10 scoping against other divisions' problems applied only to shell reuse in a shared floor heat and is removed; a one-heat floor heat cannot have `incompatible_music`, so that code is dropped). Apply calls the function after the inserts: a `competitor_conflict` row (two advanced entries share a participant) raises `COMP_ADVANCEMENT_FINAL_COMPETITOR_CONFLICT`; any other row raises `COMP_ADVANCEMENT_FLOOR_HEAT_PROBLEM` (not expected). Revision 10's removal of the publish-only mappings (`COMP10D_UNPLACED_HEAT`, `COMP10D_EMPTY_FLOOR_HEAT`, `COMP10D_HEAT_NUMBERS` are raised only by publish) stands. The deferred triggers stay as the backstop; an unmapped raw `COMP10D_*` at commit is mapped by the app by prefix.

**Locks and retry (revision 11; the full lock-order matrix and the two-round and cross-operation analysis are Appendix A.3).**

* **Strategy, one for every CF1 path.** Coarse to fine; rounds in the canonical order `(division_id, sequence_number)`; **CF1 never waits for a heat row while it holds a round lock**; the correction trigger **never takes the event lock** (the F2 correction RPC holds rounds and takes no event lock, so an event lock inside it would invert event-then-round). Apply: (1) `_compo1_lock_event(event)` (waits), (2) source round `FOR UPDATE`, (3) target round `FOR UPDATE`, (4) approved result version `FOR UPDATE`, (5) live schedule version **`FOR KEY SHARE`**, (6) the advanced entry rows **`FOR SHARE`** in id order (§1.3, P2-3), then the revalidation of precondition 7, the integrity reads and the inserts. Apply takes **no heat row** (no shell). The revoke path, inside the F2 correction transaction, takes the Final's non-cancelled heats **`FOR UPDATE NOWAIT`** in id order. A **function-level** `lock_timeout` (a `SET lock_timeout = '5s'` clause on the CF1 function that waits, restored when the function returns; R5) bounds the waits in steps 1 to 6.
* **Why `FOR KEY SHARE` and not the advisory publication lock.** Publish and a direct `schedule_versions.status` write take the version row **before** the O1 event lock (the opposite of apply). An advisory lock would only order against `publish_competition_schedule_version`, not against a direct status write. A status update is `FOR NO KEY UPDATE`, which does not conflict with `FOR KEY SHARE`, so apply never waits on a version row and no wait edge exists to any version-row writer; `FOR KEY SHARE` still blocks a delete of the live version row. **Runtime unproven** (U1, U3).
* **`set_competition_heat_lock_state` does not lock only the heat row.** It takes the heat `FOR UPDATE`, inserts the audit row (FK key-share locks), updates the heat, and on reopen the HL1 trigger takes the heat's round `FOR SHARE`: heat then round. With apply taking no heat row there is **no apply-versus-reopen cycle** in the create path. The cycle that remains is reopen versus the **revoke path** (which holds rounds and wants Final heats): handled by `NOWAIT`. The alternative of redefining the shared lock RPC was rejected (shared by O1, F2 and HL1).
* **A retried publish never succeeds once the event has started running.** `compo1_guard_publish_during_run` refuses a `published`/`live` status write with `COMPO1_RUN_IN_PROGRESS` once **any heat of the event** is `staging/active/complete`; that is permanent, not transient. (Revision 11 correction of "always the case after the callback heats are danced": on every supported path the callback heats have run through `advance_competition_floor_heat`, so it holds at apply time; it does not hold for a round locked through forged `danced` entry statuses (§3.2.1, item 4), so invariant I1 does not rely on it; the publication guard of §5 (I6) does the work.)
* **Retryable versus permanent.** One transaction, so a `40P01` victim leaves nothing partially written. **Retryable:** `40P01` deadlock_detected, `40001` serialization_failure (not expected at READ COMMITTED), `55P03` lock_not_available (`NOWAIT` and `lock_timeout`), mapped to `COMP_ADVANCEMENT_CONCURRENT_CHANGE`. **Permanent:** every `COMP_*` and `COMPO1_*` error raised with `P0001`, `23514` or `42501`, including `COMPO1_RUN_IN_PROGRESS`.
* **Who retries today, and who will.** Nobody retries automatically. The only `40P01` mapping in the app is `heatLock.ts` l.79, a **manual** "try again" message for the HL1 lock action. CF1-B's advance action classifies the SQLSTATE, retries a retryable code **once** server-side (apply is idempotent on `p_request_id`, so a repeat after a commit returns `replayed: true`), then shows the same "try again" message; it never retries a permanent code. `lock_competition_round_ballots` (`ballots/actions.ts` l.165) has **no** `40P01` mapping today (the only mapping is `heatLock.ts` l.79, which matches the text or the code); CF1-B adds the same message mapping there. Whether the Supabase client surfaces a deadlock as `error.code === "40P01"` or only in the message is **unverified** (U28). The schedule actions that can now be aborted by a deadlock with apply (`create_competition_schedule_version`, `apply_competition_floor_plan`, `apply_competition_heat_plan`) get the same message mapping in CF1-B, with a **manual** retry (no automatic retry: they are manager edits to a draft). The correction path (F2/CX1 actions) stays manual.

**Duplicate Final heat (P2-6) and invariant I1.** The only uniqueness on heats is `event_competition_heats_round_version_number_uidx (round_id, coalesce(schedule_version_id, null-uuid), heat_number)`: two heats with different heat numbers are both legal rows, so the database alone does not stop a second Final heat. Prevention in revision 11 is layered: (1) **apply** requires zero non-cancelled live heats under the event lock and both round locks; (2) **once any advancement row exists for the round (any generation, active or revoked)**, the §5 guards make every direct writer refuse: insert of any heat for the round, any revive of a cancelled heat (including pre-existing cancelled empty heats), any move of a heat into or out of the round, and any cancel outside the CF1 and O1 transactions (the revive hole of revision 10, closed in §5 by widening the scope from "a CF1 Final heat" to **every heat of the round**); (3) a deferred backstop trigger asserts I1 at commit, **on heat rows only** (it does not serialize and cannot see a version status flip, U26); (4) a publication-time guard (§5, invariant I6) covers the status flips. The tests are §7.1 items 12, 13, 16 and 17.

**Audit row for the create (P2-7).** Apply writes, in the same transaction, the `advancement_applied` result event with refs `{advancement_id, generation, source_result_version_id, entry_count, heat_ids, request_id}` plus `path: 'create'`, the new `floor_heat_id` and its `heat_number`, so a reader can see where the Final was placed. Revoking a generation cancels its heat (§4); generation 2 takes the create path again.

**Snapshot divergence (OD-12 input).** The Final heat is created by CF1 after publication, so it is **absent from the published, checksummed snapshot** (`build_competition_schedule_snapshot` emits only heats that existed when the version was published). Public and entrant schedule pages that render from the snapshot will not show it; live readers will. OD-12 (supplemental publication record) covers that; the snapshot is never rewritten.

### 3.3 Scratches and no-shows (NS1/SC1)

* Callback scratches/no-shows (X-5) never advanced: they are excluded from the engine input, so `advanced` is not true for them. Not re-checked.
* Between approval and apply, an advanced entry may become `ineligible`/refunded or withdrawn: apply refuses with the list (precondition 7); no silent shrink, no backfill. Route: record the withdrawal through the audited official process (K0 §4.1), open a correction, and recalculate (worked example in §4.1).
* After apply, **before the Final starts** there is no supported scratch route for an advanced couple (`change_competition_entry_lifecycle` refuses it, the registration sync skips it, §4.3); once the Final round is `active`, NS1 excludes a no-show and, when it lands, SC1 may; the Final calculation excludes them (X-5). ### 3.4 Capacity

Re-read at apply (precondition 6). The Final must be one heat; if `count > capacity` apply refuses. Revalidated live as a second layer. The capacity value is part of the hashed calculation evidence (`_compf2_evidence` → `finalCapacity`), so a capacity change after calculation already makes the version stale (`COMP_RESULT_STALE` at approve) and forces recalculation; the §3.4.1 guard additionally restricts when it may change at all.

#### 3.4.1 Capacity guard (OD-3, decided 2026-10-30; exact rules)

Verified today: `set_competition_round_heat_capacity(p_round_id, p_capacity)` (10D, `20261111090000` l.775–795, used by `schedule/actions.ts`) lets any manager set `1..100` on **any round at any status**, with no reason, no audit row and no status guard. It writes `event_competition_rounds.configuration.max_entries_per_heat`. SS1 deliberately leaves `configuration` unfrozen. CF1-A adds:

* **Audit table** `event_competition_round_capacity_events` (insert-only): `round_id`, `old_capacity`, `new_capacity`, `reason` (1–500 chars, required), `actor`, `at`, `request_id`, `transaction_id`.
* **Authorization:** event manager (`can_manage_event_competition`) plus the verified-email credential (as NS1). Chair, scorer, judge, other studio, anon: refused.
* **Trigger** `cf1_guard_round_capacity`, BEFORE **INSERT OR UPDATE OF `configuration`** on rounds. On UPDATE it fires only when `max_entries_per_heat` actually changes; on INSERT it refuses any row whose `configuration` carries a `max_entries_per_heat` key unless the same transaction wrote a capacity-event row (otherwise the key must be absent and the default 8 applies). Both are authorized only by a capacity-event row for this round and `txid_current()` (the code base's usual transaction-bound authorization), so the only writer is the capacity RPC. **Why INSERT is covered:** the engine and apply read the Final's capacity as the round at `sequence_number + 1` of the same division (`_compf2_evidence` → `finalCapacity`), so a *replacement* round inserted into a vacant successor slot would carry a free capacity past an UPDATE-only trigger. The path is closed three ways: (1) the INSERT arm above; (2) `guard_competition_round_delete` (SS1) refuses deleting a round of a locked program, so an existing Final cannot be swapped for a new one, and `unique (division_id, sequence_number)` blocks inserting beside it; (3) if no successor exists at calculation time, `finalCapacity` is null and the engine fails closed when a tie needs it (V15) and apply refuses a missing target. An unlocked (draft) program has no pinned engine, so it cannot calculate (`COMP_ENGINE_NOT_AVAILABLE`) and the swap changes no result.
* **Legacy 2-argument RPC: fail closed from CF1-A (revised 2026-10-30; supersedes the earlier "shim with `legacy_caller_no_reason`", which does not satisfy the approved recorded-reason requirement).** `schedule/actions.ts` calls `set_competition_round_heat_capacity(p_round_id, p_capacity)` today. CF1-A **adds** the new `(uuid, integer, text, uuid)` RPC (reason and request id required) and **rewrites the 2-argument function (pinned) to always raise `COMP_CAPACITY_REASON_REQUIRED`** without changing any row or writing any capacity event. The `cf1_guard_round_capacity` trigger independently refuses any direct update, so no path changes capacity without a recorded reason. The cost is that the *old app* cannot edit capacity in the window between SQL apply and CF1-B deploy: **a block, not a pass**. Full options, rollout and rollback windows are in §12.1.

**What blocks** (first failure wins; each is a stable `COMP_CAPACITY_*` error):

| # | Condition on the round whose capacity changes | Result |
|---|---|---|
| B1 | Round status is not `draft` or `scheduled` (started, locked, calculated, approved, published, complete or cancelled) | blocked |
| B2 | Any non-cancelled heat of the round is `staging/active/complete`, or has `lock_state <> 'open'` | blocked |
| B3 | The round has any ballot | blocked |
| B4 | The round has an **active advancement** (the generated Final exists) | blocked; the only way back is the correction path of §4 |
| B5 (**approved 2026-10-30, with the F1 exemption only, §3.4.3**) | The round is the successor of a callback round that has any ballot, or any result version (including stale), or status `ballots_locked` or later | blocked. This stops capacity from being raised to dissolve a blocked tie (D-CT-4 / OD-1) |
| B6 (**approved as the capacity-edit arm of F2, §3.4.3**) | New capacity is below the callback round's `target_advancement_count` `T` | blocked (the `T` couples must fit; consistent with OD-2) |
| B7 | New capacity outside `1..100` (the existing 10D rule), or the reason is not substantive (§3.4.3: 20–500 characters, at least 4 words, at least 3 distinct, not a placeholder), or request id missing | blocked |

**What is allowed:** a capacity change by an authorized manager (manager plus verified email), with a substantive reason and an immutable audit row, while the round is `draft/scheduled`, has no ballots, has no active advancement (B1–B4), the callback round has no ballot, no result and is before `ballots_locked` (B5), and the after-state keeps `T ≤ capacity` (B6). **B5 is approved with one exemption, F1 (§3.4.3).** A non-callback round follows B1–B4 and B7 only. Because capacity is part of the hashed evidence, a change after calculation makes the version stale and forces recalculation. The unified audit read (`competition_audit_log`) gains the capacity events by a pinned redefinition; if that pin fails the events stay readable through the preview and the gap is reported.

#### 3.4.2 Effects of the capacity freeze (B5/B6) — DECIDED 2026-10-30: B5 approved with the F1 exemption, B6 with F2 (analysis kept as the record)

Facts that drive the analysis: capacity is read (i) by the engine only to decide whether a tie at the cut fits (`|A| ≤ cap`), and (ii) by apply to check the Final fits one heat (precondition 6). If the advanced count equals `T` and `T ≤ cap`, capacity never matters. **So a capacity change after callback ballots exist can only matter when there is a tie at the cut.** An *increase* that matters is exactly the one that dissolves a blocked tie, which OD-1 forbids. A *decrease* that matters turns an allowed all-tied-advance into a block.

Worked example (F-CT-02 shape): `T = 4`, entries 11–18, three judges, capacity 8; tallies 11 = 3, 12 = 3, 13 = 2, 14 = 2, 15 = 2: five couples at or above the cut.

| Case | B5 as written (symmetric freeze once the callback has a ballot or result) |
|---|---|
| **(a) Legitimate correction while capacity is frozen** | B5 freezes **capacity only**, never ballots or corrections. A CX1 judge-entry correction and the exclusion correction (§4.1) both proceed normally; recalculation reads the same capacity 8. Example: entry 13 excluded, judges re-file, result is still five at/above the cut and capacity 8 still holds them. No capacity edit is needed, so nothing is lost. |
| **(b) Legitimate capacity increase after ballots** (say 8 → 10 because the floor was enlarged) | **Blocked** (`COMP_CAPACITY_CALLBACK_FROZEN`). The organizer cannot raise it on this round. Safe path: **none that is also safe against OD-1**, except the F1 exemption (§3.4.3), which allows only a raise to exactly `T` when `T` exceeds capacity. If the count is `T` (no tie) the increase is unnecessary (capacity does not matter). If there is a tie, the increase would dissolve a tie that must stay blocked, so it must not be allowed. Practical guidance: set capacity **before the first callback ballot** (allowed, with reason and audit); the readiness check should warn when capacity is below `T` or below a plausible tie. A genuine floor change after ballots is handled by CF2 (runoff, unapproved) or by correcting ballots, not by editing capacity. |
| **(c) Capacity decrease after ballots** (say 8 → 4 because the floor shrank) | **Blocked** too. Consequence: the five tied couples (or `T` couples) advance into a Final built at the recorded capacity even if the physical floor is now smaller; the day-of desk must handle the physical constraint outside the system (scratch via SC1 after build is possible, a smaller Final is not created automatically). A decrease cannot dissolve a tie (it only tightens), so blocking it is *stricter than needed for OD-1*. |
| **(d) B6 (capacity below `T`)** | Blocks lowering capacity to a value under `T` at any time it is otherwise allowed (e.g. before ballots). It does **not** stop `T` itself from being raised above an existing capacity: raising `T` (editable until the round starts, E2) is a different write. Required companion (CF1-B / setup readiness): reject `T > capacity` at the callback-target edit, otherwise the same condition is only caught late by apply (OD-2). If B6 is not adopted, apply still refuses `T > capacity` (precondition 6), so the system stays fail-closed either way. |

**(e) The dead end the freeze can create (found in review, stated plainly).** Apply refuses when the advanced count exceeds the Final's **live** capacity **even with no tie** (precondition 6). `T` (`target_advancement_count`) is frozen once the callback round starts (E2 `compe2_guard_round_config`), and under B5 capacity is frozen from the first callback ballot. So if `T > capacity` is discovered **after the first ballot**, neither number can change: the callback can be balloted, calculated and approved, but apply refuses forever and the organizer is stranded with no in-system way out (the exits left are cancelling the callback round via O1 and rebuilding, or CF2). Today nothing stops `T > capacity` being configured: `create_simple_competition` leaves `T` null (S11), W4 lets managers set it until the round starts, and capacity defaults to 8.

Fix options (**F1 and F2 approved 2026-10-30**; F3 not adopted):

| Fix | Rule | Effect | Risk |
|---|---|---|---|
| **F1. Narrow exemption** | While no blocked-tie result exists, a manager may raise capacity **to exactly `T`** (and only when current capacity < `T`), with reason and audit | Cures the dead end. Cannot dissolve any tie: with capacity = `T`, any tie (count > `T`) is still over capacity | Leaves one reasoned, audited capacity edit after ballots; the test must prove the `= T` ceiling |
| **F2. Prevention at setup** | A DB-level guard (trigger on rounds) refuses any state where a callback round's successor capacity < `T`: on `T` edit, on capacity edit/insert and at publish (program lock) | The dead end cannot arise for new programs. Does not help a round already past its first ballot | Needs a successor-round lookup in the guard; adds a publish-time blocker (readiness) |
| **F3. Do nothing** | Rely on apply's refusal and the readiness warning | No new rule | The dead end is reachable; a mis-set round strands the organizer |

**Decision (2026-10-30):** F2 for prevention **and** F1 as the narrow cure are both approved, with B5. The binding rules, conditions and the F-CT-02 proof that F1 cannot dissolve a blocked tie are in §3.4.3.

Alternatives considered (**A adopted** with F1; B, C, D not adopted):

| Option | Rule | Effect | Risk |
|---|---|---|---|
| **A. B5 as written** | Once the callback has any ballot, result or `ballots_locked`+, capacity is frozen both ways | Simplest, no loophole, no reasoning about tallies | Rigid: (c) cannot be reflected; owner may find it too strict |
| **B. Narrow freeze** | Freeze only once a *blocked-tie* result exists (`tie_over_capacity`) | Maximum flexibility before then | **Loophole:** managers and scorers can read ballots before calculation, compute the tie themselves, and raise capacity first. The block never appears. Defeats OD-1 in practice |
| **C. Audited increase allowed when no tie is blocked** | Increases allowed with reason+audit until a blocked result exists; any capacity change after ballots is flagged at approval and needs the second approver's acknowledgment | Allows (b) | Same pre-calculation loophole as B, mitigated only by audit and the second approver; relies on people, not a guard |
| **D. A for increases, audited decreases** | Increases frozen after the callback has a ballot; decreases allowed with reason+audit while no advancement is active, making any existing version stale | Fixes (c) without opening the OD-1 loophole (a decrease can never dissolve a tie); decrease can newly block a tie, which fails closed | A manager could force a block by decreasing (denial, not a selection); visible in the audit and the approver sees the flag |

**Decision (2026-10-30):** **A** (B5 as written, symmetric freeze) is approved **with the F1 exemption**; B and C are rejected (pre-calculation loophole); D (audited decreases) is not adopted, so a capacity decrease after callback ballots stays blocked (case (c)). Until CF1-A implements B1–B7, F1 and F2, the analysis above is the acceptance record.

#### 3.4.3 Binding capacity rules decided 2026-10-30: B5 with the F1 exemption, and the F2 setup guard

The owner approved **both safeguards** for the dead end of §3.4.2(e). The rules below are binding for CF1-A. B1–B7 stay in force **except for the single F1 exemption**; B5 (the freeze) is approved **with** F1. The general published-order restrictions of 10D/O1 are unchanged. The design as a whole is **not** approved.

**F2. Setup guard (prevention).** A DB-level trigger `cf1_guard_callback_target_capacity` makes it impossible to *write* a callback configuration whose target `T` exceeds the Final's single-heat capacity. A "callback configuration" is a `preliminary` round of a program with `advancement_method = 'promote_callback'`, whose successor round (`sequence_number + 1`, same division) is the Final. The after-state must satisfy `T ≤ capacity` (capacity = `max_entries_per_heat`, default 8) whenever `T` is not null; otherwise `COMP_CALLBACK_TARGET_EXCEEDS_CAPACITY`. It fires on:

| Arm | Write | Note |
|---|---|---|
| T edit | UPDATE OF `target_advancement_count` on the callback round | The T edit today is a direct table update (`competition/actions.ts` l.364), so a trigger covers it for every client |
| Capacity edit | UPDATE OF `configuration` on the successor, where `max_entries_per_heat` changes (this is B6) | Lowering below `T` is refused |
| Successor insert | INSERT of the successor round | Also covered by the INSERT arm of `cf1_guard_round_capacity` (§3.4.1) |
| Publish / program lock | UPDATE OF `profile_locked_at` on the program (additive trigger; 10B's protect function is not redefined) | A program with a callback round whose `T` is set and greater than the successor's capacity cannot be published. `T` null at publish is allowed (D-CT-5: set before ballots) |

It does not retro-fail existing rows; it fires only on a write to one of the fields above, and refuses any write whose after-state violates `T ≤ capacity`. To fix an existing mismatch before the callback round starts, lower `T` or raise capacity to at least `T` (both ordinary writes).

**F1. Narrow exemption (cure for an EXISTING mismatch).** An authorized, audited capacity increase to **exactly `T`**, permitted only when **all** hold (each a stable `COMP_CAPACITY_F1_*` refusal):

| # | Binding condition |
|---|---|
| 1 | **Authorization:** actor is an event manager (`can_manage_event_competition`) **and** has a verified email credential. Chair, scorer, judge, other studio, anon: refused |
| 2 | **Scope:** the round is the successor Final of a callback round; current capacity `< T`; new capacity `= T` **exactly** (not more, not less); `T ≤ 100`; and the change is within the event's applicable rules (`1..100`, B7) |
| 3 | **No prohibited Final activity:** the Final round is `draft` or `scheduled` (B1); no Final heat is `staging/active/complete`, none has `lock_state <> 'open'` (B2); the Final has **no ballot** (B3); there is **no active advancement** (B4). This is what "no capacity edit after Final ballots or other prohibited Final activity" means in the database |
| 4 | **Callback state:** the callback round is before `approved` (`draft/scheduled/active/ballots_locked/calculated`) and **no blocked-tie result version exists** (no version of the round whose rows have `advanced is null`). After approval, use the correction path |
| 5 | **Substantive reason** (below) and a request id |
| 6 | **Immutable audit:** one insert-only `event_competition_round_capacity_events` row carrying `exemption = 'f1_raise_to_t'`, old capacity, new capacity, `T`, the callback round status and the ids of the callback result versions at that moment, actor, reason, request id and transaction id; shown in the unified audit read |
| 7 | **One use:** after the raise, capacity = `T` so condition 2 (`capacity < T`) is false; F1 cannot be applied again to step capacity higher |

An existing calculated version becomes stale (capacity is in the hashed evidence) and must be recalculated; nothing else changes.

**Minimum substance of a reason (all capacity changes, recommended; binding for F1).** After trimming: 20–500 characters, at least 4 words of which at least 3 are distinct (case-insensitive), not a single repeated character or word, and not in a short placeholder list (`n/a`, `none`, `test`, `testing`, `fix`, `fixed`, `asdf`, `tbd`, `ok`). Computed in SQL by `_cf1_reason_is_substantive(text)`. It cannot judge truthfulness; the audit row is the control. The reason need not restate old capacity, `T` or round status (stored automatically). B7 is updated to this rule.

**F1 can never override D-CT-4 (worked with F-CT-02).** `T = 4`, entries 11–18, tallies 11 = 3, 12 = 3, 13 = 2, 14 = 2, 15 = 2: five couples at or above the cut.
* Capacity already 4 (= `T`): the tie of five is over capacity, advancement is blocked. F1 does not apply (`capacity < T` is false) and nothing else can raise capacity (B5). **Still blocked.**
* Capacity 3 (< `T`, an existing mismatch): F1 may raise it to exactly 4. The tie of five is still above 4. **Still blocked.**
* F1 cannot raise to 5 or 8 (condition 2: exactly `T`), and cannot be repeated (condition 7).
* A callback with a blocked-tie version already calculated: F1 is refused (condition 4).
Capacity can therefore never be moved to a value that fits a tie of more than `T` couples through F1.

**What this does to the old app, existing programs and rollback** (see §12.2): F2 refuses a T edit or publish that would create `T > capacity` with a DB error even from the old app; the old app still cannot edit capacity at all in the window (2-argument RPC refusal), so F1 exists only through the new RPC in CF1-B; existing programs with `T > capacity` are not retro-failed but are caught at the next write, at publish, by the readiness warning and at apply; rollback stays roll-forward-only after the first capacity-event row (F1 produces one).

### 4.1 Withdrawal, correction and deterministic recalculation (worked example)

If an advanced couple becomes unavailable between approval and apply, **apply refuses** (precondition 7). The only route is a correction and recalculation:

1. Record the withdrawal through the audited official process (K0 §4.1, R2 refund-exception resolution), so the entry is excluded under X-5. **This step cannot be performed today (see P-3 below).**
2. Open a correction on the callback round (manager, reason). No advancement exists yet, so nothing is revoked. **Opening it is possible, but the exclusion it exists to handle cannot yet be recorded, so the route is dead until P-3 closes.**
3. Each judge who had selected the excluded couple no longer has exactly `T` eligible picks (V11 `callback_count`), so those judges submit a **corrected ballot version** (CX1) with a reason. The judges choose; no manager does. **Integrity risk, see below (OD-13).**
4. Recalculate, second-person approve, then apply. The engine re-advances deterministically.

**Replacement rule used in the example (Option R).** Each judge keeps every non-excluded pick and replaces the excluded pick with **a couple of that judge's own choosing**: any eligible entry that is not already on their ballot and not excluded. Nothing in the system computes or fixes that choice; the picks below (J1 → 15, J2 → 16) are *illustrative judge choices*. The engine only tallies what the judges file.

Example (F-CT-01 data, `T = 4`, entries 11–18, three judges): J1 {11, 12, 13, 14}, J2 {11, 12, 13, 15}, J3 {11, 12, 14, 16}. The approved result advanced 11, 12, 13, 14. Apply is attempted and entry 13 has withdrawn: apply refuses, listing 13. After steps 1–2 entry 13 is excluded. J1 and J2 each hold 3 eligible picks, so both file corrected ballots, say J1 {11, 12, 14, 15} and J2 {11, 12, 15, 16}; J3 never marked 13 and is unchanged. Tallies: 11 = 3, 12 = 3, 14 = 2 (J1, J3), 15 = 2 (J1, J2), 16 = 2 (J2, J3). The 4th-highest tally is 2, so five couples (11, 12, 14, 15, 16) sit at or above it: a tie at the cut. With capacity 8 all five advance (D-CT-4); with capacity 4 advancement is blocked (OD-1 Option D). Entries 15 and 16 advance because the judges' corrected ballots say so, **not** because a manager chose "the next couple". If a judge does not re-ballot, the round stays blocked (fail closed).

**Correction-ballot integrity (OD-13, APPROVED 2026-10-30: Option R; DanceFlow integrity choice, not a UCWDC rule).** The corrected ballot is filed *after the approved result is known*, so a judge could change more than the withdrawn pick to steer the outcome (for example to create or break a tie at the cut). The engine is deterministic on whatever ballots exist and cannot detect that. Decision:

* **Option R (restricted), for a correction caused by a competitor exclusion:** the judge may replace **only the excluded selection(s)**. Every other pick must be identical to the judge's prior current ballot. No re-pick.
* **Option F (full re-pick) stays only for a separately authorized genuine judge-entry correction.** Every correction ballot (R or F) stores the **original ballot, the replacement ballot, the reason, the actor, the timestamp and the diff**.

**How the system distinguishes the two causes, and why a judge cannot choose it.**

* A judge **cannot open a correction** at all (F2 `open_competition_round_correction` is manager-only). The cause is not a form field a judge or the caller supplies.
* The cause is **derived by the system at the moment the correction opens**, in the same transaction, by a trigger on the round status edge (`approved|published|calculated → ballots_locked` with `correction_open`): it compares the round's *current* exclusion set with the **baseline version's** `excludedEntries`. **Baseline (defined, because F2 invalidates versions before the status update):** the round's highest-numbered result version at that moment, whatever its status (`calculated`, `approved` or already marked `stale` by this very correction), read from its stored evidence input. This works for a correction opened from `calculated` (no approved version exists) and from `approved`/`published`. The exclusion set is **exactly what F2 evidence computes**: entries scratched in every non-cancelled heat entry of the round, plus NS1 no-shows (`_compf2_no_show_entries`). It is **not** `_compe2_round_entries`, which drops only scratched entries (a no-show stays pickable there and is excluded by the engine, X-5). If the current set contains an entry **not** in the approved set, the cause is `entry_exclusion` and the new exclusions are recorded; otherwise it is `judge_entry_error`. There is no parameter to override it. If both a new exclusion and a judge-entry error exist, the cause is `entry_exclusion` (restricted); the entry error needs a second, separate correction after the first completes.
* **Who authorizes (co-sign is a separate row, never an edit):** `entry_exclusion`: the manager who opens the correction, whose reason must cite the recorded exclusion. `judge_entry_error`: the manager opens it with a reason, and a **co-sign** is required before any replacement ballot is accepted, written by `cosign_competition_correction(cause_id, request_id)` into `event_competition_correction_cosigns` (insert-only: `cause_id`, `cosigned_by`, `role` (`chair` or `manager`), `at`, `request_id`, `transaction_id`). The co-signer must be **a different person from the opener**, and **must not be anyone who files a replacement ballot under this correction** (the co-signer's user id may not equal `submitted_by` or the filing official's `user_id`; checked again at each replacement ballot insert), which rules out a chair who both co-signs and files. A judge never authorizes. Which roles may co-sign is OD-13b.
* **Recorded in** the new insert-only table `event_competition_correction_causes`, complete at open (no later UPDATE): `round_id`, `cause`, `excluded_entry_ids`, `baseline_version_id`, `opened_by`, `reason`, `at`, `request_id`, `transaction_id`. There is no nullable `authorized_by`; authorization is the separate co-sign row above. The correction cannot take effect without its cause row (the status-edge trigger raises `COMP_CORRECTION_CAUSE_REQUIRED`, so the existing F2 RPC needs no signature change). **The cause is fixed at open and never re-derived.** To keep that sound, recording a new exclusion that touches this round while its correction is open is refused (`COMP_CORRECTION_EXCLUSION_DURING_CORRECTION`); the manager finishes the open correction through recalculation to `calculated`, then opens a new correction, which derives `entry_exclusion`. Today's exclusion writers are already structurally blocked in that window (scratch is refused on certified heats; NS1 marks need an `active` round); the future P-3 writer must obey the same rule.

**Write-path check (CF1-A scope).** `event_competition_ballot_corrections` (insert-only): `ballot_id`, `supersedes_id`, `cause_id`, `reason`, `actor`, `at`, `diff` (`{removed: [...], added: [...], unchanged: n}`), written in the same transaction as the replacement ballot.

* **Primary:** a pinned text-replace of `_compe2_insert_ballot(uuid,uuid,uuid,uuid,text,uuid,jsonb,text,uuid)` (pin from the replayed chain, P-2) inserting a call to a new internal `_cf1_check_correction_ballot(round, official, supersedes_id, marks, ...)`. **Placement (verified in the E2 body):** callback marks are validated by `_compe2_validate_callback` *before* `v_prior` is selected, so the call goes **after the `v_prior` block and immediately before the ballot INSERT**, not right after validation. The function **reads the prior ballot and its marks itself** (by `supersedes_id`, round and official), never relying on the caller's variable. For a `callback_yes@1` ballot in a round with `correction_open` and a cause row:
  * `entry_exclusion`: let `old` be the superseded current ballot's picks and `X` the recorded excluded entries. Require `old ∩ X` non-empty (a judge whose ballot has no excluded pick may **not** file a new version: `COMP_CORRECTION_BALLOT_NOT_PERMITTED`); new picks must keep `old \ X` exactly, remove all of `old ∩ X`, and add exactly `|old ∩ X|` new eligible entries that were not already picked and are not in `X`. Anything else: `COMP_CORRECTION_BALLOT_RESTRICTED` listing the offending entries.
  * `judge_entry_error`: allow any valid ballot, but refuse unless a co-sign row exists (by a person who is neither the opener nor this ballot's filer), then write the diff row.
* **Backstop:** a deferred constraint trigger on `event_competition_ballot_corrections`/ballots asserts the same rule at commit, so another writer (service role, a future RPC) cannot bypass the RPC check.
* Scope: `callback_yes@1` only. A correction of other formats (including the Final's `ordinal_rank@1`) is unchanged by CF1; whether a Final exclusion needs an equivalent restriction is out of scope and raised as OD-13c.

**New SQL tests** (suite `test_T_competition_cf1_callback_final_advancement.sql`): cause derivation (new exclusion → `entry_exclusion`; none → `judge_entry_error`; both → `entry_exclusion`); a judge cannot open a correction or supply a cause; R accepts exactly the replacement and refuses an extra change, a missing replacement, a replacement already picked, a replacement equal to an excluded entry, and a judge with no excluded pick; F refuses without co-sign and stores the diff; `original`, `replacement`, `reason`, `actor`, `timestamp` and `diff` are all present and immutable; the deferred backstop rejects a direct insert; non-callback ballots untouched. Concurrency: two judges filing at once, and a ballot filing racing the correction closing.

**Scope of Option R (derivable exclusions only).** R applies only to exclusions the system can derive: scratched entries and NS1 no-shows as F2 computes them. An entry that has become **ineligible** (or refunded under an unresolved exception) is **not derivable** today: no code path puts it into `excludedEntries`. Such a case is not classified as `entry_exclusion`, and must not fall through to Option F as a shortcut: apply stays refused and the round stays blocked until P-3 provides a derivable, audited exclusion record. Replacement picks under R are checked against the F2 exclusion set (a no-show cannot be picked as a replacement).

**Option F risk, stated plainly (§4).** Option F lets a judge change **any** pick after the result and the tie are known, so a judge-entry correction **can dissolve a blocked tie** (or create one). The co-sign (and the stored diff shown to the second-person approver) is the **only control**; the engine cannot detect it. The owner is accepting that residual risk by keeping F for genuine entry errors.

**Residual items:** OD-13b (which roles may co-sign an F correction; the constraints above are fixed) and OD-13c (Final-round exclusion equivalent). Both are open and listed in §9.

**P-3: the withdrawn-couple route is DEAD until it closes (verified, stated plainly).** No existing writer in the HL1 stack can exclude a couple on a **locked or certified** callback heat: (i) **`change_competition_entry_lifecycle`** (June `20260620`, SECURITY INVOKER) **is** an existing scratch writer, but it refuses when any heat of the entry is locked or certified, and a direct `heat_entries` write is refused on such a heat by `protect_locked_competition_heat_entry`; E2 `lock_competition_round_ballots` refuses while any heat is not locked (`heats_not_locked`), so every callback heat is locked by `ballots_locked` and certified at approval (re-derived in revision 10, Appendix A.2b); (ii) Phase 10A removed the heat-override bypass (`app.competition_heat_override`; its postflight asserts no function honours it, `20261107090000` l.49 and l.1138); (iii) HL1 refuses reopening a heat once the round is `ballots_locked` or later; (iv) NS1 marks need a round that is `active`. **The SC1 official-scratch RPC is not in this stack:** a search of HL1's tree finds no **SC1** official-scratch function (the revision 9 wording "no function with `scratch` in its name" was too narrow: it missed `change_competition_entry_lifecycle`, whose name does not contain it), and the SC1 workflow exists only on `origin/competition-sc1-scratch-workflow` (migration `20270108090000_competition_sc1_scratch.sql`) and `origin/competition-int-r2-sc1`, neither of which is an ancestor of HL1 (`git merge-base --is-ancestor`, verified). Until SC1 (or an equivalent audited writer that works on certified heats, with the F2 evidence reading it) lands in the stack, a withdrawal after approval **blocks the round**: apply refuses (precondition 7), a correction cannot make the couple excluded, and nothing in CF1 invents a bypass. This is a known, fail-closed dead end, not a workable route.

Why a trigger and not a redefinition of `open_competition_round_correction`: the F2 RPC is pinned and already patched by later slices; a status-edge trigger gives one point of enforcement for *every* path to those edges, and the revoke runs inside the same statement transaction, so a refused revoke rolls back the correction atomically.

Cosmetic side effects of cancelling the Final heat in a published running order: a floor heat with no non-cancelled scoring heat (a "tombstone" of the old generation). `COMP10D_EMPTY_FLOOR_HEAT` is checked only at publish; CF1 keeps the tombstone (cannot delete from a published version) and the day-of readers must ignore floor heats with no live scoring heat. To be verified in implementation preflight.

### 4.3 Removing an advanced couple from a not-yet-started Final (revision 13; static reading, not runtime proof)

**Correction of revision 12.** Revision 12 said that after apply the registration sync and `change_competition_entry_lifecycle` can withdraw or scratch an advanced couple on the open Final heat. **That is wrong.** A reviewer reported it; I re-read both bodies and the reviewer is right. Both test whether the entry has **any** heat entry in a heat whose `lock_state` is `locked` or `certified` (sync: the `NOT EXISTS` clause of the 10A body, l.~565–575; lifecycle: June `20260620` l.322ff). Every advanced couple has such a heat entry: its callback heat, locked by E2 (`ballots_locked` needs every heat locked), certified at approval and **permanently** (HL1 refuses reopening from `ballots_locked` or later; certified heats are immutable). So both are blocked **before and after** apply. Real behaviour, each item read in the tree:

* **(i) Registration cancel or refund.** The AFTER UPDATE trigger on `event_registrations` calls the sync; its UPDATE excludes the advanced entry, so the registrant stays **`confirmed`**, the Final roster keeps the couple, no entry-change history row is written (the audit trigger fires only on entry updates), and the registration (cancelled or refunded) and the entry disagree. `finalize_competition_registration` only moves `pending` entries to `confirmed`, and `release_competition_registration` only cancels `pending`/`waitlisted` registrations and scratches `entry_dances`; neither touches a confirmed advanced entry (Appendix A.2c).
* **(ii) The existing scratch route.** `change_competition_entry_lifecycle` refuses an advanced entry permanently, and **no app code calls it** (a search of `src/` for the RPC name finds nothing; it is reachable only by a direct RPC call). NS1 marks a no-show only in an `active` round; SC1 is not in the stack. So there is **no supported route** that scratches or withdraws an advanced couple from a Final that has not started.
* **(iii) The eligibility screen.** `updateCompetitionEntryEligibilityAction` (`registrations/actions.ts` l.40) writes `eligibility_status` with a plain table update through the manager's own client under the `competition_manage` policy: no RPC, no guard (the audit trigger records an `eligibility_change` row but does not refuse). A manager can set an advanced couple `ineligible` after apply. The roster check at the Final's start (§5) then refuses the start (`COMP_ADVANCEMENT_ROSTER_STALE`), and the only ways out are to revert the change (the same unguarded screen) or a direct `heat_entries` status write (a manager can do it through the policy; it is unaudited and unsupported). Also `ineligible` does not stop E2: `_compe2_round_entries` drops only `scratched`, so the couple would be ranked.
* **Consequence for the revision 12 remedy.** "The manager scratches first" has **no supported route**. It is replaced below.

**What a supported workflow must preserve:** advancement and audit history (no edit of advancement rows, an insert-only record); Final roster integrity (roster rows only shrink, nobody is substituted: D-CT-4, D-CT-10); registration and refund consistency (the workflow never edits the registration or the entry's own status); the competition lifecycle (Final round `draft`/`scheduled`, Final heat open and not started, no Final ballot, same lock order as apply); protection against unauthorized direct writes (a transaction-bound authorizer, not an app-level check). It must **not invent a lifecycle transition**: the only roster change it uses is the existing heat-entry status `scratched`.

### 4.4 Withdrawals across advancement generations (revision 14; static reading, not runtime proof)

**The reviewer's counter-example holds in the code as designed.** Alternative A of §4.3 scratches only the **Final heat entry** of the withdrawn couple X and leaves the entry and the registration untouched. Then: (1) an authorized callback correction is allowed (Final round `draft`/`scheduled`, no start, no ballot) and its status-edge trigger revokes generation 1 (the Final heat is cancelled, X's scratched heat entry stays on the cancelled heat); (2) F2 recalculates the callback from the callback heats, where X's heat entry is not scratched and is not a no-show, so X is advanced again (F2 evidence excludes only scratched entries and NS1 no-shows); (3) precondition 7 reads only the entry's `status` and `eligibility_status` (and, since revision 13, division membership), not the old withdrawal; if X is `confirmed` and eligible, **generation 2 re-advances X and the withdrawal silently lapses**; (4) if X is `ineligible`, apply refuses `COMP_ADVANCEMENT_ENTRY_UNAVAILABLE` for X, and no action can exclude X from the callback result because an ineligible or withdrawn couple is not a derivable exclusion (P-3, the OD-13 scope note), and there is no Final heat left to withdraw X from: **a dead end**. ### 4.5 Unconditional withdrawal protection, recovery, completeness and ordering (revision 15; only relevant if §4.4 option 1 is adopted; static reading, not runtime proof)

**The reviewer's F1 claim holds.** After the Final starts, a manager's direct policy write `UPDATE event_competition_heat_entries SET status = 'checked_in'` on a withdrawn couple's scratched heat entry is a status-only update: `_comp10d_guard_heat_child` returns early for a status-only change (10D l.~351), `protect_locked_competition_heat_children` refuses only locked or certified heats (an open Final heat passes), and 10D.1 checks only INSERT and `entry_id`/`heat_id` changes (A.2d). E2's `_compe2_round_entries` (as NS1 redefined it) drops only `scratched` and no-show entries, so the couple is ranked again. A guard limited to "before the Final starts" therefore does not protect a withdrawal.

**Unconditional withdrawal guard.** Trigger `cf1_guard_withdrawn_heat_entry` (function of the same name, SECURITY DEFINER, `search_path = public, pg_temp`, because the withdrawal table has no grants), **`BEFORE INSERT OR UPDATE OF status, entry_id, heat_id OR DELETE ON event_competition_heat_entries FOR EACH ROW`**. It acts only for a heat of a callback Final round and a pair `(that round, entry)` whose **effective withdrawal state is `withdraw`** (the row with the highest `seq`, below). It refuses, **at any time, before and after the Final starts**:

* **UPDATE OF `status`** that moves a heat entry **out of `scratched`** (`old.status = 'scratched'` and `new.status <> 'scratched'`);
* **INSERT** of a heat entry for a withdrawn pair into **any heat of that round**, which covers a direct insert of a replacement row (and A-apply itself: apply skips carried withdrawals and the guard is the defence in depth against apply inserting one);
* **UPDATE OF `entry_id` or `heat_id`** that moves a withdrawn pair's row or points another row at a withdrawn entry;
* **DELETE** of the scratched row (a delete would let a replacement be inserted), except when the whole event, version or round is being deleted (the event-gone exception pattern of the 10D guards).

**Authorization evidence (the only exception).** A row in `event_competition_final_withdrawals` with `kind = 'reinstate'`, the same `(target_round_id, entry_id)`, and `transaction_id = txid_current()`, written by the audited reinstatement function in the same transaction with the actor, the reason, the co-signer, the request id and the **prior heat-entry status** it restores. **Lifecycle checks inside the reinstatement function (not in the guard, which is unconditional):** Final round `draft`/`scheduled`, no Final ballot, no Final heat started, the entry `confirmed` and eligible and in the round's division under `FOR SHARE`, a co-signer who is not the requester. **After the Final has started no reinstatement exists:** a withdrawn couple stays out; that is intended and is part of OD-10 part 2.

**Coverage and residual.** Triggers fire for every role including `service_role`, whether the writer is a SECURITY DEFINER or INVOKER function or a direct policy write. **Not covered (residual):** a table owner or superuser (who can disable triggers or run migrations); `session_replication_role = replica` is covered by creating the trigger `ENABLE ALWAYS` (below); a `TRUNCATE` (a statement the row trigger does not see and RLS does not govern; the privilege is presumed from the Supabase default and unverified, U7, U46; pre-existing for every table and out of CF1's scope); an owner-run migration.

**How E2 cannot silently rank an improperly reinstated couple.** (1) If any ballot already exists, an un-scratch changes `_compe2_heat_entries`, so the submitted ballots no longer match it and are **stale**: `lock_competition_round_ballots` refuses `COMP_BALLOTS_STALE` (NS1 header l.36–40, E2 `_compe2_round_blockers`), fail closed but only once ballots exist. (2) Before any ballot, the guard above prevents it. (3) If the guard is bypassed (residual above), the proposed E2-side cross-check closes it: the **same pinned insertion in `lock_competition_round_ballots`** as the stale-roster check of §5 also refuses a callback Final whose non-scratched roster contains a pair with an effective withdrawal (`COMP_ADVANCEMENT_ROSTER_STALE`, organizer text "A withdrawn couple is on the Final roster. Contact support."). Calculate and approve remain unguarded (they would need F2 pins). This check is an **owner decision (whether to touch E2)** and, if adopted, an **implementation requirement**; until then (3) is a stated residual.

**Ordering key and stored fields.** Withdrawal and reinstatement rows carry a **monotonic `seq bigint`, per `target_round_id`**, assigned as `coalesce(max(seq), 0) + 1` of that round **read under the Final round `FOR UPDATE`** (withdraw, reinstate and apply all hold that lock, so two writers cannot read the same maximum), with `unique (target_round_id, seq)` as the backstop. It is per **round**, not per advancement, because a withdrawal is generation-independent (§4.4). `now()`, `created_at` and `id` are **not** used (clock ties and non-monotonic UUIDs). The **effective state** of a pair is the row with the highest `seq` for `(target_round_id, entry_id)`. A withdraw row also stores `heat_entry_id` (nullable: absent when no heat entry existed) and **`prior_heat_entry_status`** (`scheduled` or `checked_in`, null when none), which an authorized reinstatement restores.

**Reinstating a carried withdrawal after generation-2 apply (revision 16, D2).** In generation 2 a carried couple has **no heat entry** (apply created none), so reinstatement cannot un-scratch anything; it would have to **insert** a heat entry into a published Final heat. That insert is refused today by 10D `_comp10d_guard_heat_child` (the version is not editable) and by `cf1_guard_final_heat_entry` (only A-apply may insert). Two options; the owner's choice is **OD-18** (§9.2) and neither is chosen here:

* **(i) Authorized insert under the reinstatement row (apply-style exception).** The reinstatement function inserts the heat entry; the pinned `_comp10d_guard_heat_child` and `cf1_guard_final_heat_entry` each gain one `or exists (reinstatement row for that round and entry with transaction_id = txid_current())` clause (the function is already pinned for apply, so no new pin), and the entry is appended at `floor_order = max + 1` because rewriting the other rows' `floor_order` is a non-status change the guard refuses (the OD-7 order is therefore broken by one appended couple, recorded in the row). **This extends OD-8's approved scope** ("insert its Final heat") to a heat-entry insert for a reinstatement: it needs the owner to confirm the extension.
* **(ii) Fail-closed refusal (the default until the owner chooses (i), OD-18).** Reinstatement of a couple that has no heat entry is **refused while an active Final heat exists** (`COMP_ADVANCEMENT_REINSTATE_NO_HEAT_ENTRY`). The couple returns only through this **exact sequence** (the earlier text "reinstatement row first, then a correction" was contradictory and is withdrawn): **(1)** an authorized callback correction revokes generation 2 (there is then no active advancement and no active Final heat); **(2)** the audited, co-signed reinstatement is recorded **after the revocation and before the next apply** (allowed: §4.4 already lets a withdrawal-state change be recorded between a revoke and the next apply, and the reinstatement row alone changes the pair's effective state, so no heat entry has to be inserted; **reinstatement after a revoke writes only the reinstatement row and touches nothing in the cancelled earlier-generation heat**: the only scratched heat entry may sit there, and E2's `_compe2_round_heats` excludes cancelled heats); **(3)** apply creates generation 3 with the corrected roster, which includes the couple **if the corrected callback still advances them** (reinstatement does not guarantee advancement; precondition 7 validates them again). Reinstatement stays refused while an **active** Final heat exists without the couple's heat entry.

The over-promise in OD-10 part 2 option B ("only an audited reinstatement restores them") is corrected there: before the start, reinstatement restores a couple **at once only if it still has a scratched heat entry**; a carried couple needs (i) or the exact sequence of (ii) (revoke, reinstate, apply).

**A withdrawal recorded against an already-scratched heat entry (revision 16, D3).** The prior-status domain of a withdrawal row is `scheduled`, `checked_in`, `scratched` or null (no heat entry); `danced` and `disqualified` cannot occur before the start and a withdrawal is refused after it. **The row is allowed for an already-scratched heat entry**: the couple is already out of the Final, the row records the decision so that it persists across generations and the §4.5 guard protects it from then on, and `prior_heat_entry_status = 'scratched'`. **Reinstatement is refused for such a row** (`COMP_ADVANCEMENT_REINSTATE_PRIOR_SCRATCH`): the earlier scratch was not the withdrawal's doing, so restoring the couple would silently undo it; the couple stays out. **This is also the exit for `COMP_ADVANCEMENT_ROSTER_INCOMPLETE`** (§5): a roster couple scratched with no withdrawal row (a direct scratch) fails the completeness check; the manager records a withdrawal for that pair (allowed against a scratched heat entry), which makes the scratch a recorded, effective withdrawal, and the start passes.

**Foreign keys: RESTRICT versus NO ACTION, and event deletion (revision 16, D4; replaces the revision 15 wording).** PostgreSQL's `RESTRICT` is checked **immediately** and **cannot be deferred**; `NO ACTION` is checked at the **end of the statement**. Event deletion cascades through programs, divisions, rounds, entries, heats and schedule versions in one statement. With `ON DELETE RESTRICT` from a CF1 table to `entries`, the immediate check would fire as soon as the event cascade deleted an entry while the advancement row still referenced it, so **no event could ever be deleted after an advancement existed**. With `NO ACTION` the check runs after the cascade has also removed the CF1 rows (which reference `events` `ON DELETE CASCADE`, with the history-protection trigger's event-gone exception), so event deletion works, while a **direct** delete of an advanced entry, a round or a version, or a division move, is still refused at the end of its own statement (`23503`). **Decision for the design:** every CF1 foreign key to entries, rounds, heats, divisions, programs and schedule versions is **`ON DELETE NO ACTION ON UPDATE NO ACTION`** (not `RESTRICT`); the FK to `events` is `ON DELETE CASCADE`, the pattern NS1 already uses (`event_competition_heat_no_shows`: `events` cascade, `heat_entry_id` with the default NO ACTION, NS1 l.79–82). The earlier §4.5 and E15 statements that said RESTRICT are corrected. **Explicit test U40 (unrun):** with advancement, withdrawal and heat rows present, (a) a direct delete of an advanced entry, round and version and a division move each fail with `23503`; (b) deleting the **event** succeeds and removes the CF1 rows; (c) re-running (b) with the FKs declared `RESTRICT` fails (documenting why NO ACTION was chosen).

**Trigger mode, function properties and residual privilege risks (revision 16, implementation safety).** (1) **Replica role:** the proposed guard triggers (`cf1_guard_withdrawn_heat_entry` and the other CF1 guards) are created **`ENABLE ALWAYS`**, so they fire under `session_replication_role = replica` (an ordinary origin-mode trigger does not). (2) **Not covered even then:** `TRUNCATE` (no row trigger fires, RLS does not apply; the privilege is presumed from the Supabase default, U46), a migration or statement run by the table owner or a superuser, `ALTER TABLE … DISABLE TRIGGER` (needs table ownership), and a superuser. Setting `session_replication_role` itself needs a privileged role that `authenticated` does not have; these are privilege-based risks, not application paths. (3) **The guard function is `VOLATILE` and says so:** in READ COMMITTED a volatile function's statements take a fresh snapshot, so its reads of the withdrawal rows see a concurrent withdrawal that committed while the guard waited on a lock; a `STABLE` function would use the caller's older snapshot and could miss it. (4) **READ COMMITTED re-fires the BEFORE ROW trigger on the newest row version after a row-lock wait** (documented PostgreSQL behaviour; stated by the reviewer, not tested here, U51), so a guard that waited on a concurrent update re-evaluates against the updated row. (5) **Fail closed:** the function has no `EXCEPTION WHEN OTHERS` swallow; an error reading the withdrawal table, a missing authorizer or an inconsistent state raises, so a direct unauthorized reinstatement is refused rather than allowed.

**Recovery from the ineligible-couple dead end (F2).** The unsupported "no dead end" claim for option 4 is removed. Counter-example: couple X is already `ineligible` and has **no withdrawal row**; a correction is allowed, the revoke runs, apply refuses `COMP_ADVANCEMENT_ENTRY_UNAVAILABLE`, and no Final heat remains to withdraw from; only reverting X's eligibility helps. Feasible, fail-closed fixes, none inventing a lifecycle transition:

* **Pre-check at the correction (recommended with option 1):** the correction trigger refuses `COMP_ADVANCEMENT_CORRECTION_UNRECOVERABLE` when any entry on the current roster (or in the approved result) is `ineligible`, not `confirmed` or in another division **and has no effective withdrawal**; the message says "Withdraw the couple from the Final first, or revert their eligibility." The CF1-B preview shows the same warning. With option 1 the withdrawal can be recorded **without a Final heat** (it is keyed by round and entry), so the manager withdraws X, then opens the correction, and generation 2 carries the withdrawal and does not validate X.
* **Without option 1 (option 4 alone):** the same pre-check is the **clear fail-closed refusal**: the manager must first revert X's eligibility, because no route can exclude X. The dead end is then prevented rather than repaired.
* **Apply-side:** if X becomes unavailable after the revoke and before the next apply, apply refuses `ENTRY_UNAVAILABLE`; under option 1 the manager records the withdrawal (no heat needed) and retries; otherwise the manager reverts eligibility.

**Final completeness and the minimum-field rule (F3).** Withdrawing every advanced couple, or all but one, was unspecified; apply could create an empty Final heat and the start guard checked membership only. Invariant **I7** (completeness): **the Final roster is exactly the advancement's entries minus the pairs with an effective withdrawal**, each present exactly once in the one Final heat, and no extra couple. Checks: (a) **apply** refuses to create a Final heat with no roster entry (`COMP_ADVANCEMENT_BELOW_MINIMUM`; a hard floor of one couple, because an empty heat cannot be ranked, independent of OD-15); (b) **withdrawal** is refused if it would leave fewer couples than the OD-15 minimum; (c) the **start guard** (§5) compares the **set of non-scratched Final heat entries** with the advancement's entries minus effective withdrawals and refuses any difference, including a scratch that has no withdrawal row, a missing heat entry, or an extra couple (`COMP_ADVANCEMENT_ROSTER_INCOMPLETE`, permanent). I8: a withdrawn pair's heat entry stays `scratched` unless an authorized reinstatement exists (the guard above). **Technical limits that bear on OD-15 (unverified, U43):** a heat whose entries are all scratched is not a ballot heat (`_compe2_round_heats` needs one non-scratched, non-no-show entry), so a Final with zero remaining couples **strands the round** (lock refuses `COMP_BALLOTS_INCOMPLETE`: no heat to ballot) and the only exit is cancelling the Final (terminal, C1); the minimum couple count of the ordinal engine was not read.

**(b) OD-15 A: at least two eligible couples to start a Final, however the roster was reduced.** Enforcement points: (1) **apply** refuses to build a roster of fewer than two (advanced count minus carried withdrawals), `COMP_ADVANCEMENT_BELOW_MINIMUM` (this **replaces the earlier hard floor of one**; consequence: a callback with a target of 1 can never produce a Final, so the readiness check should warn when `T < 2` for a callback-plus-Final program: an implementation item); (2) a **withdrawal** that would leave fewer than two is refused; (3) the **start guard** counts the roster entries that are non-scratched **and** pass the §4.6 predicate and refuses the start below two (`COMP_ADVANCEMENT_BELOW_MINIMUM`), after the completeness check (an unrecorded direct scratch fails `ROSTER_INCOMPLETE` first); (4) **after the start**, NS1 no-shows and direct scratches are handled by the OD-17 D checks, which for a **Final** round also refuse lock, calculate and approve with `COMP_ROSTER_BELOW_MINIMUM` when fewer than two eligible couples remain in the ranking set. A Final that falls below two after it started therefore cannot lock, calculate or approve (fail closed); the exits are an NS1 void (it returns the couple to the set), reopening the ballots, or cancelling the Final (terminal, C1). **The earlier "post-start gap" wording is removed.** U43 and U56 test it.

**(c) OD-2 A and G-1 A: consistent with F2/F1, confirmed.** OD-2 A (refuse a callback target larger than the Final's capacity at save and publish) is what the approved F2 setup guard does (T edit, capacity edit and insert, publish and program lock, §3.4.3) with the F1 exemption unchanged. G-1 A (a callback whose cut meets the couple count is out of scope and blocked) is E2's `COMP_CALLBACK_NOT_DANCED` plus apply's `COMP_ADVANCEMENT_SOURCE_STATE` (§1.3); nothing is added.

**(d) OD-18 A with OD-19 D.** OD-18 A: the OD-8 row is **unchanged** (§0.1, §9, §3.2): no heat entry is ever inserted by a reinstatement. The carried-withdrawal sequence is: authorized correction (revokes generation 2), then the audited reinstatement, then apply of the next generation. **Reinstatement does not guarantee advancement:** generation 3 includes the couple **only if the corrected callback still advances them** (precondition 7 validates them again). **Reinstatement after a revoke writes only the reinstatement row** and touches nothing in the cancelled earlier-generation heat (the only scratched heat entry may sit there; E2's `_compe2_round_heats` excludes cancelled heats, so it cannot affect a ranking). OD-19 D (inherits OD-13b C): the withdrawal and reinstatement rows store the requester, the co-signer (`cosigned_by`) and the co-signer's role (`chair` or `manager`, from `_compe2_round_role`), the request id and `transaction_id`; the co-signer must have the `chair` role or be an authorized manager (`can_manage_event_competition` and the verified-email rule), must be a **different person from the opener** (the requester) and **not anyone who files a replacement ballot** (the §4.1 safeguards, unchanged).

## 5. Guards that make the Final consistent with advancement (additive triggers)

**Invariants (revision 11).** A **callback Final** is a round with `round_type = 'final'` whose division's previous round (`sequence_number - 1`) is a `preliminary` round of a program with `advancement_method = 'promote_callback'` (derivable from columns that SS1 freezes at program lock). An **advanced Final** is a callback Final for which **any** row exists in `event_competition_round_advancements` as `target_round_id`, whatever its generation and whether or not it was revoked. The invariants are defined over **every heat of an advanced Final** (heats CF1 created, pre-existing cancelled empty heats, heats of earlier generations), not only over heats an advancement created:

* **I1** an advanced Final has at most one non-cancelled heat in the live version, and it is the heat of the active advancement;
* **I2** its roster (heat entries) is exactly the active advancement's entries; the rows shrink only through scratch/no-show status changes;
* **I3** no heat of an advanced Final changes its round, division, event, version, floor heat or block, and none is moved into or out of one;
* **I4** no heat of an advanced Final is ever revived: a `cancelled` heat stays cancelled;
* **I5** no heat is inserted for an advanced Final outside CF1 apply (any version);
* **I6** (revision 12) no schedule version that holds a foreign Final heat, or that is not the version holding the active advancement's heat, can become `published` or `live` (publication-time invariant, below).
* **I7** (revision 15) the Final roster is exactly the advancement's entries minus the pairs with an effective withdrawal, each present once in the one Final heat, with no extra couple (§4.5);
* **I8** (revision 15) a withdrawn pair's heat entry stays `scratched` unless an authorized reinstatement exists (§4.5; only if §4.4 option 1 is adopted).

**Authorizers (transaction-bound, the codebase's existing pattern; each checks `txid_current()`).** The guard functions are SECURITY DEFINER because the CF1 tables have no grants and no policies.

* **A-apply:** a row in `event_competition_round_advancements` with `target_round_id` = the heat's round and `transaction_id = txid_current()`.
* **A-revoke:** a row in `event_competition_round_advancement_revocations` whose advancement targets the heat's round and whose own `transaction_id = txid_current()`. This is the authorizer of the revoke path's heat cancel, written first inside `_cf1_revoke_advancement`; the advancement row of the revoked generation is from an earlier transaction and authorizes nothing.
* **A-cancel:** an O1 `round_cancelled` row in `event_competition_round_transition_events` for the round with `transaction_id = txid_current()`.
* **A-reset:** only if OD-10 route (b) is chosen: a reset row for the round in the same transaction (§4.2).

**Publication-time invariant (revision 12, P2-1).** I1 as written protects heat rows. A version status flip changes which heats are live **without touching a heat row**, so the deferred backstop cannot see it. In the forged-danced case (no heat of the event has run, because `_hl1_heat_is_danced` accepts a `danced` entry placement on a still-`scheduled` heat, §3.2.1 item 4) the O1 guard `compo1_guard_publish_during_run` does **not** refuse a publish, so a draft or review copy that holds a pre-existing Final heat could become the live version after apply and give a second live Final heat (and, separately, a new live version without the Final's own heat). `COMPO1_RUN_IN_PROGRESS` is therefore **defense in depth only, and I1 does not rely on it**. Enforcement:

* **Trigger and function:** `cf1_guard_publish_final_heats` (function of the same name, SECURITY DEFINER, `search_path = public, pg_temp`), `BEFORE INSERT OR UPDATE OF status ON event_competition_schedule_versions`, acting when `new.status in ('published','live')` and (INSERT, or `old.status is distinct from new.status`).
* **Affected versions:** every version that can enter those states: `draft` and `review` (what `publish_competition_schedule_version` accepts) including copies, and, through a direct status write or a direct INSERT as published, `superseded` and `archived` versions. A flip `published → live` of the version that holds the Final's heat passes.
* **Pins:** none. It validates the **transition**, whichever path made it, so the publish function is not redefined. Trigger names fire alphabetically, so `cf1_…` fires before `compo1_guard_publish_during_run`; it takes the O1 event lock itself (`_compo1_lock_event`, the same version-row-then-event-lock order as that guard, so no new cycle, R1/R4), then validates in a **fresh statement**, so it sees an apply that committed while it waited.
* **Validation boundary,** for every advanced Final R of the event (any advancement row, any generation) and the target version V:
  * **Rule A (no foreign heat):** V holds no non-cancelled heat of R except the heats linked in `event_competition_round_advancement_heats` to R's **active** advancement (none allowed when R has no active advancement). Error `COMP_ADVANCEMENT_PUBLISH_FINAL_HEAT`.
  * **Rule B (continuity):** if R has an active advancement, V must **contain every heat linked to that advancement** (`heat.schedule_version_id = V`). The check is against V, the version being published, **not against the current live version**, so restoring a holding version that was superseded passes. Error `COMP_ADVANCEMENT_PUBLISH_FROZEN`. Because the copy skip keeps Final heats out of drafts, no draft passes B while an advancement is active: after apply, no other version can be published until the correction revokes the advancement. Cost accepted (on supported paths this is already true through O1).
  * **Fail closed for inconsistent records:** more than one active advancement for R, an active advancement with no linked heat, or a linked heat that is cancelled raises `COMP_ADVANCEMENT_PUBLISH_INCONSISTENT`. The forged-danced state is refused through this rule whenever its heats do not match their advancement. All three errors use SQLSTATE `23514` (permanent, not retryable).
* **Closed advancements (revision 13, recovery path).** An advancement whose target round is `cancelled` is **closed**: rules A and B and the consistency rule are **not applied** to that round. Reason: an O1 cancel of a Final ends it for good (C1) and its heats can never run (`advance_competition_floor_heat` needs an `active` round). Without this rule an O1 cancel of a forged-danced Final would leave an active advancement with a cancelled heat and **every later publish would fail `COMP_ADVANCEMENT_PUBLISH_INCONSISTENT` with no repair path** (and a locked `scheduled` heat of a cancelled round stays non-cancelled: O1 cancels only open heats and HL1 refuses reopening on a cancelled round, so rule A could never be satisfied). The rule is a design choice consistent with C1, not an approved policy; it is an **implementation dependency** and a runtime gate (U30). Residual: the cancelled Final's heats stay in older versions as history.
* **No-op** for an event with no advanced Final (one indexed existence check). **Rollback:** drop the trigger; refused while an advancement row exists. **Unverified at runtime:** U25.

**How the floor-heat guard is authorized (P3a).** `_comp10d_guard_floor_heat` sees rows of `event_competition_floor_heats`, which have `(event_id, schedule_version_id, heat_number)` and **no `round_id`**, so "an advancement row for that heat's round" cannot authorize it. It is authorized by **event and version**: a floor-heat **INSERT** (only; UPDATE and DELETE stay refused in a non-draft version) is allowed when (i) an `event_competition_round_advancements` row with `event_id = new.event_id` and `transaction_id = txid_current()` exists, (ii) `new.schedule_version_id = public._compo1_live_version(new.event_id)`, and (iii) `new.heat_number = 1 + max(heat_number)` of that version (append). The clauses are written into the redefined function. This is wider than the round-bound clauses of the other guards (it is not tied to a round), but the advancement row with the current transaction id exists only inside apply, which inserts exactly one floor heat; **unverified (U24):** that nothing else can insert a floor heat in the apply transaction. The heat-child guard and the placement function resolve the round from the heat row (`heat_id` to `event_competition_heats.round_id`) and from `new.round_id`, and use the round-bound form.

**Policy and grant restrictions.** None changed by CF1. Direct writes are refused by the triggers above, not by revoking grants. The `competition_manage` policy (FOR ALL to `authenticated`) and the default table grants stay as they are (Appendix A.2 says which grants were verified from migrations and which are presumed). Two stronger hardening options exist and are **not proposed here** because they change policy or grants and need the P-8 inventory of every app direct write first: (i) revoke INSERT/UPDATE/DELETE on heats, heat entries and heat dances from `authenticated` so every write is an RPC; (ii) add a RESTRICTIVE policy that refuses `authenticated` writes to rows of callback Finals (SECURITY DEFINER RPCs run as the owner and are unaffected). Both are owner-level decisions. **Residual:** the guards cannot stop someone who can disable triggers or set `session_replication_role = replica`; no administrative bypass exists by design, so a repair needs a transaction-bound authorizer or an owner-run migration.

Other CF1 guards: `cf1_guard_final_start` (BEFORE UPDATE OF `status` on rounds, `scheduled → active`): such a Final cannot start without an active advancement, **and its roster is validated under locks at that moment** (below); `cf1_guard_advancement_approval` (§2.4); `cf1_guard_advancement_correction` (§4, which also refuses `COMP_ADVANCEMENT_FINAL_CANCELLED` as a **proposed** rule, owner-confirmable under OD-10, not an approved policy).

**Race-safe Final-start roster validation (revision 14, P2).** *The start transaction.* The only writer of `scheduled → active` for a round is O1 `start_competition_round` (O1 l.~395–440; a direct status write is refused to `authenticated`, C1). Its order is: `_compo1_lock_event(event)`, then the round `FOR UPDATE`, then its readiness checks, `_compo1_record`, and the `UPDATE rounds SET status = 'active'`. `cf1_guard_final_start` fires **inside that UPDATE**, so the event lock and the Final round lock are already held. `advance_competition_floor_heat` starts **heats**, later and separately, and needs the round already `active`; it is not the round start.

*The defect in revision 13.* The roster check read the entries without locking them. A concurrent eligibility commit (the unguarded eligibility screen, or any direct write) can land after the guard's read and before the start commits, so a Final starts with an ineligible couple. A read-only roster check does not give concurrency safety.

*The fix, using only existing functions (no change to `start_competition_round`).* Inside the guard, in this deterministic order, all **after** the event and round locks the start already holds (revision 15: step 1 covers **scratched** rows too; revision 16: the heats are taken **`NOWAIT`**, unlike E2 `lock_competition_round_ballots`, see below): (1) the Final's heats `FOR SHARE NOWAIT` in id order, **cancelled ones included**; (2) **all** heat entries of those heats, **scratched included**, `FOR SHARE` in id order; (3) the **entries** those heat entries point to **and** the advancement's entries (so a withdrawn couple's entry is covered even if its heat entry is absent), `FOR SHARE` in id order, unfiltered. Then a **separate statement** (fresh snapshot, sees updates that committed while a lock waited) revalidates: **completeness** (I7: the set of non-scratched Final heat entries equals the advancement's entries minus the pairs with an effective withdrawal, each present once in the one Final heat, no extra couple, else `COMP_ADVANCEMENT_ROSTER_INCOMPLETE`), and for every roster entry `status = 'confirmed'`, `eligibility_status <> 'ineligible'`, and `event_id`, `program_id`, `division_id` equal to the Final round's (else `COMP_ADVANCEMENT_ROSTER_STALE`, entries listed). **In generation 2 a carried withdrawal has no heat entry** (apply created none): it is a **withdrawal row consulted by apply** that excludes the couple from the generation-2 roster, and the start check subtracts it from the advancement's entry set; nothing is "marked scratched". **Lock-mode conflicts:** `FOR SHARE` on heat entries conflicts with the withdraw, reinstate and un-scratch writers, which hold `FOR UPDATE` or `FOR NO KEY UPDATE` on those rows; the withdraw and reinstate functions also take the event lock and the Final round first and so serialize with the start; a **direct** un-scratch or status write holds only the heat-entry row, so the start waits for it (bounded by the local `lock_timeout`), then revalidates and sees the new state, and a writer that starts later waits for the start's commit. A writer that holds an entry or heat entry makes the start wait; it never makes it skip.'

*Start versus HL1 lock and reopen of a Final heat (revision 16, D1; the reviewer's claim holds).* `set_competition_heat_lock_state` takes the heat row `FOR UPDATE` (10A l.945), and on a reopen the HL1 trigger `_hl1_guard_heat_reopen` then takes the heat's **round** `FOR SHARE`. A manager can lock and reopen a Final heat while the Final round is `scheduled` (the heat lock is allowed for an undanced heat in a `scheduled` or `active` round). `start_competition_round` holds the round `FOR UPDATE`, so a guard that then **waited** for the Final heats `FOR SHARE` would contradict R3 (no waiting on a heat while holding a round) and form a cycle: reopen holds the heat and wants the round; the start holds the round and wants the heat; PostgreSQL would abort one side with `40P01`. **Resolution: the start guard takes the Final heats `FOR SHARE NOWAIT`.** It never waits for a heat while holding the round, so R3 holds and the cycle has no edge from the start's side: if the lock RPC holds a heat, the start fails at once with `55P03`; if the start got the heats first, the reopen waits **at its own heat `FOR UPDATE`** (which conflicts with the start's `FOR SHARE`, so it never reaches the round lock) and proceeds after the start commits. **Does NOWAIT on the heats cover the next two steps without another cycle?** The heat entries and the entries are still locked with waits (bounded by the local `lock_timeout`), and that is cycle-free because the only writers that hold those rows hold nothing else they could be waiting for: a direct heat-entry or entry write holds that one row (its triggers only read the heat; **lifecycle and the sync take entry rows and then heat-entry rows, the reverse of the start's order, and are excluded only because an advanced couple sits on a certified callback heat, so lifecycle refuses and the sync skips before locking: U22, U31, U55**), the lock RPC and the HL1 reopen never touch heat entries or entries, the withdraw and reinstate functions take the event lock and the round first and so serialize with the start, and no entry-update path takes a round lock (U22). The one remaining cycle, a **multi-row** writer in non-id order, is the already-documented U31. Making the heat-entry and entry steps `NOWAIT` too was considered and **not adopted**: it would make the start fail whenever any roster row is merely mid-edit (even an entry-number change). **Defined behaviour:** the guard catches `lock_not_available` (from `NOWAIT` or from the local `lock_timeout`) and re-raises it with SQLSTATE `55P03` and the message `COMP_ADVANCEMENT_CONCURRENT_CHANGE`; the whole start transaction aborts, so **the round does not start (fail closed)**. It is **retryable**: CF1-B retries once server-side after a short pause, then shows "A Final heat or one of its couples is being changed. The round was not started. Try again in a moment." `COMP_*` and `COMPO1_*` validation errors are permanent and never retried. A deadlock of any other kind (`40P01`, `40001`) gets the same treatment. Start-versus-reopen is a runtime gate (U47). E2 `lock_competition_round_ballots` does wait for the heats `FOR SHARE`, but it needs an `active` round and so cannot meet a start; its pre-existing inversion with reopen is U2.

*Lock order, deterministic and consistent with the rest:* event lock, round `FOR UPDATE`, the Final heats `FOR SHARE NOWAIT`, their heat entries `FOR SHARE` (id order, waits), then the entries `FOR SHARE` (id order, waits). Apply takes event lock, source round, target round, result version, live version, then entries in id order: **entries always last, in id order**. Publication guard: version row, then event lock, no round or entry. Registration sync and eligibility writers take a registration or entry row and never a round or the event lock. The revive guard takes a heat then a round `NOWAIT` and never an entry. Hence no cycle with a single-row writer; a **multi-row** entry writer can still cycle with the start exactly as with apply (either side may be the victim, §1.3, U31).

*Caller-visible behaviour.* `40P01`, `40001` and `55P03` (the `lock_timeout` and any `NOWAIT`) are retryable: CF1-B maps them on the Final-start action to "try again" and retries **once**; `COMP_*` and `COMPO1_*` validation errors, including `COMP_ADVANCEMENT_ROSTER_STALE`, are permanent and never retried. Today the start action has no such mapping (the only `40P01` mapping is `heatLock.ts` l.79); that is a CF1-B addition, unverified.

*After the start (revision 18; OD-17 D approved).* The start guard's `FOR SHARE` lasts only for the start transaction, so the start guard itself does not catch a change after the start. It is caught **later, at ballot locking, calculation and approval**, by the OD-17 D cross-check (§4.6 a), which fails closed with `COMP_ROSTER_ENTRY_UNAVAILABLE`, and the OD-15 A minimum is enforced at the same points for a Final (`COMP_ROSTER_BELOW_MINIMUM`). Until a ballot is locked a couple who became ineligible or refunded can still be on the floor; the cross-check stops the **official ranking**, not the dance. The roster check is not repeated at `advance_competition_floor_heat` (an O1 function CF1 does not redefine). **A no-show marked after judges have submitted makes their already-submitted ballots stale:** lock refuses `COMP_BALLOTS_STALE` until judges or scorers file corrected ballot versions (NS1 header l.36–40, E2 `_compe2_round_blockers`); that ballot rework is part of the audited resolution route (U38). The three pinned changes to E2 and F2 are specified, unbuilt and unrun (U57–U61); the refund resolution route (R2) is an open implementation dependency.

**Competing heat writers.** The complete inventory of everything that can write heats, heat entries, heat dances, versions, blocks and the related round and entry rows (functions, triggers and direct writes through the policy), with its grants, existing guards and required enforcement, is **Appendix A.2** (it replaces the shorter list that lived here in revisions 2 to 10, so that one list cannot go stale). The lock order of every writer is Appendix A.3.

All are no-ops for programs that are not callback programs (e.g. "Final only").

Authorization: `_compe2_round_role(p_round_id) = 'manager'` (this includes the verified-email rule for non-managers only; managers pass through `can_manage_event_competition`, so CF1 adds the LAUNCH-SEC-1C `verified_email_for_user` check as NS1 does).

**Lock order (apply), revision 11.** Coarse to fine, rounds in the canonical order `(division_id, sequence_number)`: (1) `_compo1_lock_event(event)`; (2) source round `FOR UPDATE`; (3) target round `FOR UPDATE`; (4) the approved result version row `FOR UPDATE`; (5) the live schedule version row **`FOR KEY SHARE`**; (6) the advanced entry rows **`FOR SHARE`** in id order, then revalidation; then the integrity reads and inserts. **Apply takes no heat row** (no shell). The revoke path (inside the F2 correction transaction, which already holds the callback and later rounds `FOR UPDATE` and takes **no event lock**) takes the Final's non-cancelled heats `FOR UPDATE NOWAIT` and **must not take the event lock**. `_comp10d_copy_floor_plan` pre-locks the callback and Final rounds `FOR KEY SHARE` in the same canonical order. A short function-level `lock_timeout` (R5) bounds steps 1–6. The reasoning, the planners and `create_competition_schedule_version`, the two-round and cross-operation deadlock cases, the retry classification and the requirements an implementation must preserve are in **Appendix A.3**. Withdrawn since revision 10: the claims that apply "serializes" with schedule publish, that a publish retry succeeds, and that apply locks a shell heat.

**Rollback.** App first, then SQL. The rollback file **refuses while any advancement row exists** (it is evidence), restores the F2 `complete_competition_round` text (verifies the restored pin), restores the kind check, drops triggers, then tables. Hosted DEV/PROD: none authorized by this document.

**Grants summary.** Preview and apply: `authenticated`. Tables: none. Revoke function: none. Guard functions: none.

## 7. QA plan

### 7.1 SQL suite (`scripts/…cf1…sql`, run on the dedicated QA Postgres, never hosted, never shared DB)

1. Happy path: approved callback → apply creates one advancement, `n` entries equal the `advanced = true` rows, one Final floor heat + scoring heat + dances + heat entries, one `advancement_applied` audit row, callback round status unchanged.
2. Replay with the same request id → `replayed: true`, no duplicate rows; same id with other args → `COMP_REQUEST_REUSED`.
3. Second apply with a new request id while active → `COMP_ADVANCEMENT_ALREADY_APPLIED`.
4. Refusals: not manager / chair / scorer / judge / other studio / anon; round not approved; stale hash; version not latest approved; null `advanced` (blocked); wrong round type / `advancement_method`; target not `final`/has heats/not draft-or-scheduled; count 0; count > live capacity; entry unavailable; multi-dance.
5. Tie within capacity: F-CT-02 `cap = 8` → 5 entries advance. Tie over capacity: F-CT-02 `cap = 4` → calculate completes with null flags, `approve` refused `COMP_ADVANCEMENT_BLOCKED`, `apply` refused, nothing written.
6. Guards: hand-inserted Final heat entry not in the advancement refused; Final start without advancement refused; advancement tables immutable (UPDATE/DELETE/TRUNCATE refused).
7. Corrections: correction with no Final ballots revokes, cancels the Final heats, writes `advancement_revoked`, then re-approve + apply creates generation 2 with the next heat number; correction refused when Final has a ballot (O5), when the Final heat started, when the Final heat is locked or certified; correction of a not-yet-advanced round untouched.
8. `complete_competition_round`: refuses without an active advancement (still F3-gated), unaffected for non-callback rounds.
9. RLS/isolation: manager of studio A gets zero rows and `COMP_FORBIDDEN` for studio B; entrant/public cannot read advancement, nor the Final roster before publication (the reader inventory result from §3.6).
10. 10D integrity: the Final heat insert still fires the deferred competitor-conflict and music checks.
11. No-op for "Final only" programs.
12. **Existing Final heat refused (revision 11, no reuse):** a non-cancelled Final heat in the live version, empty, with entries, started, locked or certified, gives `COMP_ADVANCEMENT_FINAL_HEATS_PRESENT` and nothing is written; two heats the same; an **unplaced** heat (`schedule_version_id` null, as O1's `COMPO1_HEATS_NOT_PUBLISHED`) the same; cancelled heats only (any version) take the create path in a floor-mode live version and give `COMP_ADVANCEMENT_FINAL_PLACEMENT_MODE` in a block-mode live version; Final round `active`/`complete`/`cancelled` gives `COMP_ADVANCEMENT_TARGET_ROUND_STATE`; a callback round with more than one dance gives `COMP_ADVANCEMENT_MULTI_DANCE`.

Also: no live version gives `COMP_ADVANCEMENT_NO_LIVE_VERSION`.

15. **Placement guard:** the create path passes `validate_competition_heat_schedule_placement` only inside the CF1 transaction; the same INSERT from any other transaction is still refused.

Status-only scratch and un-scratch still work. A non-callback program is unaffected. A transaction-bound authorizer cannot be satisfied by an earlier request (U20).

### 12.1 Capacity RPC transition, rollout and rollback (OD-14)

Requirement: no window may allow a capacity change without a recorded reason on a callback Final; a **block is acceptable, a pass is not**. The old app can only call the 2-argument RPC.

The three options (A–C) are now decision-ready in **§9.2 OD-14** (the owner chooses there). Their technical verdicts, unchanged: (i) keep the 2-argument RPC working until an audited cutover **needs a window in which a reasonless change passes** and is rejected as written; (ii) feature-detect and fall back **is exactly a reasonless pass** and is rejected; **(iii) rewrite the 2-argument RPC to always refuse and ship SQL and app in one train is the recommended option**: fail closed from the first moment CF1-A is applied, one migration, no cutover step, no pass window; its cost is that capacity editing is unavailable from SQL apply until CF1-B is live.

Ordering and what the old app can or cannot do in each window (old app = build before CF1-B; new app = CF1-B):

| Step / window | State | Old app capacity edit | New app capacity edit | Reasonless change possible on a callback Final? |
|---|---|---|---|---|
| W0 before anything | pre-CF1 | works, **no reason, no audit** (today's behavior) | n/a | **yes (today)** |
| 1. Apply CF1-A SQL (W1) | new RPC and trigger live, 2-arg refuses | **refused** with `COMP_CAPACITY_REASON_REQUIRED` | n/a (not deployed) | no |
| 2. Deploy CF1-B app (W2) | both live | n/a | works, reason required, audited | no |
| 3. Verify (SQL suite probes, one real capacity change with a reason, one legacy call refused) | | | | no |
| Rollback R1: roll back the **app** (CF1-B → old app) while SQL stays (W3) | SQL still applied | refused (block) | n/a | no |
| Rollback R2: then roll back the **SQL** (W4), **only possible while no CF1 evidence row exists** | The rollback file refuses if any advancement, capacity-event, correction-cause, co-sign or ballot-correction row exists. **Once the new capacity RPC has been used even once (a capacity-event row), SQL rollback is unreachable; recovery is roll-forward only** (app rollback is still possible; fix forward in SQL) | works, no reason, no audit (pre-CF1 behavior) *only if the rollback ran* | n/a | yes, as in W0, only if the rollback ran |

**Window cost, stated plainly.** The 2-argument refusal applies to **every** round, so in W1 (and in W3 if the app rolls back) the old app also loses **first-round heat-size editing**, not only the callback Final's. A variant scoped to callback Finals only would leave other rounds editable without a reason, which the approved reason requirement does not allow, so it is not recommended; it is listed so the owner can choose it knowingly. Capacity editing is the only old-app function affected; the planner reads stored capacity as before.

If the app must roll back and capacity editing is needed before the SQL can be rolled back, the answer is **no**: it stays blocked (W3). That is intentional. There is no cutover migration to run or undo, so there is no state in which the audited switch could be left half-applied. Rollback order is always **app first, then SQL** (never SQL first: a rolled-back SQL under the new app would break the new RPC call).

**A.2b What the scratch writers and the registration sync do and do not block (re-derivation, OD-5/P-3).** (1) `change_competition_entry_lifecycle` **is** a scratch writer; it refuses when any of the entry's heats is `locked` or `certified`, and direct `heat_entries` updates are refused on locked or certified heats by `protect_locked_competition_heat_entry`. (4) A **Final** heat CF1 filled is `open`, but `change_competition_entry_lifecycle` still **refuses** an advanced couple (its callback heat entry is certified), so there is no supported scratch route before the Final starts (§4.3; revision 12 said otherwise and was wrong). NS1 needs an `active` round. SC1 is outside this stack. (5) **Registration sync (revision 11):** it cannot withdraw an advanced couple between approval and apply (row 9), so a registration cancelled or refunded in that window is **not** caught by precondition 7's status check and relies on the R2 exception check (not in the stack): the withdrawn-couple route stays dead and this gap joins P-3. ### A.2d 10D.1 protection: what it guarantees and what it does not (revision 13)

**Exact definition (read in `20261112090000_phase10d1_heat_entry_eligibility.sql`).** 10D.1 redefines `_comp10d_check_floor_heat_integrity()` (SECURITY DEFINER, `search_path = public, pg_temp`; its preflight asserts the 10D body's md5 `115297ed…` and that the trigger `comp10d_heat_entry_floor_integrity` exists and is deferrable and initially deferred). That trigger is a **constraint trigger AFTER INSERT OR UPDATE on `event_competition_heat_entries`, FOR EACH ROW, DEFERRABLE INITIALLY DEFERRED** (10D l.~277–283). The new check runs for `tg_table_name = 'event_competition_heat_entries'` when `tg_op = 'INSERT'` **or** (on UPDATE) `entry_id` or `heat_id` changed, **and** the heat-entry row still exists at the time the deferred trigger runs (`exists (select 1 from heat_entries where id = new.id)`). It then reads the entry (`id` and `event_id`); if `status` is not `confirmed` or `eligibility_status = 'ineligible'` (or the entry row is missing) it raises **`COMP10D_ENTRY_NOT_SCHEDULABLE`**, SQLSTATE `23514`.

**What it guarantees at commit.** For every heat-entry **INSERT**, and every UPDATE that **changes the entry or the heat**: the entry is `confirmed` and not `ineligible` **as of commit time**, whoever wrote the row (planner RPC, organizer RPC, direct authenticated write, `service_role`), because the function is a definer and a constraint trigger cannot be skipped by a statement. A row inserted and deleted in the same transaction is not checked. An entry made `confirmed` again before commit passes. `eligibility_status` values `unverified`, `needs_review` and `waived` pass; only `ineligible` fails. The check applies to every schedule version, draft or live (it does not look at the heat's version).

**What it does not protect.** Status-only updates of an existing placement (`checked_in`, `scratched`, `danced`, `disqualified`) and any UPDATE that changes neither `entry_id` nor `heat_id`; **any later change** of the entry's `status`, `eligibility_status` or `division_id` after the placement exists (so it does **not** protect the Final roster from the eligibility screen); DELETE; the entry's registration for the dance (a planner pre-check only); an administrator who disables triggers or sets `session_replication_role = replica`; and it does not look at the advancement at all.

**How apply maps the error.** Apply revalidates precondition 7 itself, **before** the inserts, and raises `COMP_ADVANCEMENT_ENTRY_UNAVAILABLE`; with the advanced entries held `FOR SHARE` until commit no writer can change them before the deferred check runs, so the raw error should be unreachable inside apply. It fires at COMMIT, outside the function, so SQL cannot re-map it; if it ever surfaces, the app maps raw `COMP10D_*` by prefix (§3.2.1).

**Runtime verification required (not executed): U32.** On a chain-built QA database: insert a heat entry for a `withdrawn`, `pending` and `ineligible` entry as `authenticated` and as `service_role` (expect failure at COMMIT, not at the statement); `SET CONSTRAINTS ALL IMMEDIATE` fires at statement end; a status-only update passes; a later change of the entry's eligibility after the placement passes (documents the gap); insert-then-delete in one transaction passes; the installed function md5 matches the pins.

**Retryable versus permanent errors, and caller behaviour.** Retryable: `40P01`, `40001`, `55P03` (the `NOWAIT` and the `lock_timeout` both give `55P03`). Permanent: every `COMP_*` and `COMPO1_*` validation failure (`P0001`, `23514`, `42501`), including `COMPO1_RUN_IN_PROGRESS`. CF1-B's advance action retries a retryable code once and never a permanent one (apply is idempotent on its request id); the schedule actions listed in §3.2.1 only map the message and leave the retry to the manager; the correction path stays manual. A deadlock victim may be **either** transaction, including the unrelated one.

**Lock-order requirements an implementation must preserve.**

* **R1** Never take the O1 event lock after any round lock in the same transaction (so the revoke trigger, which runs inside the correction RPC, must not call `_compo1_lock_event`).
* **R2** Take round locks in `(division_id, sequence_number)` order (apply: source then target; the copy pre-lock and the correction already follow ascending sequence).
* **R3** While any round lock is held, take a heat row only with `NOWAIT`, never wait.
* **R4** Never take `FOR UPDATE` or `FOR NO KEY UPDATE` on a schedule version row; the only version lock CF1 takes is `FOR KEY SHARE` on the live version.
* **R5** Bound the waiting steps with a **function-level** `SET lock_timeout = '5s'` clause on the CF1 function that waits (apply, withdraw, reinstate, and the start and publication guard functions), **not** `SET LOCAL`: `SET LOCAL` lasts until the end of the transaction and would leak to the caller's later statements and to the 10D deferred triggers at commit. The function-level setting is restored when the function returns. **Exactly which statements run under it:** in apply, withdraw and reinstate, every statement of the function (steps 1–6 and the writes); in the start guard function, only the guard's own statements (the heat entries, the entries and the revalidation; the heats are `NOWAIT`); the event lock and the round lock that `start_competition_round` takes **before** the guard are O1's own and are **not** bounded by it (unchanged, unbounded as today). Never set it to 0 (U54).
* **R6** A CF1 guard trigger that locks a round does so `FOR SHARE NOWAIT`, only on the revive path **when no advancement is visible and the round is `draft`/`scheduled`**, and only after taking the heat the UPDATE already holds (the HL1 reopen order); it never waits.
* **R7** The `_comp10d_copy_floor_plan` pre-lock covers only the callback and Final rounds of callback programs, in canonical order, before any heat insert.
* **R8** (revision 12) The advanced entry rows are locked `FOR SHARE` in id order after the version lock and before any insert (apply), or under the event and round locks of the start guard (Final start): **entry rows are always the last locks taken, in id order, in every CF1 path; at the Final start the Final heats (`FOR SHARE NOWAIT`) and then their heat entries (`FOR SHARE`, id order, scratched included) come first; the heats are `NOWAIT`, unlike E2 `lock_competition_round_ballots`, to honour R3**; no CF1 path locks an entry row `FOR UPDATE` or `FOR NO KEY UPDATE`.
* **R9** (revision 12) The publication guard takes the event lock and nothing else; it never takes a round, heat or entry lock.
* **R10** (revision 14) Withdrawal and reinstatement (if adopted) take the event lock first, then the Final round, then heat rows `NOWAIT`, then entry rows; they never take a version lock.
