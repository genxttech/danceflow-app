Status: DOCS ONLY. Read-only research of PUBLIC vendor documentation; no account, signup, form or contact; nothing sent to any vendor. Resolves (or honestly leaves open) the pre-build `[?]` list in `Wallet_Passes_Design.md` section 16 and the Zapier/Make requirements in `Integrations_Candidates.md` and `Public_API_Webhooks_Design.md`.
Retrieval date for every fact below: **2026-11-23** (by a research agent using WebFetch/WebSearch; page content is returned through a summarizing fetch tool, so "[P]" means the fetched primary page states it, not that the text was read verbatim by a human). Tags: **[P]** primary vendor page; **[S]** snippet or third party only; **[SILENCE]** the relevant primary page says nothing (not proof that no rule exists); **[UNVERIFIABLE]** could not be established, with what was tried. ## E. What changes in our designs because of these facts
1. **Apple barcodes need `messageEncoding`** (A7): the pass builder must always set it (UTF-8 is not guaranteed by the page; `iso-8859-1` is the documented example) and our pass tokens/ticket codes must be encodable in it (use ASCII/base32 only: already true for `DF-…` codes and the proposed `DFP1.…` token).
2. **The Apple list endpoint is authenticated by device library id only** (A10). Our web service must therefore return only serials that device registered, treat the device library id as an unguessable-in-practice device secret, rate limit by device and IP-miss, and never put anything identifying in the list response (opaque serials only). The per-pass `authenticationToken` still guards register, unregister and get-pass.
3. **Token length** (A14) is not specified by Apple: keep >= 32 random bytes, stored hash-only.
4. **Voiding** is the boolean `voided` plus `expirationDate` (A15). Expired-pass display is unverified, so a voided pass is the way to retire a refunded or ended pass; QA on a real device is mandatory (BLOCKED until an Apple account is authorized).
5. **Certificate validity is unknown** (A3): the design keeps expiry monitoring (alert at 60/30/7 days after the actual date is read from the issued certificate at creation time), documents that an expired certificate stops new passes and updates but not installed passes (A4), and requires the WWDR G4 intermediate in the signature chain (A5).
6. **Apple fee** (A1) is $99/year if a new account is needed; the Student iOS app implies an existing account, to be confirmed by the owner (still an enrollment/authorization item, OD-9).
7. **Google demo mode** (B1): until publishing access is granted, only listed test accounts get passes, marked "[TEST ONLY]". Review time and fees are unknown (B2), so the schedule must not assume a date, and the first release should be pilot-only with allowlisted accounts.
8. **Google JWT**: RS256 with the service-account key; claims as in B3; keep under 1,800 characters or insert objects through REST and reference ids (B4). Use `GenericObject` for membership/pack passes (required `cardTitle`, `header`) and decide EventTicket vs Generic for tickets after reading the full EventTicketObject requirements (B6).
9. **Google API quota** is 20 requests per second (B8): the update worker must throttle (token bucket) well under it and back off on 429.
10. **Zapier/Make private apps need no approval and no developer fee** (C1, D1, D2), but Zapier's private-integration API limits depend on the owner's Zapier plan (C3), Make's plan/fee requirement is unknown (D4), and **Make "Public" publishing is permanent** (D1): do not publish a Make app to Public casually; prefer sharing within an organization first. Webhook subscribe/unsubscribe endpoints are required for REST Hook triggers (C4), which the webhook design already includes.
