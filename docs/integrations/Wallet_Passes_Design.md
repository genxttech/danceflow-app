## 1. Goals and non-goals
Goals: a dancer (or guardian) can add (a) a studio membership card, (b) a class-pack card with remaining classes, and (c) an event ticket to Apple Wallet or Google Wallet; the card stays correct as classes are used, packs expire or are refunded, and memberships end; a front-desk scanner can resolve the QR on the card to the same check-in screens staff use today; revoking or voiding a card is immediate on our side.
Non-goals for v1: NFC/Smart Tap, rotating (TOTP) barcodes, payments or stored value on the pass, location-triggered lock-screen surfacing, pass sharing, any marketing push, Competition-governed events, passes for anyone without a DanceFlow account relationship, and any new paid entitlement.
Principle: **the pass is a convenience copy, never authority.** The QR proves nothing by itself; every scan is verified server-side against live state, so a stale, voided or screenshotted pass cannot grant anything.

## 2. Native vs third party
A wallet pass is not a data integration with a business partner; it is a DanceFlow-signed document that lives on the user's device and in Apple/Google's wallet services. It overlaps nothing we already ship except the on-screen ticket/QR in the Student app (which stays as the always-available fallback). Apple and Google become processors of the pass content (privacy policy and terms updates are owner items, section 14).

## 3. Repo facts this design builds on (read from origin/main and DEV catalog, 2026-11-23)
- **Event tickets:** `event_registration_attendees.ticket_code` (unique, `DF-…`, generated by `generate_event_ticket_code()`), `ticket_token`, `ticket_issued_at`, `checked_in_at`. QR image route `src/app/api/tickets/qr/route.ts` renders only `DF-[A-Z0-9-]{6,80}` codes. Staff scan with `TicketCodeScanner` on the event check-in page. The Student app shows the ticket in `mobile/student/app/wallet/event-tickets.tsx` (`ticketPass.ts` builds the on-screen pass).
- **Client identity QR:** `clients.client_qr_token` (plaintext text, `gen_random_uuid()` default, unique, **static and never rotated**). Staff open `/app/client-identity/<token>`; the RPC `get_client_by_qr_token_for_checkin` (any active studio role, studio-scoped, minimal fields: id, first/last name, photo, skill level) returns the client; appointment check-in goes through the minimized `get_client_appointments_for_checkin` RPC.
- **Lesson/class self check-in:** dancers check in inside the Student app (`/api/student/appointments/[id]/check-in`, window opens/closes, class requires current `booked` enrollment); no QR is involved.
- **Packs and memberships:** `client_packages` (`name_snapshot`, `lesson_count_snapshot`, `lessons_used`, `lessons_remaining`, `expiration_date`, `active`, `archived_at`, `refunded_at`, `refund_status`); `client_memberships` (`status`, `name_snapshot`, `starts_on`, `ends_on`, `current_period_end`, `cancel_at_period_end`). Refund flows already exist (package refund reconciliation).
- **Account links:** `client_account_links` (`status`, `relationship_type`, `can_view_schedule`, `can_manage_bookings`) decides which profiles an account may see; guardian links carry dependents.
- **Studio branding:** studio name/public name exist; per-studio pass logo and colours do not (a new, owner-supplied asset, section 12).

## 4. Pass model
| Pass | Source row | Apple style | Google class | Front (no PII beyond first name) | Barcode |
|---|---|---|---|---|---|
| Membership card | `client_memberships` | `generic` (or `storeCard`) | Generic | studio name, plan name, status (Active/Paused/Ended), valid through (`current_period_end` or `ends_on`), holder first name | pass token (6.2) |
| Class pack | `client_packages` | `generic` (or `storeCard`) | Generic | studio, pack name, "N of M classes left", expires date, holder first name | pass token (6.2) |
| Event ticket | `event_registration_attendees` (+ event) | `eventTicket` | EventTicket (or Generic) | event name, date/time, venue name, attendee first name (or "Ticket 2 of 4"), ticket status | existing `ticket_code` (6.1) |
One pass per source row, per platform. Passes are created only on the dancer's explicit "Add to Wallet" action (no unsolicited creation). Minimal fields only: no email, phone, birth date, payments, prices, notes, photo, membership price or payment method, and no member id that is usable elsewhere. Back-of-pass text: studio name, a support URL (studio public page), and "Updates may take a while to appear."
Studio branding: logo and a background colour supplied by the studio (owner-side asset), defaulting to DanceFlow neutral; no per-studio Pass Type ID (single platform pass type, section 7).

## 6. QR / check-in token semantics
### 6.1 Event tickets: reuse the existing code
The barcode message is the existing `ticket_code` (`DF-…`, QR format). Staff scanning is unchanged. Hard requirement before enabling: confirm the existing check-in action rejects refunded/cancelled registrations and double scans (verify in `events/[id]/check-in`; if it does not, fix there, not on the pass). A static code on a lock screen is acceptable because it is already printed/emailed today and is validated server-side.
### 6.2 Memberships and class packs: new revocable pass token (recommended) instead of the static client QR
Reusing `clients.client_qr_token` would put a permanent, non-rotatable identifier on every lock screen and in Apple/Google's systems. Recommendation: a stateless, MAC-protected token **bound to the pass**: `DFP1.<passId>.<version>.<mac>` where `mac = truncate(HMAC-SHA256(passSecretFromVault, passId|version), 16 bytes)`, base32/URL-safe. The database stores only `token_version` (rotate = increment). Resolution: staff scanner extracts passId, verifies MAC in constant time, loads the pass, checks `status=active` and `token_version`, then returns the same minimized identity fields as `get_client_by_qr_token_for_checkin` through a new service-role-callable resolver that enforces the scanning user's active studio role (never exposes email/phone). A voided/refunded/rotated pass fails with one uniform message. Existing static client QR flows keep working unchanged.
Alternative D1 (owner decision): reuse the static `client_qr_token` for fastest delivery and zero scanner changes, accepting a permanent bearer identifier on devices. Not recommended.
### 6.3 What scanning means
A scan only identifies the holder to an authorized staff member and opens the existing check-in screen; checking in for a lesson, class or event is still the staff action it is today, with all its validation (class enrollment, package credits, payment gates). The pass never carries entitlements, only an identifier, and its human-readable balances are informational ("N classes left" is recomputed from the live row at scan time on the staff screen).
### 6.4 Barcode properties
QR only, high error correction where the format allows, message encoding UTF-8 [?]. No NFC, no TOTP rotating codes in v1 (Google supports them for tickets [P: rotating-barcodes page, tickets/events section only]; Apple behavior [?]); revisit if screenshot abuse appears.

## 7. Apple Wallet (PassKit)
Facts verified in primary pages [P] and items still to verify [?]:
- **Pass Type ID and certificate:** only the Account Holder or an Admin of the Apple Developer account can register a Pass Type ID and create its certificate [P: developer.apple.com/help/account/capabilities/create-wallet-identifiers-and-certificates/]. Program membership is required to use the Wallet artwork/badge [P: add-to-apple-wallet-guidelines]; the annual fee and enrollment type were not confirmed [?]. A Pass Type ID belongs to a team (`teamIdentifier` must match) so the team that signs the iOS app can hold it [P-implied]. Certificate lifetime/renewal [?] (plan for expiry monitoring: alert 60/30/7 days before).
- **One platform Pass Type ID** (for example `pass.<danceflow reverse-DNS>`) for all studios; studio identity is carried in `organizationName`, logo/colours and the serial, not in the Pass Type ID, so no per-studio Apple enrollment.
- **Build and signing** [P: building-a-pass]: `pass.json` + images + `manifest.json` (SHA-1 of every file) + detached PKCS#7 `signature` using the pass certificate's private key, zipped to `.pkpass`; `passTypeIdentifier`/`teamIdentifier` must match the certificate; required keys include description, formatVersion 1, organizationName, passTypeIdentifier, serialNumber, teamIdentifier [?]. The WWDR intermediate certificate is part of the signature chain [S]. The `barcodes` array replaces the deprecated single `barcode` [P]. Styles: boardingPass, coupon, eventTicket, generic, storeCard [P].
- **Updating** [P: adding-a-web-service-to-update-passes]: `webServiceURL` (HTTPS) and `authenticationToken`; the device registers with our service; we push an **empty** `{}` APNs payload to the device's push token **using the same certificate/private key that signed the pass**; the device then calls our service for serial numbers changed since its last `passesUpdatedSince` tag and fetches the new pass. Serial and token cannot change. Endpoint paths, header form, token minimum length, 304/204 behavior, voiding fields and push rate limits [?] (to be read from the "PassKit Web Service Reference" before build).
- **Distribution** [P: distributing-and-updating-a-pass]: website download of a `.pkpass`, email attachment, or in-app add; **no Apple review or approval of passes is mentioned** (absence in the pages read; confirm before relying on it). Add to Apple Wallet badge rules [P]: only Apple's badge artwork, no modification, on web/email explain how to open on an iPhone, required trademark credit line where legal text appears.
- **Key custody:** the pass certificate private key (signing + APNs) is a platform secret in vault v2, loaded only by the signing/push worker, never logged, never returned to any client, rotated before expiry with a documented swap procedure; prefer signing in a dedicated server function with no other code paths. A KMS/HSM option is an owner decision (Architecture OD-4).
- **Web service design:** per-pass random `authenticationToken` (>= 32 bytes), stored hash-only; endpoints authenticate with it; the "serial numbers for device" call returns only serials registered by that device AND whose tokens validate in that request context; uniform 401/404; per-device and per-IP-miss rate limits; no studio or client identifiers in URLs beyond the opaque serial `<passId>`; request logs by pass id only.
- **APNs from serverless:** HTTP/2 with the pass certificate (certificate-based auth); production environment only for passes [P]. Send from the worker, never inline in user requests; delete registrations on invalid-token responses [P]. Library choice (a vetted pass-signing library vs a small in-house signer using Node crypto) is an engineering decision at build time; any new dependency changes `package.json` (CODEOWNERS-gated).

## 9. Privacy, minimization and exclusions
- Pass content is the minimum needed (section 4). Holder name: first name only by default; a guardian's pass for a dependent shows the dependent's first name only, never a photo, never a birth date; a known minor's own account cannot create a pass (guardian link only), same rule as calendar feeds.
- No location triggers or lock-screen "relevant date/location" surfacing in v1 (privacy and review simplicity).
- Event tickets only for an explicit allowlist of event classes; Competition-governed events, minors' sensitive data, scoring/results, judge identity and any payment data are excluded by allowlist (no price, no payment status, no order number on any pass).
- Apple and Google process the pass content on their platforms; the owner updates the privacy policy and studio terms (section 14). Removing a pass from a device does not delete the server record (we void it).
- Logs and audit never contain token values, auth tokens, push tokens or pass bodies.

## 10. Revocation, refunds and updates
- **Desired-state reconciler** (like the Google Calendar reconciler): a cron computes the desired pass state from the live source row (membership status/end, pack remaining/expiry/refund/archive, ticket status/check-in/refund, event cancelled) and compares `desired_state_hash` with `synced_state_hash`; on change it enqueues an update/void job. Event-driven enqueues (refund, cancel, check-in) are added through the existing domain RPC/outbox patterns later; the reconciler is the safety net and the first implementation.
- **Void/revoke** triggers: membership ended or cancelled, pack exhausted/expired/refunded/archived (`refunded_at`, `refund_status`), ticket refunded or event cancelled, dancer removes their account/link, guardian link removed, staff incident "void all". Apple: push, then the fetched pass is marked void/expired (field names [?] from the reference); Google: PATCH object state. Our side is immediate: the scan resolver rejects a voided pass at once, and the web service stops returning it for update.
- **Latency is not guaranteed** (Apple refresh after push is not documented; Google reflects PATCH on its own schedule). Therefore balances shown on the pass are informational, and the staff screen always shows live data.
- Check-in effects (lesson used, ticket scanned) update the pass opportunistically, not as a requirement for correctness.

## 11. Tenant isolation and abuse controls
Every wallet row carries `studio_id`; every RPC takes the studio and holder (tenant guards as in the feed RPCs); the Apple web service resolves a pass only via its own auth token hash and returns only the caller device's registered passes; the scan resolver verifies the scanner's active role in the pass's studio; download links are one-time and 5 minutes; mint is throttled per person (10/hour, fail closed) and per studio; per-IP-miss limits protect the web service and resolver; kill switches `WALLET_PASSES_ENABLED`, `WALLET_APPLE_ENABLED`, `WALLET_GOOGLE_ENABLED` plus the per-studio allowlist; incident actions: void all passes of a studio, disable a platform, rotate the pass MAC secret (all membership/pack barcodes become invalid and are refreshed by update).

## 19. Source validation, 2026-11-26 (owner disposition I12; checked against origin/main source, no database or runtime test)
These corrections **supersede** the statements above. Verdict: design direction accepted, **changes required before implementation approval**.
1. **Ticket check-in (6.1):** replace "verify" with a prerequisite slice that hardens the existing check-in flow (server-side authorization, atomic single-use claim, explicit payment-state policy including partial refunds, event-state check, one code path for every way of marking attendance). Details are tracked privately.
2. **Ticket codes (3):** codes are filled by a database trigger when blank and are also generated by application code; the format is `DF-` plus 10 hexadecimal characters.
3. **Client identity QR (3, 6.2, D1):** the column is never rotated, but no current flow issues it as a scannable code and no scanner reads it, so the earlier "existing static client QR flows" and "zero scanner changes" statements are wrong. Both D1 options need scanner work; the recommendation (a new revocable pass token) is unchanged. The identity lookup function authorizes by the signed-in user, so a pass-token resolver must take an explicit, verified acting user.
4. **Pack balances (4, 10):** read balances from `client_package_items` (usage type, total/used/remaining, unlimited flag; packs can hold several item types). The `lessons_*` columns on `client_packages` are not a reliable source.
5. **Refunds (10):** only a **full** package refund voids; a partial refund also sets `refunded_at`, and a refund reversal clears it, so voiding must be reversible. Event ticket state derives from the registration (there is no attendee status). No automatic membership void on payment refund was found.
6. **Memberships (4, 10):** map all seven statuses (active, paused, cancelled, expired, pending, past_due, unpaid) to pass states.
7. **Ticket ownership (11, 12):** `client_id` can be empty on registrations; ownership is user-based, so ticket passes resolve the holder by user, not only by client profile.
