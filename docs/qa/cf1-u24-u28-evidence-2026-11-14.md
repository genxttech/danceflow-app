# CF1 U24 / U28 new evidence (2026-11-14, read-only)

Statuses are unchanged: **U24 stays BLOCKED** (accepted design residual, not PASS, not waived) and **U28 stays FAIL as worded**. This file records only new evidence. No hosted writes, no service credentials.

## U24: reachability of the in-transaction floor-heat residual (PROD catalog, read-only, 2026-11-14 04:59Z)
Residual (unchanged): `_cf1_auth_apply_floor_heat` admits a second append-position floor-heat insert inside the SAME apply transaction. It is a boolean authorizer called from the floor-heat guard; it writes nothing. It passes only if an `event_competition_round_advancements` row with `transaction_id = txid_current()` exists for the event.

New PROD facts:
- `event_competition_round_advancements`: RLS on, **no policies, and anon / authenticated / service_role hold no INSERT, UPDATE, DELETE or TRUNCATE**. Clients cannot create the transaction marker row themselves.
- The only function that inserts into that table is `apply_competition_round_advancement(uuid,uuid,uuid)`: SECURITY DEFINER, owner postgres. It is also the **only** function whose source both inserts advancement rows and touches floor heats.
- Floor-heat INSERT privilege: only `service_role` (not `authenticated`, not `anon`); trigger `comp10d_guard_floor_heat` is in place beside the CF1 authorizer path. Other definer functions inserting floor heats (`insert_competition_floor_heat`, `apply_competition_floor_plan`, `_comp10d_copy_floor_plan`) never create an advancement row, so they cannot satisfy the authorizer's first condition.
- Conclusion: a client can only satisfy the authorizer by running a second floor-heat insert inside the same database transaction as the apply RPC. PostgREST executes one statement or one RPC per request, so no client composition exists. Reaching the residual requires a SECURITY DEFINER function body (the reviewed apply RPC itself) or a privileged direct SQL session (service role connection string / superuser). This bounds, but does not remove, the residual; status unchanged.

## U28: hosted PostgREST version still unreadable read-only; behaviour is version-dependent
- Unauthenticated probe of the hosted REST root (no key) returns 401 `UNAUTHORIZED_MISSING_API_KEY` with only gateway headers (`sb-gateway-version: 1`, `sb-project-ref`); no PostgREST version is exposed. Reading it needs a key or the Supabase dashboard (Settings, Infrastructure), which the owner can open.
- Published guidance: Supabase's troubleshooting note on SQLSTATE 40001 says PostgREST 14 retries such failures indefinitely and that the behaviour is fixed in PostgREST 16 (https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b). Local stack is PostgREST 14.8, which matches the transparent retry seen locally; the hosted version decides whether a deadlock surfaces. Evidence is consistent with the earlier FAIL result and does not change it.
- Engineering consequence (unchanged): RPCs that can deadlock must stay idempotent on `p_request_id`; do not rely on the client seeing `40P01`.
