## 3. The snapshot
- Content: `pg_dump --schema-only -n public` (tables, functions, triggers, policies, grants, enums, indexes, constraints). No rows. Not taken from DEV or PROD. It is taken from this host's local QA chain, which was built from the July production schema-only dump plus bootstrap plus every live-line migration in order (the existing recipe: `fullchain/build.mjs`, `bootstrap.sql`, order files, 4 explicit skips, 3 CRLF conversions).
- Manifest (JSON, committed in clear): source commit, `git rev-parse <commit>:src/lib/supabase/migrations` (the migrations tree id), Postgres image tag, `pg_dump` version, line counts, and the existing `fp.sql` fingerprint hash.
- Relationship to migrations: the snapshot already contains every migration up to its source commit. The runner compares the pinned commit's migrations tree id with the manifest and FAILS CLOSED on a mismatch (a new migration means a new snapshot); it never replays migrations on top.
- Reference seed: `e2e/setup/qa-reference-data.sql` (in the repo) is applied on the runner under its own local-stack guard; it adds the accounting categories and the `document-files` bucket.

## 4. Secure handling (nothing here is done yet)
1. Build the dump locally from the QA chain only, into a scratch directory outside the repo (ACL: current user).
2. Scan before anything is committed: reject the dump if it contains JWTs, `sk_`/`rk_`/`whsec_`/`Bearer` strings, hard-coded URLs with credentials, email addresses outside reserved test domains, or phone numbers; review function bodies of cron and notification functions by hand. If any hit cannot be removed at the source, D1 stops.
3. Encrypt with GnuPG symmetric AES-256 (integrity-protected) using a 40+ character random passphrase generated on the engineering host and stored only as a file under a user-only protected directory, never printed, never in chat.
4. Commit only the ciphertext (`docs/qa/cf1-stripe-test/db/qa-schema.sql.gpg`) and the manifest; pin the ciphertext sha256 in the workflow (`CF1_DB_SNAPSHOT_SHA256`).
5. The owner enters the passphrase once, in the browser, as environment secret `CF1_DB_SNAPSHOT_PASSPHRASE` of `competition-stripe-test` (copied from the protected file). The runner decrypts into `$RUNNER_TEMP` with `umask 077` in the one step that needs it, restores, and wipes; the plaintext is never uploaded and never echoed.
6. Rotation: a new snapshot gets a new passphrase and new ciphertext; the old ciphertext stays in public git history.
Residuals, stated plainly: the repo is public, so the ciphertext is permanent public data. If the passphrase leaks or the cipher is ever broken, the base schema of the product becomes readable (table and column names, RLS policies, function bodies; no customer data). The migrations already expose most of it, but the pre-migration base schema is new exposure. The secret scan in step 2 is therefore a hard precondition, and the owner accepts this residual or chooses another option before step 4.

## 6. F1 result (local feasibility, 2026-11-19, scratch directory, nothing exported or committed)
Setup: Supabase CLI 2.90.0 scratch project `cf1-d1-f1` outside the repo, trimmed config (studio, realtime, analytics, pooler off; its own ports 59320-59329 so it cannot collide with the host's other stacks, and the separate `df-isoqa-smoke-*` containers another session runs were not touched), started with `supabase start -x studio,realtime,imgproxy,vector,logflare,edge-runtime,supavisor,postgres-meta`.
- **Start time:** 3 min 33 s on this host with most images already cached (a cold runner adds image pull time; plan 6-10 minutes). Six containers: db, auth (GoTrue), rest (PostgREST), kong, storage, inbucket. About 400 MB RAM idle.
- **Services work:** Auth sign-up and password sign-in returned 200 and a user token; REST read and insert with the service key worked; the mail catcher answered; Storage created the bucket `document-files` (private, 15 MB limit) and listed it; Row Level Security enforced for a signed-in user (own row 201, someone else's row 403).
- **Restore mechanics proven on a SYNTHETIC `public` schema only** (a table, an RLS policy, a trigger function, grants; never the QA chain): `pg_dump -n public --schema-only --no-owner`, then `drop schema public cascade`, then restore. Findings that change the plan: (1) the dump contains `CREATE SCHEMA public`, so the restore must drop the schema first; (2) the dump contains 24 `ALTER DEFAULT PRIVILEGES` statements, and restoring as `postgres` fails with "permission denied to change default privileges" part-way through; **restoring as `supabase_admin` succeeded with exit 0** and policies, triggers and grants came back intact. The runner step must therefore restore as `supabase_admin`, then `notify pgrst, 'reload schema'`.
- **Not tested, by design:** the real snapshot (no database was dumped or exported), the migration-tree check, the reference seed, and the real app against this stack.
- **Go/no-go:** GO for the runner stack. The remaining D1 risk is not the stack, it is the snapshot content and handling (sections 3 and 4), which need F2 and F3 authorization.
- The scratch project (config only, no data, containers and volumes removed with `supabase stop --no-backup`) is in `C:\Dev\cf1-d1-f1`.
