## 1. Why a runner on GitHub (and what differs from D24)
The approved credential-isolation pattern (D24, `docs/billing/D24-GITHUB-ENVIRONMENT-PROOF.md`): a protected GitHub environment holds the only Stripe secret; the owner's approval click authorizes one run of an exact commit; the agent never sees the key; output is encrypted to the engineering evidence key (`scripts/qa/d24-gh-proof/evidence-public-key.pem`, private half stays with the owner/engineering host) and only ciphertext is uploaded.
Three things differ for Competition and are the reason a copy-paste of D24 is not enough:
1. **The harness is not on `main`.** `e2e/tests/competition-full-event.spec.ts` and the money helpers exist on `release/website-embeds` (the live line) and the CF1 candidate branch, not on `main` (`main` lacks the live-line commits; see main-reconcile status). D24's workflow is main-only. The Competition runner must run on the live line (the code that is actually in production), so its environment needs a deployment-branch rule for that branch.
2. **The harness needs a full TEST secret key, not a 3-permission restricted key.** It pays the hosted Checkout page through `POST /v1/payment_pages/<cs>/confirm` and creates `tok_visa` PaymentMethods on the connected account (`e2e/helpers/competitionFullEvent.ts: payCheckoutSession`), and the app itself creates/expires Checkout Sessions, creates refunds and reads payment intents on the connected account. A least-privilege `rk_test_` cannot be assumed to cover the undocumented `payment_pages` call; it would have to be proven by a trial run that costs an approval. Recommendation: a sandbox `sk_test_` key (TEST mode only, throwaway sandbox, expiry/rotation right after the run).
3. **It needs a running app and database, not just API calls.** The runner starts a LOCAL Supabase (`supabase start`, public demo keys, all repo migrations applied) and the Next app (`next build && next start`, per the local-E2E rule) on the runner. No hosted Supabase (DEV or PROD) credential and no production secret is involved.

## 2. Runner design (one job, one approval)
- Trigger: `workflow_dispatch` only. Environment `competition-stripe-test` (owner is the only required reviewer, "allow administrators to bypass" OFF, deployment branches = `release/website-embeds` only until `main` carries the line). Missing-environment auto-creation is unprotected, so the environment must exist BEFORE the workflow file lands.
- Guards (fail closed): repo and ref pinned; dispatched sha must equal the tip of the pinned branch; Stripe account ids pinned (platform `acct_1UZ320IPJs53nwt7`, connected `acct_1UZibNRCFiaIzL1V`, both TEST); first request is `GET /v1/account` and `GET /v1/balance` with the key: refuse unless `livemode=false`, the platform id equals the pin, and the connected account is read and its `charges_enabled` / `card_payments` status RECORDED (not required: see section 3a); then a canary: create and immediately expire one $1 Checkout Session on the connected account with an application fee, abort in seconds with a clear message if Stripe refuses it; refuse any key that is not `sk_test_`/`rk_test_`.
- Local stack: `supabase start` + apply migrations, seed through the harness fixtures only; `STRIPE_SECRET_KEY` and a locally generated `STRIPE_CONNECT_WEBHOOK_SECRET`/`STRIPE_WEBHOOK_SECRET` are passed to the app and Playwright processes as env, never echoed (GitHub masks the key; the job also unsets it for every step that does not need it).
- Webhooks: the harness today expects `stripe listen --forward-connect-to`. The draft instead uses a small **event relay** (new, reviewed code, `scripts/qa/cf1-stripe-relay.ts`, to be written): it polls `events.list` on the connected account and POSTs each authentic Stripe event, signed with the local secret, to `/api/payments/webhook`. Reasons: no Stripe CLI binary to pin, only Events-read on the key, and it gives deterministic **duplicate and out-of-order replay** for the failure-handling tests. The app's real signature verification and handlers run unchanged.
- Flags: `NEXT_PUBLIC_COMPETITION_REGISTRATION_ENABLED=true` and `E2E_COMPETITION_REGISTRATION_ENABLED=true` on the runner's LOCAL app only. Production flags are untouched.
- Evidence: Playwright JSON + traces + the harness evidence pack are written outside the checkout and encrypted with the existing evidence key; the public log shows only pass/fail counts and masked ids. Concurrency group, 60-minute timeout, one run per approval.
- Call budget (corrected 2026-11-19): a total cap across the app, the spec and the relay is NOT enforceable without app changes, so none is claimed. What is enforced: the relay's own request budget (`CF1_RELAY_MAX_POLLS`, default 1,500 `events.list` polls, about 75 minutes) and the 60-minute job timeout. Expected volume: roughly 300-600 requests in total (Q1 spec ~150-250, failure/settlement spec ~100-150, relay polling ~1,200 reads at a 3 s interval over a 60-minute worst case). All are TEST-mode requests on the sandbox, listed in the sandbox Developers > Logs for the owner's glance.
- Written 2026-11-19 (draft PR to `release/website-embeds`): the relay (`src/lib/e2e/stripeRelay.ts`, `scripts/qa/cf1-stripe-relay.ts`, 12 unit tests that need no Stripe account (passing), signature verified by the app's real `verifyStripeWebhook`) and the failure/settlement spec (`e2e/tests/competition-stripe-failure-settlement.spec.ts`, setup + F1-F4 + S1-S2, never run against Stripe).

## 3a. The restricted connected account (owner report 2026-11-19)
Facts. The account was created by provisioning with only capabilities requested and Stripe-collected requirements (`controller.requirement_collection=stripe`, Express dashboard), and was never onboarded; D24 only needed draft invoices. Restricted / payments paused / payouts paused / outstanding requirements is the normal state of such an account. It is not a Stripe penalty, and in a sandbox it is satisfied with Stripe's published test data, never real documents (Stripe, "Testing Stripe Connect" and "Testing account verification", fetched 2026-11-19). Because Stripe collects the requirements, only the account holder (the sandbox owner, through hosted onboarding or the Dashboard) can fill them; the platform API cannot, and the runner must not try.
What actually gates the run: (1) DanceFlow's own checkout gate reads `stripe_connect_charges_enabled` from the studio row, which the E2E fixture sets true locally (`competitionFullEventFixture.ts`), so the app does not consult Stripe's flag; (2) Stripe itself: its sandbox docs say sandboxes "might not enforce some capabilities", for example "a connected account might accept card payments, including through Checkout, before its `card_payments` capability becomes active". That is supportive but not a guarantee for the undocumented payment-page confirm call or for application fees; D24 proved only draft invoices on this account. (3) Stripe blocks new platforms from direct charges on LEGACY Express/Custom accounts; this account is controller-model, so that block should not apply (D24 provisioning doc, section 10).
Smallest safe remediation, in order:
- R0 (default, no Stripe change, no authorization beyond the run itself): the runner's canary above. If Stripe accepts the $1 session, the account is good enough for TEST acceptance and nothing else is needed. If it refuses, the run aborts in seconds, before any registration, at the cost of one approval and part of the key's 24 hours.
- R1 (only if the canary refuses; needs the owner's explicit go-ahead, owner performs it): complete the SAME account's sandbox onboarding with Stripe's test values. No new account, no fee, no real verification, no change to DanceFlow. Owner input needed first (optional now): the seven requirement NAMES from the Dashboard (field names only, no data) so each can be mapped. Values documented by Stripe for test mode: individual DOB 1901-01-01; ID number 000000000 (SSN last 4: 0000); address line1 `address_full_match` with a plausible city, state and ZIP; phone 0000000000 (SMS code 000-000); company tax ID 000000000; business URL https://accessible.stripe.com; US test bank routing 110000000 with account 000999999991; ToS acceptance. Whether the hosted test-mode form also offers a skip or autofill option was not confirmed from the pages read.
- R2 (not recommended; separate authorization): a new test connected account. Costs a one-shot provisioning key and run, and repeats the same onboarding question.
Not done and not asked: no account created, no verification submitted, nothing enabled, no fee, no secret configured.
