## 7. Cutover design for R2 (from `cf1-r2/CUTOVER.md`, reviewed)

Preconditions (hard): competition refund freeze from R2 SQL apply until about one hour after the R2 app is live (staff refund flow suspended, no dashboard competition refunds); pre-cutover read-only checks on the target (impact count must be 0 refunded competition payments, or the owner dispositions them); every `event_payments` PaymentIntent equals its order's. Sequence: apply R2 and the gate in one step, confirm both, deploy the R2 app, verify refund event ingestion, ledger consistency and authorization, then run the read-only reconciliation (`cutover_reconciliation.sql`, `cutover_failed_events.sql`) across the whole window. Replay of a failed event needs Stripe redelivery or a manual resend (`payment_provider_events` stores no payload and no refund id): both are separate Stripe authorizations. Missing evidence never becomes an automatic release: RB3/RB3R stay `entry_refund_evidence_missing`. Residual risks: a refund that succeeds then reverses inside the interval, retry-window exhaustion, the seconds between the R2 and gate files if applied as two steps, a gate/new-app classification mismatch (reconciliation check added), logging of the gate's 42501 as a 403. **If the freeze cannot be guaranteed, the R2 deployment is NO-GO.**
