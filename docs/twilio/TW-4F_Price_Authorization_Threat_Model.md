# TW-4F price authorization: design, trust boundary and threat model (D4-2)

Status 2026-10-31. Git only (migration `20270210100000_twilio_price_owner_authorization.sql`, stacked on D4-1 `20270210090000`); nothing is applied to any hosted database. **No residual risk below is accepted.** Each remaining exposure is a named OPEN OWNER DECISION or a named blocker; only the owner can accept a risk. Monitoring and alerting for this surface are built by the monitoring workstream (PR 391; runbook `docs/twilio/TW-4F_Price_Monitoring_Runbook.md`); this document defines the events and interfaces it consumes.

Related: `TW-4F_Price_Dual_Control.md` (D4-1 rule, runbooks, rollback), `TW-4F_Price_Dual_Control_Impersonation_Design.md` (earlier analysis), `TW-4F_Price_Limits_Proposal.md` (unapproved limits), `TW-4F_Price_Monitoring_Runbook.md` (PR 391, alerting).

## 1. The model
**Single-owner high-assurance mode (initial).** One platform owner, no second administrator, no owner-override flag, no shared or duplicate account.
1. Propose: an authenticated session, aal2, a TOTP authentication in the last 15 minutes (`tw4_price_propose`). The proposal is bound to the active price it was made against.
2. Cooling-off: a MANDATORY 24 hours (config value, row CHECK `cooling_until >= requested_at + 24 h`; it can be raised, never lowered below 24 h, by owner-level migration only). Expiry never publishes anything: a proposal whose authorization window passes stays pending and can no longer be authorized.
3. Final authorization: a SEPARATE authenticated session (its `session_id` must differ from the proposer's and from nothing else the proposer holds) AND a WebAuthn assertion by a registered key whose flags show a device-bound authenticator (user presence and verification set; backup-eligible or backed-up credentials, i.e. synced passkeys, are rejected unless the owner explicitly allows them in the configuration). This is a FLAG check, not an attestation: the database cannot prove the key is a hardware token, only that the authenticator says it is not synced (`tw4_price_authz_begin` / `tw4_price_authz_finish`).
4. The assertion is cryptographically bound to the exact proposal: the WebAuthn challenge is `sha256(canonical_hash || nonce)`. The canonical hash covers scope, price kind, old customer/provider values, new values, description, proposal version, request id, approval mode, cooling-off end and expiry. The nonce is database generated, 256 bits, single use, bound to the request, the issuing user and the issuing session, and expires in 5 minutes (config).
5. Revising a proposal (`tw4_price_revise`) invalidates it, every challenge issued for it and any signature over it, and starts a new version with a fresh cooling-off.
6. Publication happens only inside `tw4_price_authz_finish`, after the assertion verifies, under the per-kind lock; the price-list insert guard (ENABLE ALWAYS) additionally requires the approved in-flight request with the hardware-key evidence, a finished cooling-off and no suspension.

**Team mode (optional, not required at launch).** The protected configuration can be set to `team` by an owner-level migration: two distinct registered human approvers, each in their own aal2 session, no cooling-off, no hardware key (the D4-1 logic, unchanged). A request records its mode; an owner-mode request cannot be approved through the team path and vice versa.

## 2. Trust boundary (spike result and decision)
**Option A, chosen: the assertion is verified inside Postgres.** ECDSA P-256 over `numeric` in plpgsql (`_tw4price_p256_verify`), SHA-256 from core. Spike evidence: the implementation verifies signatures produced by Node's crypto (`localStack.priceauth` PA-01 runs 14 verifications and every tampering: other message, other key, altered s, r = s = 0, off-curve key), the whole WebAuthn parse (client data, origin, RP id hash, UP and UV flags, sign counter) is in SQL, and a full ceremony finishes in well under the test timeouts on a loaded host. No extension, no external service.
**Option B (a separate verifier service) was not chosen**: it would add a second trust anchor, a network dependency and a credential that has to live somewhere that the modelled compromised authority could reach unless it is isolated like the database owner is; Option A needs none of that.
What the boundary now is, honestly:
- **Credential enrollment, challenge generation, verification and publication are in the database and use no GoTrue token, no JWT claim and no service_role key for their authority.** The authority is the private key in the owner's authenticator. `authenticated` EXECUTE exists only so the owner's browser can reach the functions; the functions refuse anything that is not role `authenticated` aal2 + TOTP, and then still need the signature. `service_role` has EXECUTE on none of them.
- The relying party (`rp_id`, allowed origins) and the first credential are set by an owner-level bootstrap (`_tw4price_bootstrap`, no grants, works once). There is no application path to the bootstrap.
- Enrolling a credential needs an assertion from an EXISTING credential over the exact new key, role and label, plus a proof of possession from the NEW credential over the same challenge. Revoking needs an assertion from a DIFFERENT credential and never removes the last one. At most 3 credentials are active; one primary, spares. Every change is in the immutable audit and emitted to the monitoring feed.
- **What this does not claim**: an attacker who controls the database owner (DDL) is outside the boundary (section 4). A recovery path for a LOST authenticator (every credential gone) is NOT implemented: it is an owner-level, ticketed migration step that re-bootstraps; it must be delayed and alerting, and its design (a 7-day delay, an email to the owner, an event `credential_compromise_reported`) is a named open item, not a shipped control. Until it exists, losing all credentials means price changes stop (fail closed).

## 3. Mode, configuration and weakening protection
`studio_sms_price_auth_config` is a single row with ENABLE ALWAYS guards. Mode, cooling-off hours, authorization window, challenge lifetime, relying party and origins change only by an owner-level migration (a visible `alter table ... disable trigger`), never through a function, an API role or `service_role`; the row CHECKs bound them (cooling-off at least 24 hours). The approver registry, the credential registry and the limits table have no grants. Weakening any protection therefore needs DDL: the ceremony does not edit configuration (a ceremony-gated configuration change is deferred; migration-only satisfies the requirement and is simpler to review). The 8 limit rows stay unapproved and unenforced.

## 4. Attacker classes
Legend: **PREVENTED** (the attack cannot succeed given the stated boundary, with a test), **DETECTED-ONLY** (it can succeed and is detected), **NOT COVERED**. None of the residuals is accepted.

| Attacker | Result | Evidence and honest residual |
|---|---|---|
| `service_role` key holder | **PREVENTED** for price publication | No EXECUTE on any price function (except the refusing `tw4_price_set` and the read-only verifier and feed); no table grants; cannot write the registry, credentials, challenges, audit or configuration. Tests PA-07, PD-26, RT-06. Residual: service_role can still write `profiles` and other tables; those no longer grant price authority (registry + hardware key). It can DENY service (freeze is not available to it, but it can break unrelated flows). |
| JWT-signing secret holder / forged claims | **PREVENTED** for publication, **DETECTED-ONLY** for proposals | A forged aal2 token for a registered administrator can create proposals (and revise or freeze), but cannot publish: finishing needs a signature by a registered hardware key, which the secret does not provide (PA-07 forged claims). Proposals are visible in the audit and the 24 h cooling-off gives the owner time to see them; alerting is the monitoring workstream's. |
| GoTrue admin API (create users, reset passwords, mint sessions) | **PREVENTED** for publication, **DETECTED-ONLY** for proposals | Same as above. It can also create a "second session"; that satisfies only the session check. Residual: the owner must notice proposals he did not make (monitoring: `proposed` audit events, `approver_*` events). |
| MFA factor reset or enrolment of an attacker's TOTP for the owner | **PREVENTED** for publication, **DETECTED-ONLY** for proposals | TOTP is only a precondition; the hardware key is the authority. A GoTrue-level factor change is observable (`mfa_factor_changed` is an event kind the monitoring workstream emits from the Auth side; this migration cannot see Auth tables' changes). |
| Privileged credential misuse (an operator with a legitimate privileged credential such as the migration runner or a DBA login) | **NOT COVERED** beyond detection | Owner-level DDL can disable triggers, edit the registry, replace functions or insert rows, and the guard flags (`tw4.pricedual_write`, `tw4.priceauth_write`) are ordinary session settings that owner-level DML can set: this is **DETECTED-ONLY** by the verifier (`price_unattested`, tested with forged rows), NOT prevented, and is not "visible DDL" (a `set_config` plus DML leaves no DDL). The ENABLE ALWAYS triggers stop functions, roles and replica-mode statements; the fingerprint probes show a disabled trigger. Residual: a DB owner can still publish and then repair evidence; only separation of the owner credential from every daily-use credential and the monitoring digest (PR 391) reduce it. **OPEN OWNER DECISION: how the owner credential is held and who can use it.** |
| DB owner / DDL | **NOT COVERED** | Out of the model by construction; detection as above. |
| Credential replacement (add a key) | **DELAYED and CANCELLABLE with a hardware key; detected; NOT prevented** | Enrolment is authorized by an existing primary or spare key and is only a PENDING change: it takes effect after `credential_delay_hours` (24 to 168) and never while publication is suspended. The new key proves possession; a duplicate public key (revoked ones included) is refused; at most 3 credentials (primary, spare, recovery) are ever active, one primary and one recovery. A pending change whose SIGNER was revoked is VOID (a revocation voids everything the key signed, and apply re-checks under the same credential lock; race-tested, PA-18, PA-21). A primary or spare key can cancel a pending enrolment with a hardware assertion bound to that change; a bare session cannot, and neither can the recovery key. Events `credential_replaced` (status pending / applied / cancelled / voided) are emitted. It depends on the owner or monitoring noticing within the delay. |
| Credential revocation / eviction (an attacker with a session and one ordinary key tries to cut the owner off) | **A primary or spare key can revoke ONLY ITSELF; evicting another ordinary key needs the OFFLINE RECOVERY credential. A stolen ordinary key can no longer evict anything but itself.** Revocation stays **IMMEDIATE and FINAL** | OWNER POLICY (2026-11): `tw4_price_cred_revoke` accepts (a) **self-revocation**: the target signs its own revocation (ceremony purpose `revoke`, the only allowed signer is the target; immediate, not cancellable, voids what the key signed); (b) **eviction**: ONLY the recovery credential can revoke another ordinary key (ceremony purpose `revoke_other`, challenge purpose `recover_revoke_key`): the assertion is bound (hash) to the exact target credential record and to the challenge expiry, uses a single-use nonce, and the role check inside the assertion makes it the recovery key's act only; it is audited (`credential_revoked` with `via`, `recovery_used` with `action = revoke_ordinary_key`) and raised as the critical event `credential_recovery_used` (tolerant of a monitoring outage: the failed emit is audited and replayable); (c) the recovery credential is retired only by itself (R3-1). The last active signing credential is never revoked, by anyone, so eviction by the recovery key cannot leave pricing without a signer. The recovery credential is NOT a universal bypass: it cannot publish, authorize, approve, thaw, cancel an ordinary enrolment or enrol (except through `recovery_enroll`, delayed 72 h and louder than anything else), and it cannot evict the recovery key. Self-revocation stays immediate on purpose: a lost or suspect key must be retirable at once. What this closes: the earlier RESIDUAL where a stolen primary plus a session cut the owner off from the spare at once (PA-34, PA-35, RTA-11). What remains: a stolen ordinary key can still be used to PUBLISH after the cooling-off until the owner evicts it with the recovery key or freezes; the freeze is immediate and ordinary. Tests: stolen primary revokes the spare directly (refused), by a crafted recovery-type ceremony (refused), a recovery assertion replayed for another target (refused), the recovery evicts once and a replay is refused, races (recovery-revoke vs apply, vs the target's self-revoke, two simultaneous recovery assertions: PA-36), the last-credential rule and the three-credential scenario (PA-35). |
| Lost, stolen or compromised authenticators / the recovery path | **BOUNDED; recovery credential custody is the control; residuals are OPEN OWNER DECISIONS (none accepted)** | The OFFLINE RECOVERY credential (role `recovery`, at most one active, installed only by the owner-level step) can ONLY (a) freeze (`tw4_price_recovery_freeze`), (b) start the re-enrolment of a new primary (`tw4_price_recovery_enroll`), (c) cancel that recovery enrolment, and (d) evict an ordinary key (`recover_revoke_key`, immediate, bound to the exact target, never the last ordinary key), and (e) retire itself. It can never publish, authorize, enrol (except `recovery_enroll`), thaw, or change a mode, limit or configuration: the role is enforced inside the assertion check, not in the callers. **What the rules now PREVENT (PA-26, PA-27, browser harness):** an ordinary key (primary, spare, or a stolen one) cannot revoke or replace the recovery key (only the recovery key can retire itself, and NO ordinary key can enrol a recovery key at all, and a primary or spare key can no longer evict the other ordinary key (only the recovery key can): it is installed only by the owner-level runbook step, which refuses while one is active or a recovery is in progress); after a recovery freeze or while a recovery enrolment is pending, ordinary keys cannot thaw, enrol, revoke or apply anything, cannot cancel the recovery enrolment (only the recovery key can), and publication stays suspended (a pending recovery enrolment suspends pricing by itself, a recovery freeze sets a hold only the recovery key clears). Completion is unchanged: the delay is `recovery_delay_hours` (default 168, never under 72 by CHECK), `credential_recovery_used` and `recovery_enrollment_started` are critical events, every active credential including the single-use recovery key is revoked and the new key is the only primary (it may lift the freeze). It works under a freeze and with monitoring down. No administrator bypass exists. **Consequences, stated honestly:** (1) a MISTAKEN recovery freeze or recovery enrolment can be ended only by the recovery key (cancel, which clears the hold; the freeze stays and an ordinary key then thaws); if the recovery key is LOST the hold ends only when a recovery completes or by owner-level DDL, so lose neither the recovery key nor the habit of using the ordinary freeze (`tw4_price_freeze`, which ordinary keys can lift) for non-recovery cases. (2) A stolen recovery key plus a session can freeze pricing and block every ordinary key until the owner completes a recovery (a denial of service, not a publication path); the owner's remedy is to start and complete a recovery with the remaining recovery key custody, which is why it is kept offline. (3) A stolen recovery key AND session AND an owner who never notices the critical alerts for the whole delay completes a takeover. OPEN OWNER DECISIONS: whether the recovery key should need a second person; whether a mistaken recovery freeze needs a shorter owner-level path. |
| Cancelling a pending change (remediation authority) | **BOUNDED** | Only pending ENROLMENTS and recovery enrolments exist, so only they can be cancelled; a hardware assertion by an active primary or spare key bound to the exact change is required (PA-22); a revocation is never cancellable. Cancelling can never publish a price or weaken a policy. |
| Old authenticator session (a session whose TOTP code is old, or a stolen long-lived session) | **PREVENTED for every sensitive ceremony; emergency stops stay open** | OWNER POLICY: aal2 alone is not enough. `_tw4price_session_actor('recent')` requires the TOTP entry of the JWT `amr` claim (`{"method":"totp","timestamp":<unix seconds>}`, written by the local GoTrue when a code is verified) to be at most `fresh_mfa_max_age_seconds` old (default 600 = 10 minutes, CHECK 60..3600, changes only by owner-level DDL like every other configuration value). A missing, string-form, malformed or future timestamp FAILS CLOSED. Tier `recent` covers propose, revise, approve, authorize begin and finish, credential begin / enrol / revoke / apply / cancel, thaw and the recovery enrolment. `tw4_price_freeze`, `tw4_price_report_compromise` and the recovery freeze (its begin and its signed finish) keep plain aal2 so an emergency stop is never blocked by an old code. The Next app uses the same window (`fresh` tier, 10 minutes) and sends a stale session to the existing step-up page (`/platform-mfa/challenge?stepup=1`). **Observed GoTrue behavior (RTA-10, local GoTrue):** a refresh-token refresh keeps the ORIGINAL amr timestamp and session id (it does not freshen); re-verifying a code on the same session (`factors/<id>/challenge` + `verify`) issues a token with a newer TOTP timestamp, which is what the step-up page does. A WebAuthn transaction approval is separate and unchanged. |
| Credential properties at enrolment (synced passkey, no user verification, wrong origin) | **VERIFIED, fail closed; hardware compatibility NOT claimed** | A key that arrives by ceremony proves the required properties with its own possession assertion (`_tw4price_check_assertion`): user presence and user VERIFICATION flags set, backup-eligible (BE) and backed-up (BS) flags clear unless the owner's migration sets `allow_backup_eligible` (default `false` for primary, spare AND recovery), relying party id hash, exact origin, `webauthn.get` type, challenge, sign counter increasing when the authenticator counts, and a valid P-256 (ES256) signature. The signing key's assertion is checked the same way. A key that arrives WITHOUT a ceremony (bootstrap primary, installed recovery key) has no proof until the owner-level `_tw4price_attest_begin` / `_tw4price_attest_finish` runs an assertion by that key through the same checks and stamps `proof_verified_at`; the hosted preflight FAILS while any active credential has none. There is no attestation statement (`attestation: none`): the flags and the origin are the strongest evidence an assertion carries, so a software authenticator that sets the right flags cannot be told from a hardware token in the database. Discoverable credentials (resident keys) are not required. PA-38 tests each refusal with the software authenticator; real YubiKey / Titan-class compatibility is for the owner's later pass: see `TW-4F_Price_Hardware_Authenticator_Protocol.md`. |
| Two compromised registered keys (primary and spare) | **NOT PREVENTED (no universal two-signature revoke)** | OWNER DECISION: no two-signature revoke. An attacker who holds both ordinary keys and a session can enrol (delayed, cancellable) and retire their own keys within the delays, but cannot evict the recovery key; the owner's recovery key evicts them. Controls: the 24 h enrolment delay and cancel, immediate events, the freeze, and the offline recovery key, which is expected to be the one credential the attacker does not hold. |
| Two compromised approvers in Team Mode
| Owner device or session theft | **DETECTED-ONLY** / partly **PREVENTED** | A stolen laptop session gets a proposal at most (aal2, TOTP) and cannot finish without the hardware key and a second session. A stolen hardware key alone cannot propose (no session). Both together, plus the 24 h cooling-off, publish. During the wait, the owner CAN interrupt only if he notices: freeze needs only a session, rejecting or revising needs a session, cancelling a credential change needs a key. Nothing alerts him in this migration beyond the emitted events (`price_authorization_started`, `pricing_suspended`, `credential_change_pending`); alert delivery is the monitoring workstream's and is not built here. Residual: the window relies on the owner noticing. |
| Phishing / real-time relay of a WebAuthn assertion | **PREVENTED** (origin) / residual on the owner | The assertion is bound to the relying party id and exact allowed origins (a look-alike origin is rejected, PA-04) and to the exact transaction hash. A relay to the REAL origin would need the attacker to control a page served from the real origin. The owner must read the transaction summary on the approval screen (kind, old and new value); the UI displays it from the database, not from the page that started the ceremony. |
| Proposal tampering / TOCTOU | **PREVENTED** | The hash covers every field; the proposal is immutable (binding trigger, also in replica mode); a revision invalidates old challenges; a signature over one version never authorizes another (PA-05); a changed active price invalidates the proposal (stale base). |
| Replay | **PREVENTED** (nonce) / counter **DETECTED-ONLY** | A single-use nonce is consumed with the signature for every purpose (publication, enrolment, revocation, thaw). The sign counter must increase for authenticators that implement it and every valid assertion advances the stored counter; a regression is recorded as `integrity_failure` and emits `price_integrity_failure`. Authenticators whose counter stays 0 get replay protection from the nonce only; the counter cannot detect a cloned key for them. A finished request is final; concurrent identical submissions publish once (PA-03, PA-11). |
| Cooling-off bypass | **PREVENTED** | Row CHECK; no function or replica-mode owner statement shortens it; no challenge is issued before it ends; expiry never publishes (PA-06). |
| Mode-switch / configuration attacks | **PREVENTED** for functions, roles and replica-mode statements; **NOT COVERED** for owner DDL | PA-08. |
| Freeze abuse | **PREVENTED** as a publication path | Freeze can only suspend (PA-10); lifting needs a hardware key that was active when the suspension began (the local `frozen_at`; for a monitoring-only suspension every active key qualifies because credential changes are never applied while suspended). Eligibility never reads the monitoring table's timestamps (PA-24), so a forged `recorded_at` cannot wedge the thaw. The thaw is bound to the suspension it lifts (hash includes `frozen_at` and the monitoring suspension sequence); a `pricing_resumed` row in the monitoring table lifts nothing. A hostile freeze is a denial of service by a compromised session; the owner thaws with the key. |
| Compliance side effects | **PREVENTED** | STOP / START / HELP processing is independent of prepaid balance, price publication and any suspension (`localStack.tw4inbound` D2 and D2b). |
| Blind signing: compromised administrator origin (XSS, malicious deploy of the admin page) showing a different summary than it signs | **NOT COVERED** | The assertion signs the database's hash, the page is only a display. If the admin origin itself is compromised, the owner can be shown a false summary and sign an attacker's proposal. Mitigation (not prevention): `tw4_price_authz_begin` emits `price_authorization_started` with a 16-hex fingerprint of the hash so a second channel (monitoring) can show the owner what the database was asked to authorize, and the 24 h cooling-off lets him compare. Delivery of that second-channel message is not built in this PR. |
| Authenticator is not hardware (software or synced passkey) | **PREVENTED for synced credentials by flags; NOT COVERED for software authenticators** | Backup-eligible and backed-up credentials are rejected (PA-04). No attestation is checked, so a software authenticator that reports device-bound flags cannot be distinguished. |
| Authorization gate refusals | **DETECTED (registered sessions only), rate-capped** | The registry check comes BEFORE any audit write in begin and finish: a non-administrator, even with an aal2 session, gets an error and NO row (PA-23). A refused attempt by a REGISTERED administrator's session is committed to the audit (`gate_refused`) and returned as an answer; routine refusal rows (`gate_refused`, `assertion_rejected`) are capped at 100 per actor, event and hour so a hostile registered session cannot flood the audit (rows beyond the cap are not written; the refusal itself is unchanged). Integrity, publication, credential and freeze events are never capped. |
| Emergency actions during a monitoring outage | **PREVENTED from being blocked** | Freeze, compromise report, hardware-key cancel and thaw commit their audit row and TOLERATE a failed emit (the emit failure is itself recorded as an `emit_failed` audit row), also when `monitoring_expected` is set and the events table is missing; an integrity failure is audited the same way (PA-20). Actions that open a risk (propose, begin, enrol, revoke, apply) keep the strict emit and FAIL CLOSED with TW046 during an outage, so the outage never lets anything new through. The outage does not move any `effective_at`: a pending credential change is applied (strictly) once monitoring is back or `monitoring_expected` is cleared by the owner. |

## 5. Interfaces and events (for the monitoring workstream)
`tw4_price_verify(p_since)` returns `ok`, `anomalies`, `checked_at` with codes `price_unattested`, `request_anomaly`, `several_active_prices` (unchanged). `tw4_price_audit_feed(after_id, limit)` (service_role) returns the immutable local audit. Security events are inserted into `studio_sms_price_security_events` (created by the monitoring migration `20270210110000`, which sorts AFTER this one, so every emit is conditional on the table existing) from owner-level SECURITY DEFINER functions: `credential_replaced` (detail.status pending / applied / cancelled / voided), `credential_revocation_accepted`, `credential_recovery_used` (action recover_freeze, recovery_enroll, recovery_completed; critical), `recovery_enrollment_started` (critical), `event_emit_failed` (critical), `price_authorization_started` (second channel), `price_integrity_failure` (counter regression), `approver_added`, `approver_removed`, `approver_registry_changed` (registry triggers), `pricing_suspended` (freeze, compromise report), `pricing_resumed` (hardware-key thaw), `credential_compromise_reported`. `mfa_factor_changed` and `approver_credential_replaced` originate on the Auth side and are emitted by the monitoring workstream. No secret is ever in a detail: no key, credential id, challenge, nonce or token. If the LATEST suspension event in that table is `pricing_suspended`, propose, approve, begin and finish are refused until the hardware-key thaw (which writes `pricing_resumed`) follows; when the monitoring table is expected (`monitoring_expected` in the configuration) and missing, an emit fails loudly (TW046) instead of dropping the event.

**Emit failures are recoverable.** A failed emit is recorded as an immutable `emit_failed` audit row that keeps the event kind, subject and payload (no secrets). The monitoring job lists the unacknowledged ones (`tw4_price_emit_failures`) and replays them (`tw4_price_emit_replay`, service_role only; it re-emits the original event marked with the audit id, adds an `event_emit_failed` event, appends one acknowledgement row and never changes the audit row; it does nothing while the events table is missing, so it never acknowledges into the void). `_tw4price_prune` never removes `emit_failed` rows or their acknowledgements.

**Integration with the monitoring migration (#391, 20270210110000).** When `_tw4pricemon_emit_event` exists every emit goes through it (kind validated, seq assigned gapless by its trigger, timestamps forced by the database); this schema reads only `seq` and `kind` of that table, never a timestamp. A monitoring outage can never authorize a change: begin, propose-side calls, enrol, revoke and apply use the strict emit and fail closed; freeze, recovery freeze, cancel, thaw and integrity failures are tolerant. `tw4_price_monitor_status` is informational only and is not consulted. Event kinds this schema emits that the monitor does not classify yet (the monitor reports them as unknown, warning): `price_authorization_started`, `price_integrity_failure`, `price_proposed`. `tw4_price_propose` now emits `price_proposed` (tolerant) and is refused with TW046 when `monitoring_expected` is set and the events table is missing. A replayed `pricing_suspended` that no longer holds is delivered as a stale `event_emit_failed` (informational) and never re-suspends pricing. R3-6 (every emitter serialises on the monitor's event-sequence lock, reachable only by a registered administrator session, held for milliseconds) is theoretical and documented only.

**Custody procedure: THREE hardware credentials, three places.** (1) PRIMARY hardware key: the owner's daily key, bootstrapped by the owner-level runbook step (`_tw4price_bootstrap_with_recovery` installs it together with the recovery key in ONE transaction, so the system never runs with a primary and no recovery key). (2) SPARE hardware key: a second, device-bound key enrolled by the primary through the ceremony (24 h delay, cancellable), kept OFFLINE in a different physical place (safe), used only when the primary is lost: the spare is the one the owner reaches for first. (3) RECOVERY key: a third, SEPARATELY PROTECTED hardware key (own custody, own safe or deposit box, never carried, never used except to freeze or recover); it is installed ONLY by the owner-level step (`_tw4price_install_recovery`: at bootstrap, or again after a completed recovery or the recovery key's own retirement) and NEVER through an ordinary ceremony, because a stolen ordinary key could otherwise install its own. Each recovery-key use is a critical alert: after any unexpected one, cancel the recovery enrolment with the recovery key (or freeze). After a recovery completes: enrol a new spare, have the owner-level step install a new recovery key, and store it offline. Lost primary or spare: revoke it (immediate and final) with the other key and enrol a replacement. All ordinary keys lost or stolen: freeze (any session or the recovery key), start the recovery from the recovery key, wait out the delay.

**Hardware-bound credentials are the production requirement.** `allow_backup_eligible` is false by default: any assertion whose authenticator data shows BE (backup eligible) or BS (backed up), i.e. a synced passkey, is refused at enrolment (signer and new key) and at EVERY later assertion, including a key that was enrolled without the flag and later reports it (the flags are read from each assertion, not remembered; a flip is a plain refusal with an `assertion_rejected` audit row, PA-30). Switching the owner-level opt-in on admits synced keys; switching it off refuses them again at once, without grandfathering. Because there is no attestation, the flags are the strongest evidence of device binding the database has: use FIDO2 security keys or other non-backup-eligible authenticators for the primary, the spare and the recovery key, never a cloud-synced passkey.

**Session and sign-out semantics.** A GoTrue access token is a stateless JWT and survives a sign-out until it expires. The database therefore checks, in `_tw4price_session_actor`, that the session named by the token's `session_id` (a uuid) still exists in `auth.sessions`: a signed-out or administratively revoked session is refused at once (real-token tests RT-10 and RTA-04). A claim that is not a uuid cannot name a session and is left to the other checks (the synthetic claims of the local suites). A factor removed mid-flight: the token already issued keeps its aal2 claim until its expiry (at most the token lifetime), but its refresh is aal1 and is refused everywhere (RTA-05). HOSTED PREFLIGHT: the function owner must be able to read `auth.sessions` (`select 1 from auth.sessions limit 1` as that role), or every pricing call fails closed.

**Trust-boundary risks that remain (not downgraded).** (a) An attacker with a session AND ONE stolen ordinary key can, instantly, revoke the other ordinary key, publish after the 24 h cooling-off with the stolen key, and enrol further ordinary keys (24 h delay): the stolen ordinary key is the dominant risk, the recovery path and the freeze are the remedy, not a prevention. (b) OUT OF THE DATABASE: a compromised session can change the owner's password, TOTP or MFA factors in GoTrue, locking the owner out of aal2 (so out of the recovery ceremony, which still needs a registered administrator session). OBSERVED against the local GoTrue in its default configuration (RTA-05, RTA-09): a stolen PASSWORD alone (a new aal1 session of a user with a verified factor) cannot enrol a factor (403), cannot remove the verified factor (422) and cannot change the password (401); an AAL2 session (after the TOTP) CAN change the password with no reauthentication nonce (200) and CAN remove its factor, so the out-of-database risk needs a compromised aal2 session, not just the password. Mitigations to configure in GoTrue and verify on the hosted project (not enforced by this schema): secure password change requiring a fresh reauthentication (GOTRUE_SECURITY_UPDATE_PASSWORD_REQUIRE_REAUTHENTICATION), MFA removal requiring reauthentication, short JWT expiry, and notification emails on credential changes. The database-side session check (previous paragraph) makes a sign-out or an administrative session revocation effective at once. (c) A compromised admin origin can still show false summaries (blind signing, see above). (d) No attestation; no real hardware token in the local runs.

**Owner decisions still open, with recommended options.** (1) ADMIT FEWER THAN TWO ORDINARY KEYS TO BE LEFT BY ONE REVOKE (eviction guard): today the stolen key can revoke every other ordinary key at once. Recommended: revoking an ordinary key that would leave fewer than two ordinary keys takes a 24 h delay cancellable by the target key or the recovery key, or needs the recovery key's co-signature; exact owner window today: zero (immediate). Not implemented in this slice because it changes the immediate-revocation decision. (2) ALERT RATE LIMIT: `tw4_price_authz_begin` emits one `price_authorization_started` event and audit rows per call without a rate limit (a flood did not block the freeze: 830 ms during a 60-call flood). Recommended: cap the events per session per hour and alert on the cap; exact owner window today: unlimited events, the freeze stays available. (3) Whether the recovery key should need a second person, and whether a mistaken recovery freeze needs a shorter path (stated above).

**Retention and cleanup.** Challenge rows are single-use and expire in `challenge_ttl_seconds`. The audit is evidence. `_tw4price_prune(interval)` (owner level only, no grant to any API role, minimum retention 30 days, default 90) removes used or long-expired challenges and routine audit rows (`challenge_issued`, `gate_refused`, `assertion_rejected`) older than the interval; the row guard itself refuses to delete anything else, even with the prune flag set, so integrity, publication, credential, freeze and emit-failure events are never pruned (PA-23). Pruning is not scheduled yet: running it is an owner-level maintenance step.

## 6. Credential isolation for the pricing path only (bounded; the 199 `createAdminClient` call sites are untouched)
The pricing path already holds no service-role key: the actions and panel use the administrator's own user-scoped client, and the functions are not executable by service_role. Remaining bounded steps (hosted configuration, owner action, not done here): a dedicated Postgres login role that holds EXECUTE on `tw4_price_verify` and `tw4_price_audit_feed` only, for the monitoring job; the owner credential used for migrations and the approver registry kept outside the application's secret scopes; no price code path in any route that reads `SUPABASE_SERVICE_ROLE_KEY`.

## 7. What is implemented, what is not
Implemented and tested locally (Docker, software authenticators, real GoTrue tokens): sections 1 to 5 except the items below. Server actions: propose / approve / reject (D4-1); begin / finish / revise / freeze / report-compromise; credential begin / enrol / revoke / apply / cancel / pending and thaw (all AAL2-guarded, registered in the assurance registry), with client components (`PriceAuthorize`, `PriceCredentials`) that drive `navigator.credentials`; unit tests mock the database and the browser API, and **the browser-side WebAuthn calls have not been exercised in a real browser with a real authenticator**. Limits on prices are checked again at begin, finish and Team approval (mechanism only; the eight limit rows stay unapproved). Lost-authenticator recovery is the offline recovery credential above. Not implemented: ceremony-gated configuration change; attestation; alert transport (monitoring workstream); scheduled pruning.
