## 3. Answers to the seven questions
1. **Endpoints.** Stage A, GET only: `api.twilio.com/2010-04-01/Accounts/{AC}.json`; `trusthub.twilio.com/v1/CustomerProfiles/{BU}`, `.../EntityAssignments`, `/v1/EndUsers/{IT}`, `/v1/Policies`, `/v1/CustomerProfiles`, `/v1/TrustProducts`; `messaging.twilio.com/v1/a2p/BrandRegistrations`. Stages B/C add the runner's calls: POST `CustomerProfiles` (+ `/EntityAssignments`, `/Evaluations`, status `pending-review`), POST `EndUsers`, POST `api.twilio.com/.../Addresses.json`, POST `SupportingDocuments`, POST `TrustProducts` (+ assignments, evaluations, submit), POST `a2p/BrandRegistrations` (`Mock=true`), plus lookup GETs before each create and GET brand status.
2. **Persistent artifacts.** Yes from stage B on. Stage A: none. B: draft Customer Profile, EndUsers, Address, SupportingDocument, Evaluations. C: the profile and trust product move to `pending-review` (real compliance review), plus the mock brand. Only the mock brand expires on its own (30 days).
3. **Fees.** Documented: Trust Hub, address, evaluation and mock-brand calls carry no fee; no number, Messaging Service or campaign is created; SMS cannot be sent. Not verified against an invoice (check Console billing before and after). **Worst case if Twilio ignored `Mock=true` and created a real Standard brand: about $46 (incl. $41.50 secondary vetting).** The real adapter now treats a brand response that does not say `mock: true` as an unknown outcome and stops (it also refuses to adopt an existing non-mock brand in a mock run), so a second brand is not created in the same run. The one-paid-brand guard lives in the local database and `cleanup` deletes it, so "once" holds only until cleanup; do not clean up between stage C and reading the report. Unverified: that Twilio returns a boolean `mock` on brand records (Stage A reports how many existing brands carry such a field). The test can be completed without charge on the documented behavior; the $46 is the bound, not the expectation.
4. **Future problems.** Rejected profile or trust product: editable and resubmittable or replaceable; ConfiDance gets its own new set, so there is no technical dependency. Duplicate: the runner looks up by FriendlyName before creating, so reruns adopt rather than duplicate. Real risks: (a) GenX TotalTech LLC owns the ISV Primary profile, so a Secondary profile with the same EIN may be flagged by Twilio's review; (b) whether it or the mock brand counts against a per-EIN brand limit is **unverified**; (c) a rejection may draw attention to the ISV account. Each `seed` creates a new random studio id, so resources are never adopted across seeds. Mitigation: Stage A first (read the Primary profile and inventory), and optionally a one-line heads-up on ticket #29647095 before stage C (needs its own authorization).
5. **Identification and cleanup.** Every resource's FriendlyName is `df:<env>:<studio uuid>:<step>:<seq>` (prefix `df:`; Stage A inventories that prefix before and after). The `evidence` command prints step, status, SID, friendly name, mock flag from the ledger; run it BEFORE `cleanup` because cleanup deletes the local ledger. Cleanup of Twilio side: mock brand expires (30 days); drafts can be deleted in the Console (the adapter has no delete); submitted bundles cannot be withdrawn and stay as test records. `cleanup` cancels the onboarding (erases the EIN) and removes the local fixtures and the throwaway EIN key.
6. **Is a fully simulated run enough?** No. It is done (404 unit/integration tests, the R1 dry run, and now this harness), and it proves the runner logic. It cannot prove Twilio accepts our payloads: business type, position, region and A2P company-type mappings, the Primary-profile assignment, response shapes. Stage A gives real evidence with zero artifacts; B adds payload evidence with no review submission; C the rest.
7. **Production changes?** None for any stage. No Vercel env change, no deployment, no PROD SQL, no PROD runner window. The harness runs from a developer machine against the disposable local database with `NODE_ENV=production VERCEL_ENV=production TW4_ISV_REAL_CALLS=on TW4_ISV_MOCK_BRAND=on` set in the operator's shell for that run only (the runner's own real-calls gate is unchanged). Credentials are typed or exported by the owner; the harness never prints them.

## 4. Credential handling
Owner creates a temporary Standard API key (`SK...` + secret) in the Console and exports `TWILIO_ACCOUNT_SID`, `TWILIO_API_KEY_SID`, `TWILIO_API_KEY_SECRET` in their own terminal; revokes the key afterwards. Stage A uses the key directly. **Stages B/C currently authenticate with the account SID + auth token only** (`real.ts` is unchanged). Using an API key there needs a small reviewed change to `real.ts`/`IsvConfig`; otherwise stages B/C need the master token for one run (rotate afterwards). Whether Trust Hub / A2P accept API-key auth is not verified; Stage A will show it for the read endpoints.

## 7. Stage A launcher (added after the second attempt)
Second Stage A attempt exited with code 2 and produced no new report: the command reused `--out` with the first attempt's report file, which Stage A (by design) never overwrites; the one-line message went to stderr and was easy to miss. Fixed: every refusal now prints "nothing was sent to Twilio / Problem / To fix", `--out` problems explain that the old report was not updated, and `scripts/tw4-validation/run-stage-a.ps1` replaces the manual steps. It prompts for Account SID, key SID and key secret (hidden), validates their shape before anything is sent, writes a NEW timestamped report under `%LOCALAPPDATA%\tw4-validation\reports`, runs Stage A once, and clears the variables in a `finally` block. `-DryRun` (and `stage-a.ts --self-test`) runs everything against canned data with no network. The first attempt's 401 (code 20003) has no confirmed cause yet; the launcher's checks and the report's hints cover the likely ones.

**Correction (launcher dry run):** the first version of `-DryRun` still prompted for credentials (it only skipped the prompts when a test hook supplied values, which hid the gap in testing). `-DryRun` is now fully non-interactive: it uses built-in synthetic credentials (`AC0000...`, `SK0000...`, a 32-character placeholder secret), skips the confirmation prompt, and with `-CompareLegal` uses synthetic name/EIN. Verified with stdin closed, with a network tripwire on fetch / TCP / DNS (0 blocked attempts; only tsx's local pipe), and across the 10-case validation matrix.

**Correction (secret entry, Windows PowerShell 5.1):** `Read-Host -AsSecureString` stores a Ctrl+V key press as ONE literal control character (0x16), so a "paste" produced 1 character / 1 asterisk. Reproduced by injecting a real Ctrl+V key event into a child console (length 1); a true 32-character paste burst through the same prompt is fine (32), and bracketed-paste markers add extra characters. The launcher now uses its own hidden reader (`[Console]::ReadKey`): Ctrl+V and Shift+Insert read the clipboard (`Get-Clipboard -Raw`), Enter on an empty secret prompt does the same, pasted bursts and typed input work, bracketed-paste markers are swallowed, Backspace edits, Esc cancels; only asterisks are echoed; the clipboard is cleared afterwards only if it still holds that secret. `-DryRun -Interactive` runs the real prompts against canned data. Test harness: key events injected with WriteConsoleInput into the launcher in its own console (10 scenarios, fake clipboard cmdlets so a real clipboard is never touched).

## 8. Stage A authentication failure: root cause and fix (2026-10-16)
Report `tw4-stage-a-20261016-084424.json` (API key auth): one GET to `api.twilio.com/2010-04-01/Accounts/{AC}.json`, HTTP 401, **code 70004** ("Unauthorized"); the harness stopped there. (The hint text printed "20003" because it was hardcoded; it now quotes the real code. The first attempt's report said 20003.)
Root cause: **the probe's first request is an endpoint a Standard API key is not allowed to call.** Twilio's API key docs: Standard keys have "access to all API resources except Accounts and Keys"; error 20003's documented causes include "a Standard API key used where a Main API key is required (e.g. /Accounts, /v1/Keys)"; error 70004 means the credentials and the resource are unrelated. The Basic-auth construction was correct (username = API key SID, password = API key secret, per Twilio's requests documentation) and the credentials may well have been fine; the harness misread "this key may not read this resource" as "these credentials are invalid" and stopped before testing anything else. Region note: API credentials are region-specific; a US1 key is expected for api/trusthub/messaging.twilio.com.
Fix (local, tested): with an API key the Accounts endpoint is **not requested** (report shows `account.ok: null`, `skipped`); the first Trust Hub read (policy list) is the credential check, and only a 401 on a read the key may make stops the probe. With the auth token the account check stays. Hints now cite the real code and explain both cases. Unverified until a real run: that Trust Hub and A2P endpoints accept Standard API keys (Twilio's docs do not say either way); if the policy read returns 401 from the correct account and region, stop and report: switching to the master auth token is a separate decision (the CLI needs the explicit --use-auth-token flag; the launcher has NO auth-token mode and clears TWILIO_AUTH_TOKEN, so it can never fall back to it).
Stages B/C are unaffected: the runner authenticates with Account SID + auth token, and Addresses (an account sub-resource) is not the Accounts resource.

**Pre-run hardening (before the final controlled Stage A run):** the CLI no longer silently picks up an ambient TWILIO_AUTH_TOKEN: the token is used only with `--use-auth-token`, and a key together with a token (variable or flag) is refused as ambiguous. Reports list every check that was not performed under `notRun` (`account.ok` is null, never true, when skipped; after rejected credentials the primary-profile and inventory reads are listed as not performed) and the CLI prints them. Correction: an earlier message said the launcher supports a token rerun; it does not.
