## 5. Application release items
- **Defect (FIXED in the release PR; was a release blocker for EIN retention):** `src/app/api/cron/sms-onboarding-purge/route.ts` exports only `POST`; Vercel Cron calls routes with `GET`, so a `vercel.json` entry would get 405 every day and never purge. Add `GET` (same logic, `dynamic = "force-dynamic"`, same `CRON_SECRET` check) like the other cron routes, then register `{ "path": "/api/cron/sms-onboarding-purge", "schedule": "17 3 * * *" }`. The sweep is a no-op until data exists, so it is safe to schedule at release. Postflight: the function returns `{ok:true, purged:0}` and shows 200 in cron logs.
- **EIN encryption key:** generate 32 random bytes offline (`openssl rand -base64 32`), store as `SMS_EIN_ENCRYPTION_KEY` (Production only, Sensitive) and optionally `SMS_EIN_ENCRYPTION_KEY_ID` (default `v1`); keep an offline copy in the password manager (without it stored EINs cannot be decrypted; the owner would re-enter them). Rotation: new id + new key; keep the old key as `SMS_EIN_ENCRYPTION_KEY_<OLDID>` until old ciphertexts are purged. The key must be set BEFORE the candidate build is made (env changes apply to new deployments only). Missing key fails safe: the wizard says setup is temporarily unavailable and writes nothing.
- **Environment for the later real run (do not set at release):** `TWILIO_ISV_PRIMARY_PROFILE_SID`, `TWILIO_ISV_PRIMARY_POLICY_SID`, `TWILIO_ISV_SECONDARY_POLICY_SID`, `TWILIO_ISV_A2P_POLICY_SID`, `TWILIO_ISV_COMPLIANCE_EMAIL`, and `TW4_ISV_REAL_CALLS=on` only for the run. `TW4_ISV_FAKE` and `TW4_ISV_MOCK_BRAND` must never be set in PROD except the mock validation decision below. ## 7. Twilio mock-brand validation: requirements and safeguards
**What Twilio's documentation says (read today):** a mock brand is created with `Mock=true` on the BrandRegistration request and requires a **real ISV-type Customer Profile and an A2P messaging profile** to exist first. Mock creation carries no TCR fee and no billing event; there is no vetting of the submitted data; mock brands cannot send SMS, cannot be deleted manually and expire automatically 30 days after creation (mock campaigns can be deleted). Source: https://www.twilio.com/docs/messaging/compliance/a2p-10dlc/mock-brand-api
**Real API calls it would make (about 25, parent account, HTTP Basic):** read: `GET` the Primary profile (status + policy), `GET` the profile/trust-product lists by FriendlyName, `GET` the brand list, `GET` the brand status; optional read-only `GET /v1/Policies` to obtain the three policy SIDs first. Writes: `POST` CustomerProfiles; EndUsers (business, representative, A2P: 3); Addresses; SupportingDocuments; EntityAssignments (S6-S9 and T3-T4: 6, including assigning the ISV Primary profile into the test profile); Evaluations (2); **submit the Secondary profile and the TrustProduct for Twilio review (`Status=pending-review`, 2 calls)**; TrustProducts; BrandRegistrations (`Mock=true`).
**Fees:** the mock brand itself: none documented. Trust Hub profile, trust product, address and evaluation calls: no fee appears in Twilio's published pricing or in the design cost table (design section 11 lists none); not verified on the account invoice, so check Console billing before and after. No number is bought, no Messaging Service or campaign is created, no SMS can be sent. The paid (Standard) brand is never created in this validation because `TW4_ISV_MOCK_BRAND=on` flags the step as mock; the runner would refuse the paid path for that studio afterwards.
**The real risk is not money:** the Secondary profile and TrustProduct are REAL Trust Hub resources submitted to Twilio's compliance review, and they persist (only the mock brand auto-expires). Fabricated business or EIN data in a submitted profile can be rejected and may draw scrutiny to the ISV account. Recommended: use **GenX TotalTech LLC's own real business information** (entered by you personally in the wizard; staff never handle the EIN) so any review is legitimate. Unverified: whether a second profile for the same EIN, or the mock brand, counts against Twilio's per-EIN brand limit; ask or accept.
**Isolation from ConfiDance:** a separate studio row marked as a test (never a customer), its own onboarding, ledger and runner window (a window for one studio never helps another); FriendlyNames embed the test studio's UUID so lookups can never match ConfiDance; the one-brand-per-studio guard is per studio, so ConfiDance's real brand later is unaffected; the mock brand is flagged on the ledger, is never mirrored into a registration row (no registration row = sending stays fail-closed for the test studio) and can never approve or purge; ConfiDance's pilot switch stays off until its own authorized run; the test studio's resources are never reused for ConfiDance (it needs its own new profile, trust product and brand).
**Where the database runs (decision needed):** the runner is gated to a production deployment, and production has no designated test owner accounts (standing rule: none are to be created). Two options. **(L, recommended)** a one-off harness run on this machine against the disposable LOCAL database with a production-mode process, using Twilio credentials supplied through the process environment for that single run (never written to a file, never printed); PROD data is never touched, but the master Twilio token is used on a developer machine, so it needs your explicit approval and the token should be rotated afterwards if you prefer. **(P)** the test studio in PROD via SQL-created rows and no user account: more PROD writes, needs a PROD SQL authorization for fixtures and a cleanup plan. Neither is allowed until you authorize it.
**Preconditions for the run:** Twilio Primary profile `twilio-approved` and the three policy SIDs read first; compliance mailbox decided; mock flag on; window opened for the test studio only for the shortest time; a Twilio Console billing check before and after; run read and recorded step by step; afterwards the test studio's onboarding is cancelled so its EIN is erased immediately.
