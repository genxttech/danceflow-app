# TW-4F price dual control: impersonation threat model and bounded design (D4-1)

Status 2026-10-31. Git only; nothing is applied to any hosted database. **The remaining impersonation risk below is an OPEN OWNER DECISION. Nothing in this document, the migration or the PR accepts a residual risk; only the owner can.** Pricing release stays BLOCKED until the owner has decided and an independent security review of the final tree is complete.


**Monitoring and alerting** for this surface (scheduled verification, evidence chain, security-event feed) is built by the monitoring workstream: see `docs/twilio/TW-4F_Price_Monitoring_Runbook.md` (PR 391). The authorization design, trust boundary and threat model are in `docs/twilio/TW-4F_Price_Authorization_Threat_Model.md` (D4-2).

**Update (D4-2):** the remaining paths in section 4 are re-analysed, per attacker class and with PREVENTED / DETECTED-ONLY / NOT COVERED marks, in the threat model; the single-owner mode adds a hardware-backed WebAuthn approval verified inside Postgres, which removes GoTrue-admin and JWT-secret compromise as ways to PUBLISH a price (they can still propose). Nothing is accepted.

## 1. The vulnerability the owner named
Before this change, `tw4_price_propose(.., p_actor)` and `tw4_price_approve(.., p_actor, ..)` were executable by `service_role`. A holder of the service-role key (or compromised server code) could, without any session, AAL2 step-up or TOTP, read the administrators (service_role can read `profiles`), call `propose(actor = A)` and `approve(actor = B)` and publish a price in two calls (reproduced by reviewer 2). `service_role` can also write `profiles` and, with the GoTrue admin API, create a user, so even "knowing two real administrator ids" was no barrier.

## 3. What is DESIGNED, not implemented (bounded)
1. **Scheduled check and alert (d).** Run `select public.tw4_price_verify(<cutover timestamp>)` from the existing hourly operations job (the one that already runs `tw4_rfl` health scans) using the service role; any `ok = false` writes an alert through the existing provider-alert path (`studio_sms_provider_alerts`, audience platform) naming the codes only. Size S-M; needs a new alert kind (migration) and a job registration, so it is not shipped here. Until then the owner runs the query by hand after every price change and before any hosted apply.
2. **Cooling-off (option C).** `approved` price takes effect after N minutes with a cancel window. Size M (new effective-at column and a job). Not shipped.
3. **Dedicated credential for the verifier and any future price job (option G).** A direct Postgres login role (not service_role) with EXECUTE on `tw4_price_verify` only, in its own secret scope. Size M: needs a pg driver path in the job runner and hosted configuration; document-only here, and nothing hosted was touched.
4. **Signed approval token minted outside the app trust domain (option F).** Size L; only if the owner wants resistance to a full server compromise that includes the GoTrue admin API.

## 4. Impersonation paths that REMAIN (release-blocking unless the owner decides otherwise)
| Path | Why it still works | Mitigation available |
|---|---|---|
| GoTrue admin API / ability to mint sessions | Anyone who can create a session for a REGISTERED administrator (admin API with the service-role JWT secret, `generateLink`, password reset, MFA factor deletion and re-enrolment of the administrator's own TOTP) obtains a real aal2 token. The database cannot tell it from the administrator's. Needs the service-role key or the project's JWT secret, and is visible in the Auth audit log. | Treat the service-role key and JWT secret as the root of trust (section 6); alert on `auth.mfa_factors` changes and admin-API logins for registered approvers; cooling-off (3.2); signed approval token (3.4) |
| Compromise of an approver's own account and authenticator | Two real, registered, compromised administrators publish a price within the (optional, unapproved) limits. | per-kind limits once approved; verification job; cooling-off |
| Owner-level DDL (database owner, superuser, migration runner) | Can disable triggers, edit the registry, replace functions. Same limit as every TW-4F guard. | Restrict the owner credential; verifier detects forged price rows afterwards |
| Registry written by the same person who also acts as an approver | A registered administrator with owner access could register a second identity. | The registry change is an owner-level, ticketed runbook step (section 5 of the dual control doc), reviewed by a second person |

## 5. Evaluation of the "no authenticated grants" convention
Every other TW-4F function is service-role only. The price entry points are the first that grant EXECUTE to `authenticated`, deliberately: the guarantee that the approver is a real, fresh, second-factor session can only be enforced where the user's own token reaches the database. The exception is bounded: four functions; `security definer` with `search_path = pg_catalog, public, pg_temp`; no table grants anywhere; all real work in internal functions with no grants; the function itself refuses any token that is not role `authenticated`, aal2, TOTP, a registered administrator; replay and separation of duties are enforced in the database. The manifest and probes list the new grants. A reviewer who rejects the exception can instead keep service-role functions with a signed approval token (3.4).

## 6. Where the service-role key lives (inventory and recommendations)
- 199 non-test source files call `createAdminClient()` (`src/lib/supabase/admin.ts`), among them every platform SMS action (`src/app/platform/sms/*Actions.ts`), the provisioning runners (`src/lib/sms/twilioIsv/factory.ts`, `cancelRuntime.ts`, `cancelRunner.ts`), and 10+ billing routes that read `SUPABASE_SERVICE_ROLE_KEY` directly (`src/app/api/billing/**/route.ts`). All run on the same Vercel project and share one environment variable.
- **This PR removes the price path from that list**: `priceChangeActions.ts`, `PriceChangesPanel.tsx` and `lib/sms/priceChange.ts` use only the user-scoped client.
- Recommended, not implemented (hosted configuration, owner action): (1) keep the key in the server-only environment scope of the production project only, never in Preview or Development scopes that run branch code; (2) rotate it on any staff change and after any incident, and rotate the JWT secret if the GoTrue admin API is believed compromised; (3) never log request headers or environment on the server (no logger in the repo prints the key; keep it that way, add a lint rule if the owner wants); (4) move provider runners (`twilioIsv`) to a separate Vercel project or a job runner with its own scoped credential so a bug in a web route cannot reach them (size M-L); (5) a Postgres login role with only the EXECUTE grants a given job needs (option G).
