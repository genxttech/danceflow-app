## C. The six proposals (owner at the keyboard)

Order and amounts are in the manifest. For each of the six kinds:

1. Sign in, complete the authenticator code (must be at most 10 minutes old) and open Platform > SMS > Price changes > Propose a price change. Enter the kind, the customer price and provider cost from the manifest (dollars, up to six decimals for `sms_usage` and `sms_inbound`), the description and the reason. Submit. Result: request pending, cooling-off 24 hours, nothing published.
2. Wait at least 24 hours. Nothing a function, an administrator or a service key can do shortens this; it is a row constraint.
3. In a DIFFERENT session (sign out and in again), open the same panel, choose Authorize with my hardware key, read the summary (it comes from the database and shows the exact micro-dollar amounts, for example `$0.017`), and touch the key. The database verifies the signature over the hash of those exact values and publishes.
4. One open proposal per kind exists at a time, so all six can be proposed on the same day and authorized the next, each with its own touch.

A micro-dollar proposal is not revised: withdraw it (Withdraw proposal) and propose the corrected amounts, which restarts the cooling-off. Team-mode approval of a micro request refuses by design.

## G. Lost-device recovery (single owner)

Consequence of losing the key: prices cannot be changed until recovery completes. Published prices, billing safeguards and everything else are unaffected; no money is at risk. The process is deliberately slow and independently verified.

1. FREEZE at once (any signed-in platform administrator session with the authenticator app: Platform > SMS > Price changes > Suspend price publication, or `tw4_price_freeze`). Put the verification reference of this incident in the freeze reason (for example "lost device REF-2026-11-10"). If pricing is already frozen the reason cannot be rewritten (including a freeze made with the recovery key, which has fixed text); the reset script then accepts the existing freeze only if it was set at or after the incident start time that engineering asserts and records in the audit (@@INCIDENT_START@@), so a freeze made BEFORE the incident cannot be reused. This is audited and cannot publish anything. Also use "Report a compromise" if theft or abuse is suspected.
2. INDEPENDENT OWNER VERIFICATION, in writing, through channels that do not depend on the lost device, at least ONE of which is outside the owner's PC, mailbox and authenticator app (for example a phone call or a text to a number on file before the incident, or an in-person confirmation): (a) the request made to engineering in the owner's engineering session, and (b) a confirmation sent from the owner's own verified account email to the engineering session, plus the owner signing in to the platform admin area with password and authenticator app (fresh code) and reading back the freeze reason. Engineering records the verification reference (date, channels, what was checked). If any channel cannot be verified, the reset does not proceed.
   What this recovery does and does not protect, plainly: it protects against an attacker who has only an app session (the reset is unreachable from the app). It does NOT protect against someone who controls the owner's PC, mailbox, authenticator app and engineering tooling together: that person can freeze, create a key, send the confirmation and wait 72 hours. That residual risk is the same as database-owner compromise, which is outside this design's boundary; the outside-channel requirement above is what narrows it.
3. WAITING PERIOD: pricing stays frozen at least 72 hours from the freeze (the same minimum as the in-app recovery enrolment). The reset script enforces it from `frozen_at`. During the wait the monitoring feed and alerts keep running; any unexpected publication attempt is refused because pricing is frozen.
4. Before the reset, reject every pending price proposal (a pending proposal could otherwise be authorized by the new key after its cooling-off). Then RESET (owner-level, visible, one transaction): the owner creates the replacement key on /platform/sms/key-setup, checks it reads ACCEPTABLE, and gives engineering the public values; engineering runs `scripts/hosted/tw4f/lost_device_reset.sql` with the verification reference. It refuses unless frozen 72 hours, cancels pending credential changes, revokes EVERY active credential, clears a recovery hold, installs the new key as an ordinary bootstrap key (never as a recovery-enrolled key), RESTARTS the freeze clock after the new key exists (the new key, like any primary key, can also lift a later freeze; that is inherent, not closed by the reset) (a second reset after a bad key therefore waits another 72 hours, so check the key first), writes an immutable audit row per revoked credential and for the new key (reference, database session user, transaction id), and emits a monitoring event.
5. PROVE AND LIFT: the new key signs the enrolment proof (`_tw4price_attest_begin/finish`), then lifts the freeze with its own thaw ceremony. Prices already published are untouched. Afterwards enrol a second device-bound credential.
6. REVIEW: the audit rows (`credential_revoked`, `credential_bootstrapped` with `via = owner_level_reset`) and the monitoring event are read back and recorded with the ticket. Tested locally: `localStack.pricehello.test.ts` cells HR-1 to HR-4 (HR-4 covers a recovery hold). Tool 2 on the setup page signs whatever challenge is pasted: after the enrolment proof, do not use it again (a later release removes the route).

## H. Signature counter policy (device-bound passkeys)

Some platform authenticators report a signature counter of 0 on every use (the owner's Windows Hello does NOT: it counted 1 to 4 in the real-device check, so clone detection by counter is active for it). The database accepts a credential whose counter is and stays 0 (no clone detection by counter for that credential), and it never relaxes the rule for a credential that counts: once a counter has moved, an equal, lower or zero value is refused as a possible cloned authenticator and recorded as an integrity failure. Accepted limitation for a zero-counter key: Windows Hello keys are non-exportable and bound to the device TPM, so the realistic clone path does not exist; compensating controls are user verification on every signature, the exact-price signature, the separate session, the 24 hour cooling-off, the alerts and the freeze. A key that counts and later reports 0 (for example after a TPM or driver change) is refused as a possible clone and recorded as an integrity failure; recovery is the reset above. "Device-bound" here means NOT REPORTED AS SYNCED: the database has no attestation, so it relies on the authenticator flags and on the TPM check in B.4 step 0. The setup page shows the counter after the proof, the hosted preflight prints how many active credentials report counter 0, and the owner confirms the acceptance in the release authorization. Tested: `localStack.pricehello.test.ts` cells HC-1 to HC-3.
