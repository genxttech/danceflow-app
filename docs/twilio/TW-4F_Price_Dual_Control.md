# TW-4F SMS price dual control (D4-1)

Status 2026-10-31. Git only: migration `20270204090000_twilio_price_dual_control.sql` is not applied to any hosted database. **The pricing release gate stays BLOCKED** until the owner has decided the OPEN OWNER DECISION below and an independent security review of the final tree is complete. Two independent reviews of earlier heads found no P0 or P1 CODE defect; that is not a statement that the design is accepted.

## Rule
A published SMS price changes only when one REGISTERED platform administrator proposes and a DIFFERENT registered administrator approves, each through their OWN authenticated session: the public functions `tw4_price_propose / approve / reject / requests_list` are executable by `authenticated` only, take the identity from `auth.uid()` (no actor parameter) and require aal2 plus a TOTP authentication (within 15 minutes for propose and approve). `tw4_price_set` refuses every caller. A price row can be inserted only while an approved request for exactly those amounts is being applied; retired prices are never re-activated; published prices are never edited, deleted or truncated. These guards are `ENABLE ALWAYS` (they also fire under `session_replication_role = replica`), as are the request-table and registry guards, so forging a decision needs visible DDL.

## Runbook: the approver registry (owner-level, never an API role)
The registry `studio_sms_price_approvers` starts empty; until it has two rows nobody can change a price. Register: `insert into public.studio_sms_price_approvers (user_id, added_note) values ('<uuid>', '<ticket and reason, 10+ characters>');`. Revoke: `update public.studio_sms_price_approvers set revoked_at = now(), revoked_note = '<reason>' where user_id = '<uuid>';` (revocation is final for that row; use a new user to re-register). Each change is a ticketed step reviewed by a second person. The user must also hold `profiles.platform_role = 'platform_admin'` and have a non-banned, non-deleted auth user.

## Runbook: prices must never be INSERTed outside the workflow (F8)
No migration, seed script, restore or logical-replication apply may INSERT (or DELETE, TRUNCATE, re-activate) rows of `studio_sms_price_list` from now on: the guard refuses them, also in replica mode. Supported procedure for a new price (including a new kind): add the kind to the price-list check constraint in a migration, add it to `PRICE_KIND_TEXT`, then publish with propose + approve. Supported procedure for a restore: an owner-level, ticketed step that disables `studio_sms_price_list_00_activation` and `_00_truncate` for that statement and re-enables them with `enable always trigger`; afterwards run `select public.tw4_price_verify()` and review every listed price. Local QA suites do the same through `priceFixture.ts` (marker-asserting, local databases only).

## Rollback and recovery (fail closed)
The rollback never restores single-administrator publication: `tw4_price_set` stays a refusing stub with EXECUTE revoked from every role; the price-list triggers stay, and the insert guard refuses every insert; all callable functions are dropped; if any request or registry row exists the three tables are RETAINED (audit evidence and authorization data are never destroyed), otherwise dropped. It refuses (55000) when `tw4_price_set` or a guarded function was replaced by a later slice. So "rolled back" does NOT mean "identical to the catalog before"; it differs by exactly: `tw4_price_set`'s privileges, the refusing guard functions and their two price-list triggers, and the retained tables. Recovery after a rollback (with or without evidence) is to re-apply the migration, which is idempotent over retained tables; it is tested in `localStack.pricedual` PD-23, PD-23b, PD-23c and by the runner chain (`--residue` lists the accepted catalog lines). Rolling back in a live environment disables price changes entirely until re-applied.

## Operational notes
- Lock order: the functions share-lock the parties' `profiles` rows first (id order), then the per-kind advisory lock and the request row. Tooling that changes several platform roles in one statement should update profiles in id order, or it can deadlock with an approval (fails safe).
- Price kinds are read from the price-list check constraint with a lowercase `[a-z][a-z0-9_]*` rule; a kind with a digit first, an uppercase letter or a hyphen would not be proposable. The UI list `PRICE_KIND_TEXT` must gain every new kind; `localStack.pricedual` PD-09c compares it to the database.
- `tw4_price_requests_list` returns the latest 100 requests; older rows stay in the table.
- Amounts are capped at 10,000,000 cents by CHECK (the UI can enter at most 9,999,999). Per-kind limits are data and unapproved: `TW-4F_Price_Limits_Proposal.md`. A provider cost above the customer price is allowed until the owner approves limits.
- A requester's withdrawal is recorded as `rejected` by the requester.
- Detection: `select public.tw4_price_verify()` (service role or owner) lists published prices without a matching two-person applied request and request anomalies. Design for the scheduled alert: the impersonation design doc.

## OPEN OWNER DECISION: impersonation and the service-role key
The earlier design let a holder of the service-role key propose as one administrator and approve as another with no session (reviewer 2 reproduced it). This PR closes that path (session-bound entry points, no actor parameter, service_role has no EXECUTE, a protected approver registry service_role cannot write) but is **not** claimed to remove all impersonation: a holder of the GoTrue admin API / JWT secret who can mint sessions or reset MFA factors for a registered administrator, and owner-level DDL, remain. See `TW-4F_Price_Dual_Control_Impersonation_Design.md` for implemented vs designed controls, remaining paths, the option table and costs. Whether the remaining risk is acceptable for a pricing release is the owner's decision and is **open**.
