Status: **specification only (revision 3: revision 2 reconciled with the final M14 bytes, submitted for the quick re-review that was queued).** Revision 2 had a conditional GO for local-only work; revision 3 changes no decision, it makes the M14 interactions explicit (section 9). No SQL, code, flag, env or email is authorized by this document. Gate A stays closed; no billing gating (pilot grants, staff roles and Gate A only). **Numbering:** this slice is **M15**. M14 is the hold-semantics and purge-liveness fix (`NSI_M14_Hold_Semantics_Spec.md`), a safety item that comes first. Sequence: M13 DEV apply, M14, this slice (M15), then I3-2 (M16).

**Owner-decision labels.** Everything marked **[recommended, pending owner decision]** is a DRAFT default that implements my recommendation. It stays flag-free and changeable (one function or one setting each). Silence is not approval.

## 1. Scope
1. The **minor determination service path** (A5): a birthday-based determination, a self-declaration fallback, a session-facing routing read, and a staff-facing read of the basis.
2. **Moved to I3-2 (M16):** guardian decline (A6) and N1 outcome alignment (A9). A terminal declined status with no writer would be dead code, and guardian sessions do not exist yet (M12 is student audience only).
3. Post-completion changes (a birthday corrected after submission, a client who turns 18 between invitation and submission) are handled by the I3-4 submit step calling the determination again (section 5) and, for already-completed requests, by I3-2.

## 2. Principles
1. **No personal value crosses the function boundary.** The database reads `clients.birthday` itself, scoped to the request's studio; callers get only outcome words. No birthday, age or threshold appears in a return value, an audit row or an error text.
2. **Determinations are append-only and monotone.** The latest row governs, but **an automatic path may never write "adult" once any row says "minor"**. Only an owner or admin (existing staff function, mandatory reason, source `staff_override`) can move a request from minor to adult. A `staff_override` row also blocks every later automatic insert.
3. **A declaration is not authenticated evidence** (P1-A rule): it is stored as `declared`, with provenance (section 4), and the birthday rule runs first inside the database so a declaration can never override a trusted birthday.
4. **Lock order** (every writer): read session and request without locks, `lock_client`, `request FOR UPDATE`, then **re-check** the session (not revoked, not expired, `link_valid`) after the lock. Each function gets a deterministic lock-order check and a probe removing `lock_client`.
5. Nothing writes to appointments, clients or `client_account_links`. The age rule is isolated in helpers so O5 changes one function, not the design.

## 3. Age rule [recommended, pending owner decision O5]
**Reference date: the studio-local date.** `intake_private.studio_local_date(p_studio_id)` returns `(now() at time zone tz)::date` where `tz` is the studio's validated time zone (`studio_settings.timezone`, checked against `pg_timezone_names`). **A null or invalid time zone falls back to `Etc/GMT+12` (UTC-12, the last place on Earth to reach a new date)**, so a misconfigured studio can never make anyone an adult early. The local date is stored in `evaluated_on`.
`intake_private.age_in_years(p_birthday date, p_on date)` = completed years using `date_part('year', age(p_on::timestamp, p_birthday::timestamp))` (the `timestamp` overload, never the `timestamptz` one), flagged IMMUTABLE. A person is a **minor** when that age is below the **effective threshold** `greatest(intake_settings.minor_age_threshold, 18)`.
- **Threshold clamp [recommended, pending owner decision O5b]:** the studio setting allows 13 to 21 today; until the owner and counsel decide otherwise, values below 18 are **clamped up to 18** inside the function (a studio cannot lower the age of majority for intake). The conflict between the setting's range and the clamp is itself an explicit owner decision; tests cover thresholds 13, 18 and 21.
- The day of the 18th birthday: adult. The day before: minor. 29 February birthdays: PostgreSQL semantics, the person turns 18 on 1 March; flagged for legal review with O5.
- A birthday in the future, or older than 120 years, is **not trusted**: treated as no birthday.
- The "pending legal review" note stays attached in the staff UI until cleared (spec 14.9).

## 4. Functions (level 11; all `SECURITY DEFINER`, pinned search path; explicit `REVOKE ALL ... FROM public, anon, authenticated, service_role, intake_destructive`, then `GRANT EXECUTE` to the listed role only)

| Function | Role | Behavior |
|---|---|---|
| `intake_determine_minor_from_birthday(p_studio_id, p_request_id)` returns text | `service_role` | Lock order of section 2. Early returns, each its own **explicit outcome word or error code**: unknown request (22023), Gate A closed (`gate_closed`), erasure barrier (`erasure_barrier`), client/studio drift (`assert_drift_free`, 42501), request not open (`request_not_open`: only `pending`, `invited`, `in_progress` qualify). Then: `staff_override_exists`, `kept_minor` (a minor row exists and the birthday would say adult), `no_birthday` (also for untrusted birthdays), `already_current` (the latest automatic row has the same answer, source and threshold: **no new row**, so a daily call cannot grow the table; the comparison ignores the date), or `determined_minor` / `determined_adult` (one `birthday` row, `evaluated_on` = studio-local date, effective threshold recorded, audit `minor_determination_recorded` with `basis` only) |
| `intake_declare_minor_status(p_session_hash, p_is_minor)` returns text | `service_role` | Session rules of section 2 (audience must be `student`). **First applies the birthday rule inside the database** by running the determine logic: if a trusted birthday exists the declaration is ignored (`birthday_used`, the birthday result governs, a birthday-minor can never be overridden by a declaration). Otherwise: `already_determined` if any row exists, else one `declared` row (declared class `minor` or `adult`; [recommended, pending decision O12] plus `under_13` as a third class so the app can route it to staff without collecting a date). **Provenance:** audit `minor_determination_recorded` with `actor_type = 'student'`, `object_type = 'intake_session'`, `object_ref` = the session id, metadata `basis` = `declared` or `declared_via_staff_link` (when the session's minting actor is a staff member) and `generation` |
| `intake_session_minor_state(p_session_hash)` returns text | `service_role` | `unknown`, `minor` or `adult` for the session's request (latest row); nothing for an invalid session. **Routing only: the app must never display it.** No source, date or threshold |
| `intake_minor_basis(p_studio_id, p_request_id)` returns table | authenticated, `assert_staff('view_status')` | For staff: the source word (`birthday`, `declared`, `staff_override`), whether the declaration came through a staff-minted link, the effective threshold and the local date it was evaluated on. **Never the birthday.** The UI labels a birthday-based answer as such |
| `intake_private.studio_local_date(uuid)`, `intake_private.age_in_years(date, date)` | none | Internal helpers (STABLE and IMMUTABLE respectively, recorded in the catalog inventory); no API grants |

**[Recommended, pending owner decision O11] A declared adult never completes without staff confirmation.** Because a self-declared "adult" through a link is not verified, `fulfillment_state` gains a derived state `staff_confirmation_outstanding` when the latest determination is `declared` and adult; staff clear it with the existing override (reason required). Implemented as one branch in `fulfillment_state` (changeable); listed as an owner decision.

The existing staff function `intake_record_minor_determination` is unchanged: owner/admin, mandatory reason, source `staff_override`; it is the only path from minor to adult.

## 5. How the student path uses it (I3-4, not here)
The app calls `determine` when the invitation is issued, `session_minor_state` when a session opens (`minor` leads to the guardian flow, `adult` to the student flow, `unknown` to the declaration question), and **calls `determine` again at submission** so the answer is evaluated as of the submission date (the monotone rule means a minor can never become an adult by waiting out the call).

## 6. Catalog and privileges
Level 11: the four public functions and the two helpers; the existing `intake_minor_determinations` table, triggers and policies unchanged. Body markers `nsi-body:m15` for the four public functions. The rollback drops the functions and restores the M14 `assert_catalog` and is **refused once any `birthday` or `declared` row exists**; its fingerprint is checked against the expected M14 value, and the harness includes the replay guard test (replaying M15 on a newer database must fail closed or be documented).

## 7. Tests (new suite, lifecycle harness, DEV-safe suite, concurrency)
- **Time zone and date (P1-1):** a studio in Los Angeles at 23:30 the day before a birthday (still a minor); `Pacific/Kiritimati`; null and invalid time zones fall back to `Etc/GMT+12`; the stored `evaluated_on` is the local date.
- **Age rule edges:** the day before and the day of the 18th birthday; 29 February birthdays in leap and non-leap years; thresholds 13, 18 and 21 (13 clamps to 18); future and 120-year-old birthdays; null birthday.
- **Birthday first (P1-2):** a declaration cannot override a trusted birthday-minor; probe removing the in-database birthday rule.
- **Provenance (P1-3):** audit row contents for `declared` and `declared_via_staff_link`; the staff read exposes the basis and never the birthday; O11 branch behavior.
- **Monotone (P1-4):** after a minor row, an automatic adult attempt returns `kept_minor` and writes nothing; only the staff override moves to adult.
- **Reference and state (P1-5):** automatic determinations refuse non-open requests with the explicit word; the submission-date re-evaluation.
- **Lock order (P1-6):** declare racing revoke, determine and staff override ends consistently; deterministic lock-order check; probe removing `lock_client`; session re-checks after the lock (a session revoked while waiting yields nothing).
- **No daily growth:** repeated calls on later dates write nothing when answer, source and threshold are unchanged.
- **Early returns:** Gate A closed, erasure barrier, drift, non-open request each give their explicit outcome.
- **Tenant scoping:** a client's birthday from another studio is never used.
- **Privileges:** service_role only; `anon` and `authenticated` refused; helpers not executable; the staff read rejects non-staff; no personal value in any return, audit row or error.
- **Mutation probes:** drop the monotone rule, drop the override check, drop the "no row exists" check on declare, drop the birthday-first rule, flip `<` to `<=`, drop the birthday sanity bounds, drop the time-zone fallback, drop `lock_client`.
- DEV-safe level-11 suite (no fixtures), rollback and replay-guard checks, full-chain replay after the slice.

## 9. Revision 3: reconciliation with the final M14 bytes (migration sha256 `ae6bbf0b0d05bd46aed96eb284d0eb8ca53bf917f08af39692fa9415b7cef2d2`; fingerprint `be5a715adedad4197649593d23c6ce09|770`; 104 intake functions)
M15 is written against these bytes. If the M14 review changes them, this section is re-reconciled before any M15 SQL.

1. **Isolation guard (M14).** `lock_client` raises 55000 unless the transaction is READ COMMITTED. All four public M15 functions call `lock_client`, so they inherit the guard and add none of their own. Tests: each function under REPEATABLE READ fails closed with 55000 and writes nothing; the probe removing `lock_client` is detected by this test as well as by the lock-order check.
2. **No hold check in determinations.** M14 holds only block deletion (erase, purge, direct delete through `delete_guard`). A determination is an insert/read path and never consults `client_has_active_hold`. A held client may still receive a determination; the hold keeps the data when an erase later arrives. Test: a determination for a held client succeeds, then an erase of that client is refused (hold) and the determination row survives.
3. **Erase interaction (M14 semantics).** `intake_minor_determinations` rows are removed by the existing erase path, and the M14 `delete_guard` resolves their subject through the request (fail closed with 42501 if it cannot). M15 adds **no new table**, so the guard and its subject resolver are unchanged. Tests: (a) erase of a client with determinations succeeds and removes them; (b) an erase racing a determine serializes on the client lock: determine first, the row is erased with the client; erase first, determine returns `erasure_barrier` and writes nothing.
4. **Audit rows carry `client_ref`** (the M14 `session_revoked` fix applies to every new audit event). `minor_determination_recorded` and the declaration provenance event set `client_ref` to the request's client so erase and purge, which select audit rows by client, cannot orphan them. Test: after erase no determination audit row for that client remains outside the retention rules; a probe dropping `client_ref` is detected.
5. **Catalog and fingerprint.** The function inventory grows from 104 to 110 (four public, two helpers); the presence-loop levels extend from 1..10 to 1..11 (the M14 trigger function `legal_hold_insert_guard` stays at level 10). Markers `nsi-body:m15`. The expected M15 fingerprint is computed by the generator run and recorded in the migration notes, not asserted here. **Rollback** restores the **M14** `assert_catalog` (not M13), drops the six functions, and its fingerprint check is against `be5a715adedad4197649593d23c6ce09|770`.
6. **Replay guard.** Replaying M15 on a database that already has M16 or later must not strip their objects: the replay either fails closed with an explicit message or is a documented no-op; tested in the lifecycle harness together with the DEV-safe level-11 check.
7. **Process (unchanged).** Generator-built migration and rollback, fresh-container lifecycle with mutation probes, deterministic lock-order checks, race checks (determine vs erase, declare vs revoke, determine vs staff override), full-chain replay on the final bytes, independent review, DEV apply by `sb.sh` under the standing conditions. No M15 SQL exists; this revision is text only.
8. **What the re-reviewer is asked to check:** that sections 1 to 6 above are the only M14 interactions, that "no hold check in determinations" is acceptable, and that audit `client_ref` on every new event is sufficient for erase/purge selection.

## 10. Revision 4: corrections from the independent re-review of revision 3 (verdict: CONDITIONAL GO for local-only implementation; no P0; one P1)
Where this section conflicts with sections 1 to 9, **this section governs**. Evidence references are the reviewer's, against the M14 bytes (sha256 `ae6bbf0b…2d2`).

1. **P1-1: `fulfillment_state` is part of M15's catalog, marker, rollback and fingerprint plan.** The O11 branch (`staff_confirmation_outstanding`) replaces the M3 body of `intake_private.fulfillment_state` in place. Therefore: (a) the new body carries `-- nsi-body:m15` and a version tripwire `c_guard` entry `intake_private.fulfillment_state|nsi-body:m15|11` (M16 will replace it again and bump the marker); (b) the function inventory is still 110 (the function is replaced, not added); (c) the O11 branch sits **after** the "no completion, so incomplete" check, so it can never hide `incomplete`; (d) the rollback restores the **exact M3 body with its ACL** (`intake_destructive` EXECUTE, SECURITY DEFINER), and the lifecycle checks that the post-rollback fingerprint equals `be5a715adedad4197649593d23c6ce09|770`.
2. **P2-1: erase-first races have two interleavings, both specified.** (i) The erase commits before determine's unlocked read: the request is gone, the function returns 22023 (unknown request). (ii) Determine read the request, then waits on the client lock: after acquiring it, **re-read the request**; if it is gone, check the erasure barrier using the client from the unlocked read: barrier active returns `erasure_barrier`, otherwise 22023. No insert is attempted, so no exception comes from `collection_gate` or the foreign key. Both interleavings get their own test, plus a mutation probe removing the re-read.
3. **P2-2: the audit `client_ref` rationale is corrected.** M14 erase and purge do not select or delete audit rows (the table is append-only; determination audit rows survive erasure by design). `client_ref` is required because `audit_write` sets `retention_state = 'held'` when the client is held, `erasure_barrier_active` reads it, and I6 minimization will use it. Tests (replacing the unreachable one in 9.4): `client_ref` equals the request's client, `request_ref` equals the request id, `retention_state = 'held'` when a hold is active at write time and `scheduled` otherwise; a probe dropping `client_ref` flips the state and is detected.
4. **P2-3: only the two writers lock.** `intake_determine_minor_from_birthday` and `intake_declare_minor_status` call `lock_client` (and inherit the 55000 isolation guard). `intake_session_minor_state` and `intake_minor_basis` are reads: no `lock_client` (no contention with erase or purge), the same session-validity checks without locking. The REPEATABLE READ tests target the writers, with a fixture that reaches the lock (early returns before the lock never touch it; each writer also gets an entry-point isolation check like M14:605 so the test cannot pass trivially).
5. **P2-4: staff-link provenance is stored on the determination row.** The `declared` row's `actor_user_id` is set to `intake_sessions.issued_by_user` (the session copy matches the invitation), null for system-minted links; `intake_minor_basis` derives "declared via staff-minted link" from it. Audit metadata `basis` repeats it for reporting but is not the source of truth. This keeps the table unchanged and the read independent of I6 audit minimization.
6. **P2-5: B2 is closed here.** `fulfillment_state` stops treating "no determination" as adult: when a completion exists and no determination exists it returns `determination_outstanding` (the M5 submit guard stays as defense in depth). Tests: no determination plus completion gives `determination_outstanding`; a determination of either answer gives the normal state. If the owner prefers to defer, the branch is one line and B2 stays open with this text removed.
7. **P2-6: rollback race.** The rollback first takes `lock table public.intake_minor_determinations in access exclusive mode`, then checks for `birthday` or `declared` rows, then drops the M15 functions **before** installing and calling the M14 `assert_catalog` (otherwise it fails with an unexpected function), then restores `fulfillment_state`.
8. **Low items adopted.** (a) Re-check the session after the lock exactly like `intake_session_context` (revoked, absolute expiry, idle expiry, then `link_valid`), reading the session row `FOR UPDATE`, because `intake_revoke_session` serializes only on the session row. (b) "Latest" = `order by created_at desc, id desc` in the monotone check, `already_current` and `session_minor_state`. (c) Time zone precedence: `studio_settings.timezone`, then `studios.timezone`, then `Etc/GMT+12`, with a deterministic `limit 1` ordering; the uniqueness of `studio_settings` per studio is verified in the first local run before the SQL is trusted. (d) SECURITY DEFINER stated per function in the inventory: the four public functions and the two helpers each get an exact t/f. (e) Staff override rows store the unclamped threshold and a server-time `current_date`; `intake_minor_basis` reports the effective threshold only for automatic rows and states "staff override" otherwise. (f) The audience check cannot be exercised until M16 (`intake_sessions.audience` is student-only); the probe for it is deferred and listed as such. (g) M15's replay guard refuses when any intake function carries an `nsi-body:m16`-or-later marker (not by naming objects), and M15 keeps the exact signature `public.intake_determine_minor_from_birthday(uuid,uuid)` because the M14 replay and rollback guards bind to it.
9. **Test gaps added:** rollback fingerprint equals M14 after `fulfillment_state` is restored; both erase-first interleavings; audit `retention_state` and `request_ref`; two concurrent `determine` calls yield exactly one row; a hold committed before determine marks the audit row held; `session_minor_state` returns nothing for idle-expired, superseded-generation, closed-request and barrier sessions; the O11 branch never hides `incomplete`; M14 replay and M14 rollback over M15 are refused; mutation probes for dropping the after-lock session re-check, `link_valid`, and the request re-read.
10. **Not verified by the reviewer (to be checked in the first local run):** that `public.studio_settings` is unique per studio and where `timezone` lives; that nothing but staff and client-create paths writes `clients.birthday`; that I6 will select audit rows by `client_ref`.
