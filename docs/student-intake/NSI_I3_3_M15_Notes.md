## Behavior decisions made while implementing (all inside spec rev 4)
- **Order in `determine`:** isolation check, unlocked request read (unknown request raises 22023), gate (`gate_closed`), drift check (raises 42501), `lock_client`, request re-read `FOR UPDATE` (gone: barrier gives `erasure_barrier`, otherwise 22023), barrier, open-request check, staff override, birthday, threshold clamp, monotone, no-daily-growth, insert and audit.
- **`declare`:** the session is read unlocked, the client lock is taken, then the session row is re-read `FOR UPDATE` and re-checked (revoked, absolute and idle expiry, audience, `link_valid`), then the request is locked. The birthday rule runs first by calling `determine` (re-entrant lock). `birthday_used` covers every birthday-driven answer; `already_determined` covers an existing row or a staff override.
- **Provenance:** the declared row stores `intake_sessions.issued_by_user` in `actor_user_id`; the audit basis is `declared` or `declared_via_staff_link` and carries the invitation generation. Today every invitation is staff-issued (issuing needs an authenticated staff member), so the system-minted case is not testable until the app-side issuer exists; the suite proves the staff-minted case.
- **The P1-A draft rule 4** ("a staff-minted link can never declare adulthood") is **not implemented**: it is a draft in `NSI_P1A_Staff_Minted_Links.md`, awaiting its own review; M15 records the provenance exactly as spec rev 4 says. If the rule is accepted it is a one-line change in `declare` plus a test.
- **`clients.date_of_birth`** also exists in the base schema next to `birthday`. M15 reads only `birthday` (the documented birthday column). Whether the two can disagree, and which the app treats as authoritative, is an open verification for the first DEV check of real data; no personal value appears in any return, audit row or error either way.
- **Holds:** determinations never consult holds (holds block deletion only). A held client gets a determination, its audit row is marked held, and an erase is refused with the row intact (N13).
