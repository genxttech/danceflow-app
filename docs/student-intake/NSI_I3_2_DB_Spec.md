# NSI I3-2 (M16) database specification, revision 2: guardian path split into M16a / M16b / M16c

Status: **specification only (revision 2, after the independent review of revision 1: NO-GO for SQL on revision 1, conditional GO for a narrowed first slice once its P0/P1 items were folded in).** No SQL, code, flag, env or email is authorized by this document. Gate A stays closed; no billing gating (pilot grants, staff roles and Gate A only). Written against the FINAL applied bytes of M14 (sha256 `ae6bbf0b…2d2`) and **M15 (sha256 `0b700fb2…cdfe`, fingerprint `3fc0eea416e8f820856935a2b94d078a|776`, 110 functions)**. Owner-decision labels **[recommended, pending owner decision]** are draft defaults; silence is not approval. **Nothing here depends on the unresolved drafts** P1-A rule 4 (`NSI_P1A_Staff_Minted_Links.md`), O11 or O5b; O2 is not needed (existing capabilities are reused); O4 touches only M16c.

**Sequencing note (M15.1).** `NSI_Resume_Status.md` and the D11 report plan an M15.1 (drift fixes and tests for M15) before Gate A. M16a is written to apply on M15 or on M15.1: its precondition guard accepts the M15 marker or a later M15.x marker, its rollback target fingerprint is recorded at generation time, and if M15.1 changes `intake_minor_basis` or `determine` the `c_guard` entries are re-reconciled before SQL.

## 0. What the review changed (revision 1 to 2)
| Review item | Resolution in this revision |
|---|---|
| P0-1 the session holder chose the address for the email code | The recipient address HMAC (with its kid) is **fixed by staff when the guardian invitation is requested**, stored on the pending row, copied to the invitation and bound to the guardian respondent; a challenge may target only that hash; verify requires `challenge hash = respondent email hash` (same kid). Changing the recipient needs a staff action, a new generation and an audit row. Residual risk, stated: staff choosing an address they control is attributable, not prevented (M16b section 3) |
| P1-1 respondent guard impossible as written | Evidence-based guard (M16a section 3); `link_verified` stays an insert-time value under the existing `tenant_guard` |

| P1-3 decline evidence cannot be erased | Corrected: decline evidence lives in retained `intake_consent_evidence` and **survives erasure** (soft references); event type `declined` only |
| P1-4 M12 issuer is student-only | Internal issuer extracted; audience widening; audience-scoped generation and revocation; guardian links exist only through finalize (M16a section 2, M16b) |

| P1-6 replaced functions not listed | Full replaced-function table with markers and rollback targets (section 6) |
| P1-7 challenge design gaps | Section M16b 4 (app-supplied challenge id, outcomes returned never raised, per-respondent cap with supersede, kid on every HMAC, resolution only through the session) |

## 1. Rules inherited (unchanged)
1. A link session is never authenticated evidence; assurance stays `declared_unverified` through a link. A copy of a link never counts as guardian consent. Wording: "email verified", "declared relationship (self-attested)"; never "verified guardian". Nothing writes `client_account_links`, `appointments` or `can_sign_documents`.
2. Lock order for every writer: unlocked reads, `lock_client` (inherits the M14 READ COMMITTED guard), `request FOR UPDATE`, then the new rows, then **re-check** (session not revoked/expired, `link_valid`, request still exists with the barrier and drift re-checked, as in M15 rev 4). Every writer also has an entry-point isolation check.
3. M14: new tables are resolved by `delete_guard` through the request (fail closed 42501), removed by the replaced erase and purge, hold-protected; every new audit event carries `client_ref`.
4. Every new function: explicit `REVOKE ALL … FROM public, anon, authenticated, service_role, intake_destructive` then explicit grants; pinned search path; privilege tests by catalog (never by calling a refused function on the local QA image, which crashes it).
5. Each new function returns `gate_closed` **before** any insert while Gate A is closed (`collection_gate` would raise 42501 and `intake_rate_limit_hit` would return false, which would otherwise surface as `limited`).

## 2. M16a: guardian audience, evidence-based respondent guard, erase/purge, staff attestation (level 12)
1. **Audience widening.** `intake_invitations.audience` and `intake_sessions.audience` CHECKs accept `guardian`; the `issued_by` CHECK gains `two_party`. The M12 internal issuer is extracted as `intake_private.issue_invitation_impl(…, audience, issued_by, issued_by_user, …)`; `public.intake_issue_invitation` becomes a thin wrapper that **refuses `audience = 'guardian'`** (so guardian links exist only through finalize, M16b); `intake_next_invitation_generation`, generation numbering, invitation revocation and session revocation are **scoped by audience** (issuing a student link no longer revokes a guardian session). Replaced with `nsi-body:m16`; the rollback restores the exact M12 bodies and is refused once any guardian-audience invitation or session exists.
2. **Audit.** `intake_audit_events.event_type` CHECK is widened (`guardian_invitation_requested`, `guardian_invitation_issued`, `guardian_email_challenge_issued`, `guardian_email_verified`, `guardian_attested`, `guardian_declined`) and `audit_write`'s metadata allowlist gains `method`, `staff_minted`, `reason_code` already exists; no key carries an address, code or token. Replaced `audit_write` carries `nsi-body:m16`; rollback restores the exact M2 body and is refused once any new event type exists.
3. **Evidence-based respondent guard.** `respondents_guard` (replaced) allows an UPDATE of `assurance` only for `declared_unverified → email_code_verified` when a consumed challenge exists for that respondent whose email hash equals the respondent's `email_hmac` (same kid), and for `declared_unverified → staff_attested` when an attestation row exists for that respondent; nothing else, and `assurance_at` only with those. INSERT of `email_code_verified` or `staff_attested` stays refused by `tenant_guard`; `link_verified` stays an insert-time value set by `intake_save_draft` through a verified link (existing path unchanged). The guard is about *other definer functions*, since no role has table DML grants; the test is "a definer function or postgres updating without an evidence row is refused". Rollback restores the exact M3 bodies. The revalidation of assurance at read time (A4) is **not** claimed: `fulfillment_state` reads the stored value, and A4 stays a documented limitation until a later slice.
4. **Erase and purge.** `erase_client_impl` and `purge_expired_impl` are replaced under the restricted role (the M14 pattern: temporary CREATE grant, ownership by `intake_destructive`, then revoke) with markers m14 → m16. Delete order for a client: challenges, attestations, pending invitation requests, **then** sessions and invitations (`finalized_invitation_id` references invitations), then everything the M14 implementation already deletes, all before `intake_requests`. New tables have `intake_destructive` SELECT and DELETE grants and `_destructive_select` / `_destructive_delete` policies (the M12 pattern). Purge adds expired challenges and unfinalized, expired pending requests to the candidate union (so their clients are try-locked) with the same held-client pre-filter and ordered deletes. Attestations: **retained with the request until erase** (no separate purge period; a retention period is an I6 decision, listed as an open item). Rollback restores the exact M14 bodies and ownership.
5. **Staff attestation (L0).** `intake_attest_guardian(studio, request, respondent, method, relationship, reason)`: authenticated, `assert_staff(…, 'attest')` (an existing capability: owner, admin, front desk). Writes the immutable attestation row (method `in_person` or `phone_verified`, relationship word, reason, attesting staff user; **no name or address column**, so nothing personal is stored beyond the staff user) and, in the same transaction, sets `staff_attested` through the guard path. If the guardian has not opened the link and no guardian respondent exists, attest **refuses** (`no_respondent`); creating a respondent for an absent person is a separate decision (open item). Audited `guardian_attested` with `method`.
6. **Capabilities.** No new capability: `attest` for attestation, `send` for the guardian invitation request (the current matrix; `designate_guardian` for front desk stays gated by the existing `front_desk_guardian_selection` setting). O2 therefore does not block SQL.
7. **Tables (level 12; RLS enabled, no API grants):** `intake_guardian_attestations` (id, studio_id, request_id, respondent_id, method, relationship, reason, attested_by, attested_at; fully immutable: update and delete refused except through the erase path under `intake_destructive`; `collection_gate('continuing')`, tenant guard (respondent belongs to the request, role guardian, same studio), no-truncate, `delete_guard`).

## 3. M16b: two-party guardian issue and email challenge (level 12)
1. **Pending request.** `intake_guardian_invitation_requests` (id, studio_id, request_id, respondent_id nullable until finalize, `recipient_email_hmac bytea` + `recipient_kid text` **set by staff at request time**, requested_by, requested_at, `expires_at` (15 minutes), `finalized_invitation_id`, `finalized_at`, `superseded_at`). Uniqueness: `unique (request_id) where finalized_at is null and superseded_at is null` (no `now()` in the index); a new request supersedes the open one explicitly under the client lock, and expired unfinalized rows are purged. `collection_gate('new_obligation')`; delete order as in M16a 4.
2. **Request RPC** `intake_guardian_request_invitation(studio, request, recipient_email_hmac, recipient_kid)`: authenticated, `assert_staff('send')`; requires the latest determination to be `minor` (via `fulfillment_state`'s source of truth, not the app), the request open, Gate A open (else `gate_closed`); writes the pending row; audit `guardian_invitation_requested` (no address). The address HMAC is computed by the app (the database cannot HMAC); the staff UI never receives a token.
3. **Finalize RPC** `intake_guardian_finalize_invitation(p_pending_id, p_invitation_id, p_generation, p_kid, p_token_salt, p_token_hash, p_expires_at)`: **service_role only** (the full M12 parameter set plus the pending id, so the ambiguity of revision 1 is gone). Re-checks, after the client lock: pending row not expired/superseded/finalized, request open, latest determination still `minor`; creates the guardian-audience invitation through the internal issuer with `issued_by = 'two_party'` and the recipient hash copied onto the invitation; marks the pending row finalized; audit `guardian_invitation_issued` (staff user from the pending row). **Residual risk, stated:** a staff member who chooses a recipient address they control can still receive the code; this is attributable (audit names the requester) but not prevented; and while delivery is copy-link only the staff UI would show the token, so prevention rests on the email code bound to the staff-recorded recipient.
4. **Email challenge** `intake_email_challenges` (id **supplied by the app**, so the code can be derived from it: `deriveEmailCode(secret, challenge id)`; studio_id, request_id, respondent_id, `email_hmac` + `kid` copied from the invitation's recipient (never from the caller), `code_hash` (HMAC of the code, never the code), `expires_at` (10 minutes), `attempts int` (max 5), `consumed_at`, `superseded_at`, `created_at`). Immutability trigger: only `attempts` (increasing by exactly one) and `consumed_at` (once) change.
   - `intake_issue_email_challenge(p_session_hash, p_challenge_id, p_code_hash, p_ip_bucket bytea, p_email_bucket bytea)`: service_role; audience `guardian`; the target address is the invitation's bound hash (no caller-supplied address, which closes the P0); a new challenge **supersedes** the open one (so attempts × N cannot multiply the guessing budget) and at most N issues per respondent per hour are allowed via the M12 rate-limit buckets whose hashes the app passes in; returns the outcome word only. No student-email comparison exists any more (the recipient is fixed by staff), so the same-email oracle disappears; the staff request refuses a recipient equal to the student respondent's `email_hmac` (same kid) only inside the staff-authenticated RPC.
   - `intake_verify_email_challenge(p_session_hash, p_challenge_id, p_code_hash)`: service_role; resolves the challenge **only through the session's request and respondent** (a foreign or unknown id returns `invalid` without incrementing, so nobody can burn another person's attempts); under the client lock, increments `attempts` first and **returns** an outcome (`ok`, `invalid`, `expired`, `locked`, `superseded`) and never raises after the increment (a raise would roll the increment back); on a match requires `challenge hash = respondent email_hmac` (same kid), consumes the challenge and sets `email_code_verified` through the guard path (M16a 3); audit `guardian_email_verified` (no email, no code).
   - Every HMAC column stores its `kid`; the HKDF subkey for email HMACs is separate from the invitation-token key (TS side, documented in the notes).
5. **`link_valid` for guardians.** A guardian-audience link is valid only while the latest determination is `minor` **and** the request is open (re-checked at finalize and again at each guardian read); if staff override to adult, the guardian link stops working (revoked at the override by the existing override function's call path in I3-4, and refused at read time here). The converse case (completed while adult, later overridden to minor) leaves a `submitted` request that `link_valid` already refuses; its handling is an I3-4 question, recorded as open.

## 4. M16c: guardian decline (level 12; O4 [recommended, pending owner decision: terminal per request])
1. **State machine.** `intake_requests.status` CHECK gains `declined`; `requests_guard` allows `invited | in_progress → declined` and `declined →` nothing; `intake_requests_one_open` already excludes it (no index change). `link_valid`, `responses_guard`, `save_draft` and submit already refuse non-open statuses, so the revocation in the decline RPC is defense in depth. "Terminal" means terminal for **that request**: the evaluator suppresses new requests only through completions and open statuses, so a later qualifying appointment creates a **new** request. That behavior is the O4 consequence, stated, not hidden.
2. **`fulfillment_state`** (replaced again, marker m16, `c_guard` level 12): a `declined` request returns `declined` (branch before the completion check); everything else as M15.
3. **Decline RPC** `intake_guardian_decline(p_session_hash, p_reason_code)`: service_role; Gate A open else `gate_closed`; guardian session; requires a non-superseded guardian **respondent of the session's request** with assurance rank ≥ 2 (email verified) or an attestation row (assurance lives on the respondent, not the session); allowed from `invited` or `in_progress` only; moves the request to `declined`, revokes its invitations and sessions (all audiences), records decline evidence, audit `guardian_declined` with `reason_code` from a fixed list.
4. **Decline evidence** is a row in `intake_consent_evidence` with `event_type = 'declined'` (never `attested`, which `fulfillment_state` counts as consent), `required_assurance`, the pinned `template_version_ref`, a non-empty `consent_text` that is the decline wording (versioned like consent text), under the existing evidence guards and platform policy. **Retained evidence survives erasure** (soft references, as for all consent evidence); the tests assert that survival, not removal.

## 5. Outcome vocabulary (scoped)
New functions (M16a/b/c) return from one set: `ok`, `invalid`, `expired`, `locked` (attempts exhausted; never confused with SQLSTATE 55P03), `superseded`, `limited`, `not_open`, `gate_closed`, `erasure_barrier`, `no_respondent`, `already_done`, `declined`. Shipped words of M12 and M15 (`request_not_open`, `birthday_used`, `already_determined`, `invalid`, and the empty result of exchange and `session_context`) are **not** renamed; unifying them is a later cosmetic change with marker bumps. Error classes keep SQLSTATEs (22023, 42501, 55P03, 55000).

## 6. Replaced functions and catalog (all with `nsi-body:m16`, a `c_guard` entry, and rollback to the exact prior body)
`public.intake_issue_invitation` and `intake_private`-side generation helper (M12), `public.intake_next_invitation_generation` (M12), `intake_private.requests_guard` and `intake_private.respondents_guard` (M3), `intake_private.erase_client_impl` and `intake_private.purge_expired_impl` (M14), `intake_private.audit_write` (M2), `intake_private.fulfillment_state` (M15 entry `…|nsi-body:m15|11` becomes `m16|12`), and, only if needed, `intake_private.link_valid` (M12). New objects (level 12): tables `intake_guardian_attestations`, `intake_guardian_invitation_requests`, `intake_email_challenges` (each with the gate, tenant, delete, no-truncate and immutability triggers and the two destructive policies), the internal issuer, the RPCs above. The function count is computed by the generator (110 plus the new objects), `assert_catalog` presence levels extend 1..11 to 1..12 with the c_rel/c_fn/c_trg/c_pol entries, and each slice's rollback restores the exact prior `assert_catalog` and fingerprint (M16a to the M15 value `3fc0eea4…|776`). **Rollback refusals:** any new event type, guardian-audience invitation or session, non-M3 assurance value, challenge, attestation, pending request or `declined` request; table lock first; replay guard refusing when any later marker exists; the M15 rollback and replay guards already refuse over M16 markers.

## 7. Tests (per slice; suite, lifecycle with mutation probes, race harness, DEV-safe)
- **M16a:** audience-scoped generation/revocation (a student issue does not revoke a guardian session); guardian direct issue refused; guard allows only the evidence-based transitions and refuses a definer update without evidence; erase of a client with a challenge, attestation and pending request succeeds (no 23503) in the right order; purge clears expired rows and skips held clients; attestation role matrix (`attest`: owner/admin/front desk yes; instructor, other studio, anon no), mandatory reason, immutability, `no_respondent`; gate-closed ordering; markers, fingerprint, rollback refusals and exact restoration.
- **M16b:** recipient bound at request and copied; challenge can target only the bound hash; verify requires hash equality (same kid); attempts committed on a wrong code (outcome returned, no raise); foreign challenge id does not increment; supersede and per-respondent cap; expiry; consume once; no personal value anywhere; finalize re-checks (pending expired/superseded, determination no longer minor, request closed); lock-order checks and a race for verify vs decline, finalize vs revoke, attest vs decline; REPEATABLE READ refusals; probes for each removed check.
- **M16c:** every allowed and refused transition; decline needs verified assurance or an attestation; not completion; evaluator creates a new request after a decline (O4 consequence asserted); `fulfillment_state` declined; evidence survives erasure and carries `declined`; revocation of sessions and invitations; rollback refused once a declined request exists.

## 8. Owner decisions and open items
O4 (decline terminal per request) affects M16c only. O2 is resolved by reusing existing capabilities. O11, O5b and P1-A rule 4 are not touched. Open items, not blocking: creating a guardian respondent for an absent guardian through attestation; a retention period for attestations (I6); A4 read-time revalidation; the "completed while adult, later minor" case (I3-4); copy-link prevention only holds through the email code until delivery exists (T1 to T4, M-0).

## 9. What the next review should check
That the recipient binding closes the P0 without the session holder choosing any address; that the evidence-based guard cannot be bypassed by the replaced erase/purge or any other definer function; the erase/purge delete order against every foreign key; the audience-scoped revocation semantics; and the M16a rollback exactness against M2, M3, M12 and M14 bodies.
