# NSI I3-2 (M16b) database specification: two-party guardian invitation and recipient-bound email challenge (revision 1, for review before any SQL)

Status: **specification only.** No SQL, code, flag, env or email is authorized by this document. Gate A stays closed; no billing gating (pilot grants, staff roles and Gate A only). Sits on **M16a** (applied to DEV, fingerprint `63e82e902ac004b406195a9164b944b2|807`, marker `nsi-body:m16a`); the precondition guard accepts the M16a marker or a later M16a.x marker. Parent: `NSI_I3_2_DB_Spec.md` revision 3 section 10.3 (the required changes this document implements). **Nothing here depends on the unresolved drafts** P1-A rule 4, O11, O5b, or on O4 (decline is M16c). Owner-decision labels **[recommended, pending owner decision]** are draft defaults.

## 0. The threat and what the database can and cannot do
The P0 of the first review: whoever holds a guardian link must not be able to choose the address that receives the email code. The database never sends mail and cannot compute an HMAC. The closure is therefore split:
- **Database (this spec):** staff fix the recipient address HMAC when they request the invitation; it is copied onto the invitation; a challenge may be issued, and verified, only for a guardian respondent whose stored `email_hmac` and `email_hmac_kid` **equal the bound recipient**; a wrong value gives the same outcome word as any other refusal.
- **App (required conditions, tested on the TypeScript side, stated here so they are not forgotten):** (a) `email_hmac` is computed on the server from the normalized address and never accepted from a client; (b) the code is sent only to the address from which that same HMAC was computed; (c) the bound hash and the recipient address are never shown to a client; (d) one canonical normalization (trim, Unicode NFKC, lower-case, plus-tag rule decided once) and one HKDF subkey for email HMACs, separate from the invitation-token key.
- **Structural fix, preferred and owned by I3-4:** a session-bound guardian `save_draft` that sets the guardian respondent's `email_hmac` from the invitation itself, so no caller ever supplies one. **M16b stays dark and is not activated before that exists or before conditions (a) to (d) are verified.** `intake_save_draft` today is service-role, not session-bound (`NSI_I3_1_DB_Spec.md` line 77); this dependence is explicit.
- **Residual risk, stated:** a staff member who records an address they control receives the code. It is attributable (the audit names the requester) and not prevented. While delivery is copy-link only (before T1 to T4 and the M-0 close-out) the link and code are shown to the requesting staff session by the app, so prevention rests on the code binding alone.

## 1. Rules inherited (unchanged)
A link session is never authenticated evidence; assurance stays `declared_unverified` through a link; a copy of a link never counts as guardian consent. Wording: "email verified", "declared relationship (self-attested)"; nothing writes `client_account_links`, `appointments` or `can_sign_documents`. Lock order for every writer: unlocked reads, `lock_client` (M14 READ COMMITTED guard), `request FOR UPDATE`, new rows, then re-check (session, `link_valid`, request re-read with barrier and drift) after the lock; every writer also has an entry-point isolation check and returns `gate_closed` before any insert. Every function: explicit `REVOKE ALL … FROM public, anon, authenticated, service_role, intake_destructive` then explicit grants, pinned search path. Privilege tests are by catalog (a refused call crashes the local QA image). Every audit event carries `client_ref`.

## 2. Schema changes (level 13)
1. **`intake_invitations`** gains `recipient_email_hmac text null` (max 128, as the respondent column), `recipient_email_hmac_kid smallint null`. The `audience` CHECK accepts `guardian`; `issued_by` accepts `two_party`. New CHECK: `(audience = 'guardian') = (recipient_email_hmac is not null and recipient_email_hmac_kid is not null and issued_by = 'two_party')`. `invitations_update_guard` (replaced) makes the two recipient columns immutable. `intake_sessions.audience` accepts `guardian`.
2. **`intake_guardian_invitation_requests`** (pending requests; the two-party handshake): `id`, `studio_id`, `request_id`, `client_id`, `recipient_email_hmac text`, `recipient_email_hmac_kid smallint`, `requested_by uuid`, `requested_at`, `expires_at` (15 minutes), `finalized_invitation_id uuid null`, `finalized_at`, `superseded_at`. Partial unique index on `(request_id) where finalized_at is null and superseded_at is null` (no `now()` in the index; expiry is checked in code). `collection_gate('new_obligation')`; insert guard (request in studio and client, request open, recipient columns present); update guard: only `finalized_*` once and `superseded_at` once change; `delete_guard`; no-truncate; destructive-role `SELECT`/`DELETE` and the two policies. FK: `finalized_invitation_id → intake_invitations (studio_id, id)` **restrict**.
3. **`intake_email_challenges`**: `id uuid` (supplied by the app: the code is derived from it, so the database cannot mint it), `studio_id`, `request_id`, `client_id`, `respondent_id`, `invitation_id`, `email_hmac text`, `email_hmac_kid smallint` (copied from the invitation's recipient, never from the caller), `code_hash bytea` (32-byte HMAC of the code; the code is never stored), `expires_at` (issue + 10 minutes), `attempts smallint` (0 to 5), `consumed_at`, `superseded_at`, `created_at`. Update guard: only `attempts` (increase by exactly one, never above 5), `consumed_at` (once, only when `attempts <= 5`) and `superseded_at` (once) change. Insert guard: respondent is the request's current guardian respondent; hmac equals the respondent's; invitation is the live guardian invitation. `collection_gate('continuing')`, `delete_guard`, no-truncate, destructive `SELECT`/`DELETE` and policies. FKs restrict: respondent, request, **no foreign key to sessions or invitations other than `invitation_id → intake_invitations` (restrict)**, so purge ordering below applies.
4. **Audit:** the event-type CHECK gains `guardian_invitation_requested`, `guardian_invitation_issued`, `guardian_email_challenge_issued`, `guardian_email_verified`. No new metadata key (`audience` and `generation` are already allowed); no address, hash, code or token appears in any audit row, return value or error text.

A respondent already at rank 2 or higher returns `already_done` before any increment |
| `intake_private.pending_*_guard`, `challenge_*_guard`, trigger functions | none | Insert and update guards of the two new tables (section 2) |

## 4. Replaced functions (each with `nsi-body:m16b`, a `c_guard` entry at level 13, and rollback to the exact prior body)
- `intake_private.respondents_guard` (M16a body): adds `declared_unverified → email_code_verified` only when a **consumed** challenge exists for that respondent whose `email_hmac` and kid equal the respondent's; `staff_attested` still needs an attestation; `assurance_at` moves only with an allowed change; nothing else changes. `email_hmac` may still never go from null to a value or be changed once set.
- `intake_private.link_valid` (M12 body): guardian branch — a guardian invitation is valid only while the latest determination is minor and the request is open; everything else as M12. (Student branch byte-identical.)
- `intake_private.invitations_update_guard` (M12 body): recipient columns immutable.
- `public.intake_issue_invitation` (M12 body, **signature unchanged**; no second overload, which `assert_catalog` would flag): the only change is that its session revocation is `and s.audience = 'student'` (M12 revokes sessions of every audience on a student re-issue; with guardian sessions that is wrong). The staff revoke-all (`intake_revoke_invitations`) and the key-rotation revoke stay all-audience (a deliberate "stop everything"). `intake_next_invitation_generation` stays student-only.
- `intake_private.erase_client_impl` (M16a body) and `intake_private.purge_expired_impl` (M14 body), both under the restricted role (the M14 pattern).
  - **Erase order (complete):** completions, response revisions, responses, **challenges, pending requests (before invitations, `finalized_invitation_id` restrict), attestations**, respondents, determinations, request appointments, sessions, invitations, requests, designations, relationship state.
  - **Purge:** challenges expired and unconsumed more than 24 hours; unfinalized or superseded pending rows past expiry; **finalized pending rows whose invitation is purge-eligible are deleted before that invitation** (otherwise the invitation delete would raise 23503 and abort the whole purge for every studio); consumed challenges and attestations are **kept until erase** (they are the evidence behind the stronger assurance). The new tables enter the purge candidate union so their clients are try-locked with the same held-client pre-filter and ordered deletes (M14).
- `intake_private.audit_write`: unchanged (no new key). The audit event-type CHECK is replaced (M16a text plus the four new event types); `intake_private.assert_catalog` (level 13).

## 5. Catalog, rollback, replay
Level 13 entries in `c_rel` (two tables, grants `intake_destructive:DELETE,SELECT`), `c_fn`, `c_trg`, `c_pol`, `c_guard`; the presence loop extends to 1..13; the function count and fingerprint are computed by the generator run. Rollback restores the exact M16a bodies of every replaced function and the M16a event-type CHECK and `assert_catalog`; it is **refused** once any pending request, challenge, guardian-audience invitation or session, `email_code_verified` respondent, or any of the four new event types exists; table lock first; replay guard refuses when an `m16c`-or-later marker exists; the M16a replay and rollback already refuse over an `m16b` marker.

## 6. Tests
Suite: recipient bound at request and copied to the invitation; a respondent with a different hmac or kid cannot get or verify a challenge (same `invalid` word, no write); `same_as_student` and `recipient_link_set` only for authenticated staff; supersede of the open pending row, guardian respondent and draft on re-request; finalize re-checks (pending expired, superseded or finalized; determination no longer minor; request closed; generation scoped to guardian; student invitation and session untouched); verify (correct code consumes and promotes; wrong code increments and **commits** with `invalid`; fifth wrong code then `locked`; expired and superseded without increment; foreign challenge id does not increment; consumed cannot be reused; `already_done`); per-respondent issue cap from rows; new challenge supersedes the open one; guard allows only the evidence-based transitions; `email_hmac` still immutable; guardian link stops when the determination becomes adult; student re-issue no longer revokes a guardian session; erase of a client with pending rows, challenges, attestations and invitations succeeds in the stated order; purge deletes finalized pending rows before invitations and keeps consumed challenges and attestations; audit shape (client_ref, audience, generation, no personal values); catalog (inventory, markers, ACLs, `assert_catalog`). Lifecycle with a mutation probe for every check above; race harness: finalize vs revoke, verify vs verify (attempt accounting never loses an increment), verify vs erase (both interleavings), request vs request (one open pending row), isolation levels; DEV-safe level-13 suite; full-chain replay on the final bytes; independent review before any DEV apply.

## 7. Dependencies, open items, what is not decided here
Depends on: M16a on the target; I3-4 session-bound guardian save for the structural closure (section 0); email delivery (T1 to T4, M-0 close-out) before any code is sent; none of these is started. Not decided here: a retention period for consumed challenges and attestations (I6); whether a guardian respondent may be created by attestation for an absent guardian (M16a returns `no_respondent`); the "completed while adult, later overridden to minor" case (I3-4); decline (M16c, O4).

## 8. What the review should check
That the recipient binding closes the P0 given the stated app conditions and cannot be defeated by any database path (including `intake_save_draft` supplying a different hmac, a superseded respondent, a re-request race, or an attestation on the same respondent); the supersede-on-re-request semantics against `responses_guard` and the submit paths; the erase and purge orders against every foreign key; the audience-scoped revocation and `link_valid` guardian branch against exchange and session context; attempt accounting under concurrency; and that the replaced-function list and rollback exactness are complete.
