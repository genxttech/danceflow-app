## 0. The threat and what the database can and cannot do
The P0 of the first review: whoever holds a guardian link must not be able to choose the address that receives the email code. The database never sends mail and cannot compute an HMAC. The closure is therefore split:
- **Database (this spec):** staff fix the recipient address HMAC when they request the invitation; it is copied onto the invitation; a challenge may be issued, and verified, only for a guardian respondent whose stored `email_hmac` and `email_hmac_kid` **equal the bound recipient**; a wrong value gives the same outcome word as any other refusal.
- **App (required conditions, tested on the TypeScript side, stated here so they are not forgotten):** (a) `email_hmac` is computed on the server from the normalized address and never accepted from a client; (b) the code is sent only to the address from which that same HMAC was computed; (c) the bound hash and the recipient address are never shown to a client; (d) one canonical normalization (trim, Unicode NFKC, lower-case, plus-tag rule decided once) and one HKDF subkey for email HMACs, separate from the invitation-token key.
- **Structural fix, owned by I3-4 (Option B, section 11):** a session-bound guardian save in which the guardian types the address, the server computes its HMAC, and the respondent is created only when it equals the bound recipient. **M16b stays dark and is not activated before that exists or before conditions (a) to (d) are verified.** `intake_save_draft` today is service-role, not session-bound (`NSI_I3_1_DB_Spec.md` line 77); this dependence is explicit.
- **Residual risk, stated:** a staff member who records an address they control receives the code. It is attributable (the audit names the requester) and not prevented. While delivery is copy-link only (before T1 to T4 and the M-0 close-out) only the link is shown to the requesting staff session by the app (never a code, section 10.1), so prevention rests on the code binding alone.

## 1. Rules inherited (unchanged)
A link session is never authenticated evidence; assurance stays `declared_unverified` through a link; a copy of a link never counts as guardian consent. Wording: "email verified", "declared relationship (self-attested)"; nothing writes `client_account_links`, `appointments` or `can_sign_documents`. Lock order for every writer: unlocked reads, `lock_client` (M14 READ COMMITTED guard), `request FOR UPDATE`, new rows, then re-check (session, `link_valid`, request re-read with barrier and drift) after the lock; every writer also has an entry-point isolation check and returns `gate_closed` before any insert. Every function: explicit `REVOKE ALL … FROM public, anon, authenticated, service_role, intake_destructive` then explicit grants, pinned search path. Privilege tests are by catalog (a refused call crashes the local QA image). Every audit event carries `client_ref`.

## 2. Schema changes (level 13)
1. **`intake_invitations`** gains `recipient_email_hmac text null` (max 128, as the respondent column), `recipient_email_hmac_kid smallint null`. The `audience` CHECK accepts `guardian`; `issued_by` accepts `two_party`. 2. **`intake_guardian_invitation_requests`** (pending requests; the two-party handshake): `id`, `studio_id`, `request_id`, `client_id`, `recipient_email_hmac text`, `recipient_email_hmac_kid smallint`, `requested_by uuid`, `requested_at`, `expires_at` (15 minutes), `finalized_invitation_id uuid null`, `finalized_at`, `superseded_at`. Partial unique index on `(request_id) where finalized_at is null and superseded_at is null` (no `now()` in the index; expiry is checked in code). `collection_gate('new_obligation')`; insert guard (request in studio and client, request open, recipient columns present); update guard: only `finalized_*` once and `superseded_at` once change; `delete_guard`; no-truncate; destructive-role `SELECT`/`DELETE` and the two policies. FK: `finalized_invitation_id → intake_invitations (studio_id, id)` **restrict**.
3. **`intake_email_challenges`**: `id uuid` (supplied by the app: the code is derived from it, so the database cannot mint it), `studio_id`, `request_id`, `client_id`, `respondent_id`, `invitation_id`, `email_hmac text`, `email_hmac_kid smallint` (copied from the invitation's recipient, never from the caller), `code_hash bytea` (32-byte HMAC of the code; the code is never stored), `expires_at` (issue + 10 minutes), `attempts smallint` (0 to 5), `consumed_at`, `superseded_at`, `created_at`. Update guard: only `attempts` (increase by exactly one, never above 5), `consumed_at` (once, only when `attempts <= 5`) and `superseded_at` (once) change. Insert guard: respondent is the request's current guardian respondent; hmac equals the respondent's; invitation is the live guardian invitation. `collection_gate('continuing')`, `delete_guard`, no-truncate, destructive `SELECT`/`DELETE` and policies. FKs restrict: respondent, request, **no foreign key to sessions or invitations other than `invitation_id → intake_invitations` (restrict)**, so purge ordering below applies.
4. **Audit:** the event-type CHECK gains `guardian_invitation_requested`, `guardian_invitation_issued`, `guardian_email_challenge_issued`, `guardian_email_verified`. No new metadata key (`audience` and `generation` are already allowed); no address, hash, code or token appears in any audit row, return value or error text.

## 9. Revision 2 (after the review of revision 1: NO-GO as written, CONDITIONAL GO once these changes are in; a diff check of this revision against the list is enough). This section governs where it conflicts with sections 0 to 8.

### 9.1 P0: bind the address the code is SENT to, not only the stored hash
The database cannot see the address a code is mailed to, and `intake_save_draft` takes `email` and `email_hmac` as independent fields. So `intake_issue_email_challenge` gains two parameters: `p_send_to_email_hmac text, p_send_to_kid smallint`. It returns `invalid` unless they equal the invitation's recipient **and** the respondent's stored hash and kid. App rule (e1): compute that HMAC in the same request handler, from the exact normalized address the code is then sent to; the send-to address is never read back from a client. No copy of the staff-recorded address is stored beyond its keyed hash (Option B). The "structural fix" is reworded: I3-4's session-bound guardian save takes the typed address, normalizes it server-side, computes its HMAC with the key id recorded on the invitation, and sets the respondent's `email` AND `email_hmac` from that one computation only when it equals the bound recipient; it never copies a hash onto a respondent whose address it did not compute. Refused issues (`invalid`, `limited`) are counted in a database-computed bucket (per respondent, from challenge and refusal rows) so issue cannot become an unlimited "is it this address" oracle.

### 9.2 P1 changes
1. **Re-request stops the old link.** The request RPC, under the client lock, **revokes the current guardian invitations and guardian sessions immediately** (reason `resent`), supersedes the open pending row, the current unsubmitted guardian respondent and draft **and open challenges**. Finalize supersedes again any unsubmitted guardian respondent, draft and open challenge that appeared in the interval. Issue and verify require `challenge.invitation_id = session.invitation_id` and that the invitation is the latest guardian generation. The guard additionally requires the consumed challenge's invitation to be the latest live-or-used guardian generation for the request.
2. **Purge cannot abort on retained challenges.** The invitation purge (candidate union and delete) excludes invitations referenced by any challenge or finalized pending row (`and not exists (select 1 from intake_email_challenges c where c.invitation_id = x.id)` and the same for pending rows) **or** the references are deleted first in the same statement set; the eligible invitation set is computed once so pending rows and invitations work on exactly the same set under the purge limit. Consumed challenges and attestations remain until erase, so their invitations remain too.
3. **Finalize and request preconditions are exact.** Both require `status in ('invited','in_progress')` (a `pending` request has no pinned version and `link_valid` refuses it), `pinned_version_id is not null`, `request_has_live_target`, no submitted guardian response, `guardian_recipient_link_id is null`, and the latest determination minor. Finalize restates the M12 expiry bounds (1 hour to 30 days) and the 16-byte salt, 32-byte hash and 8-character `kid` checks, and returns the guardian generation. The request RPC **returns the next guardian generation** (`requested:<pending id>:<generation>`), so the app has the number finalize needs without a new helper.

The rollback test compares `pg_get_constraintdef` for each restored constraint (`assert_catalog` does not).

App condition (e2): guardian-audience save and submit happen only from a guardian session's context. Until then M16b stays dark. P1-A rule 3 ("staff-minted never satisfies guardian consent") is stated as **not applying to guardian sessions** (rule 5 governs: the consent basis is the challenge or attestation row).

### 9.3 P2 changes
- **Single guardian respondent is enforced:** issue and verify return `invalid` unless exactly one non-superseded guardian respondent exists; a partial unique index `(request_id) where role = 'guardian' and superseded_at is null` is added (rollback drops it).

## 10. Revision 3 (text fixes from the revision 2 re-review: CONDITIONAL GO for local-only authoring). This section governs where it conflicts with sections 0 to 9. The address-storage and governance question (P1) was decided on 2026-11-26 (Option B, section 11, `NSI_I3_2_M16b_Decision_Address_and_Sequencing.md`).

### 10.1 The code goes only to the stored guardian email
The send-to address is the current guardian respondent's stored `email`, read server-side by the app; it is **never fresh client input** and never a value returned to or edited by a browser at send time. `intake_issue_email_challenge` still requires `p_send_to_email_hmac` and `p_send_to_kid` to equal both the invitation's recipient and the respondent's stored hash, and the app computes them in the same handler from that exact normalized string. **Normalization:** trim, Unicode NFKC, lower-case; **no plus-tag stripping and no provider-specific rewriting**; the code is sent to exactly the normalized string that was hashed. **Codes are never returned to, shown to or recoverable by any staff session** (only the link may be shown to the requesting staff session while delivery is copy-link only); this replaces the "link and code are shown" sentence of section 0. If the code is derived from the challenge id, the derivation is **keyed** with its own HKDF subkey (separate from the token and email-HMAC subkeys); otherwise the code is random.

### 10.2 Challenge retention and the guessing budget
Challenges are **kept while their invitation is the latest guardian generation and is neither revoked nor expired**; an unconsumed challenge becomes purge-eligible only 24 hours after both its own expiry and that invitation's revocation or expiry. So the lifetime cap of 50 challenges per invitation is counted from rows that still exist. Consumed challenges are kept until erase. Caps (all counted from challenge rows under the client lock): 5 issues per 60 minutes and 10 per 24 hours per respondent, 50 per invitation, 5 attempts per challenge. With 8-digit codes the worst case per invitation is 250 guesses; the notes record that bound.

### 10.3 Issue-attempt bucket (defined)
Issue attempts are counted with the existing M12 mechanism, not a new table. After the session and respondent checks and **before any comparison**, the database computes `sha256(convert_to('intake/challenge-issue/v1|' || respondent_id::text, 'UTF8'))` (the request id when there is no single respondent) and calls `intake_rate_limit_hit` for **both** windows (5 per 3600 seconds and 20 per 86400 seconds, the function's window maximum), every attempt. Over either limit the outcome is `limited` and nothing is compared. `gate_closed` is returned before any call. The counter rows follow the M14 rate-limit purge.

### 10.4 Purge (replaces the wording of 9.2 item 2)
The exclusion is **mandatory, not an alternative**: both the invitation candidate union and the invitation delete carry `not exists` predicates for **every** referencing row (challenges, and pending rows by `finalized_invitation_id`), so rows retained until erase never occupy the oldest-first candidate window. The "eligible set computed once" claim is dropped (the M14 body recomputes each delete with its own limit; the mandatory exclusion makes that safe). Delete order inside one run: eligible challenges, then eligible pending rows, then sessions, rate limits and invitations as M14. **Every new delete is filtered by the locked client set** (as the M14 deletes are), because an unlocked client would make `delete_guard` raise 55P03 and abort the whole run. A finalized pending row is purge-eligible only when no challenge references its invitation.

### 10.5 Complete rollback list
In order: refusal conditions (any pending row, challenge, guardian-audience invitation or session, `email_code_verified` respondent, any of the four new event types, any `m16c`-or-later marker, or M16b not applied); table locks; **drop the four new RPCs and every new guard function** (the pending-row and challenge insert and update guards) after dropping the two tables (`intake_email_challenges` first, then `intake_guardian_invitation_requests`); drop the partial unique index `intake_respondents_one_open_guardian`; drop CHECKs `intake_invitations_recipient_iff` and `intake_invitations_recipient_student_null` and the columns `recipient_email_hmac`, `recipient_email_hmac_kid`; restore under their exact names `intake_invitations_audience_check`, `intake_invitations_issued_by_check`, `intake_sessions_audience_check`; restore the exact bodies of M12 `link_valid`, `invitations_update_guard`, `intake_issue_invitation` and **`intake_revoke_invitations`**, M16a `respondents_guard` and `erase_client_impl`, M14 `purge_expired_impl` (both under the restricted role); restore the M16a audit event-type CHECK and `assert_catalog`; verify the M16a fingerprint. The lifecycle compares `pg_get_constraintdef` for every restored constraint and checks that the index and columns are gone (`assert_catalog` does not).
**Forward preflight:** before creating the partial unique index the migration counts requests with more than one non-superseded guardian respondent and refuses with that count if it is not zero (never silently supersedes).
**New names:** tables as in section 2; constraints `intake_invitations_recipient_iff`, `intake_invitations_recipient_student_null`; index `intake_respondents_one_open_guardian`; pending-row partial index `intake_guardian_invitation_requests_one_open`. `c_guard` entries (marker `nsi-body:m16b`, level 13) **replace** the earlier entries of `intake_issue_invitation`, `erase_client_impl`, `purge_expired_impl`, `respondents_guard` and are **added** for `link_valid`, `invitations_update_guard`, `intake_revoke_invitations`.

### 10.6 Requirements on I3-4 and on the owner (activation, recorded here so they are not lost)
- I3-4's session-bound guardian save and submit **re-check the session under the client lock** (revoked, expiry, `link_valid`), as `intake_declare_minor_status` does, so a stale save cannot recreate a respondent after a re-request and lock the legitimate guardian out.
- Whether a link counts as staff-minted is derived from **how it was issued**: `staff_minted = (issued_by = 'staff')`; `two_party` (guardian) invitations are not staff-minted even though `issued_by_user` records the requester. This changes the wording of the **draft** P1-A note ("`issued_by_user` is not null"); the change is **pending owner decision** and this spec does not apply it. Until accepted, a derivation from `issued_by_user` would mark every guardian submission as staff-assisted.

- **Refused-save bucket (Option B).** The guardian save compares inside the database function, under the client lock. Every attempt to create the guardian respondent (its address cannot be set later; a wrong address needs a staff re-request) first calls `intake_rate_limit_hit` on `sha256(convert_to('intake/guardian-save/v1|' || request_id::text, 'UTF8'))` with 5 per 3600 seconds and 20 per 86400 seconds; over either limit the outcome is `limited` and **no comparison is made**, so a correct guess cannot succeed after the limit. A mismatch returns the generic refusal and does not raise, so the count commits. Attempts are counted, not only refusals, because the existing function has no read-only check. A re-request does not reset the bucket (it is keyed by the request).
- **Address and key rules (Option B).** `email` and `email_hmac` are written together from one server-side computation and neither is changed alone; the email-HMAC key used by an unexpired invitation is retained for its life.

### 10.7 Smaller fixes
- The refusal of value-to-null on `email_hmac` applies **only on the transition to `email_code_verified`** (the new row must carry a non-null hash equal to the challenge's); the M16a allowance for later redaction by value to null is otherwise unchanged.
- New tables use composite foreign keys `(studio_id, request_id)`, `(studio_id, respondent_id)` and `(studio_id, invitation_id)` (and `(studio_id, finalized_invitation_id)`), all restrict, as M12 and M16a do.
- `intake_issue_email_challenge` returns `already_done` when the respondent's assurance rank is 2 or higher, so no pointless email is sent.
- "Latest determination" everywhere means `order by created_at desc, id desc` (M15).
- "Live-or-used generation" in the respondent guard is defined as: the consumed challenge's invitation is the highest-generation guardian invitation of the request and that invitation is not revoked.
- Finalize's second supersede (respondent, draft, open challenges) is audited with the same event and a count, as the request's is.
