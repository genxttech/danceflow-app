# NSI I3-2 (M16b) database specification: two-party guardian invitation and recipient-bound email challenge (revision 2 in section 9 governs; for a diff-check before any SQL)

Status: **specification only.** No SQL, code, flag, env or email is authorized by this document. Gate A stays closed; no billing gating (pilot grants, staff roles and Gate A only). Sits on **M16a** (applied to DEV, fingerprint `63e82e902ac004b406195a9164b944b2|807`, marker `nsi-body:m16a`); the precondition guard accepts the M16a marker or a later M16a.x marker. Parent: `NSI_I3_2_DB_Spec.md` revision 3 section 10.3 (the required changes this document implements). **Nothing here depends on the unresolved drafts** P1-A rule 4, O11, O5b, or on O4 (decline is M16c). Owner-decision labels **[recommended, pending owner decision]** are draft defaults.

## 0. The threat and what the database can and cannot do
The P0 of the first review: whoever holds a guardian link must not be able to choose the address that receives the email code. The database never sends mail and cannot compute an HMAC. The closure is therefore split:
- **Database (this spec):** staff fix the recipient address HMAC when they request the invitation; it is copied onto the invitation; a challenge may be issued, and verified, only for a guardian respondent whose stored `email_hmac` and `email_hmac_kid` **equal the bound recipient**; a wrong value gives the same outcome word as any other refusal.
- **App (required conditions, tested on the TypeScript side, stated here so they are not forgotten):** (a) `email_hmac` is computed on the server from the normalized address and never accepted from a client; (b) the code is sent only to the address from which that same HMAC was computed; (c) the bound hash and the recipient address are never shown to a client; (d) one canonical normalization (trim, Unicode NFKC, lower-case, plus-tag rule decided once) and one HKDF subkey for email HMACs, separate from the invitation-token key.
- **Structural fix, preferred and owned by I3-4:** a session-bound guardian `save_draft` that sets the guardian respondent's `email_hmac` from the invitation itself, so no caller ever supplies one. **M16b stays dark and is not activated before that exists or before conditions (a) to (d) are verified.** `intake_save_draft` today is service-role, not session-bound (`NSI_I3_1_DB_Spec.md` line 77); this dependence is explicit.
- **Residual risk, stated:** a staff member who records an address they control receives the code. It is attributable (the audit names the requester) and not prevented. While delivery is copy-link only (before T1 to T4 and the M-0 close-out) the link and code are shown to the requesting staff session by the app, so prevention rests on the code binding alone.

## 1. Rules inherited (unchanged)
A link session is never authenticated evidence; assurance stays `declared_unverified` through a link; a copy of a link never counts as guardian consent. Wording: "email verified", "declared relationship (self-attested)"; nothing writes `client_account_links`, `appointments` or `can_sign_documents`. Lock order for every writer: unlocked reads, `lock_client` (M14 READ COMMITTED guard), `request FOR UPDATE`, new rows, then re-check (session, `link_valid`, request re-read with barrier and drift) after the lock; every writer also has an entry-point isolation check and returns `gate_closed` before any insert. Every function: explicit `REVOKE ALL … FROM public, anon, authenticated, service_role, intake_destructive` then explicit grants, pinned search path. Privilege tests are by catalog (a refused call crashes the local QA image). Every audit event carries `client_ref`.

## 2. Schema changes (level 13)
1. **`intake_invitations`** gains `recipient_email_hmac text null` (max 128, as the respondent column), `recipient_email_hmac_kid smallint null`. The `audience` CHECK accepts `guardian`; `issued_by` accepts `two_party`. New CHECK: `(audience = 'guardian') = (recipient_email_hmac is not null and recipient_email_hmac_kid is not null and issued_by = 'two_party')`. `invitations_update_guard` (replaced) makes the two recipient columns immutable. `intake_sessions.audience` accepts `guardian`.
2. **`intake_guardian_invitation_requests`** (pending requests; the two-party handshake): `id`, `studio_id`, `request_id`, `client_id`, `recipient_email_hmac text`, `recipient_email_hmac_kid smallint`, `requested_by uuid`, `requested_at`, `expires_at` (15 minutes), `finalized_invitation_id uuid null`, `finalized_at`, `superseded_at`. Partial unique index on `(request_id) where finalized_at is null and superseded_at is null` (no `now()` in the index; expiry is checked in code). `collection_gate('new_obligation')`; insert guard (request in studio and client, request open, recipient columns present); update guard: only `finalized_*` once and `superseded_at` once change; `delete_guard`; no-truncate; destructive-role `SELECT`/`DELETE` and the two policies. FK: `finalized_invitation_id → intake_invitations (studio_id, id)` **restrict**.
3. **`intake_email_challenges`**: `id uuid` (supplied by the app: the code is derived from it, so the database cannot mint it), `studio_id`, `request_id`, `client_id`, `respondent_id`, `invitation_id`, `email_hmac text`, `email_hmac_kid smallint` (copied from the invitation's recipient, never from the caller), `code_hash bytea` (32-byte HMAC of the code; the code is never stored), `expires_at` (issue + 10 minutes), `attempts smallint` (0 to 5), `consumed_at`, `superseded_at`, `created_at`. Update guard: only `attempts` (increase by exactly one, never above 5), `consumed_at` (once, only when `attempts <= 5`) and `superseded_at` (once) change. Insert guard: respondent is the request's current guardian respondent; hmac equals the respondent's; invitation is the live guardian invitation. `collection_gate('continuing')`, `delete_guard`, no-truncate, destructive `SELECT`/`DELETE` and policies. FKs restrict: respondent, request, **no foreign key to sessions or invitations other than `invitation_id → intake_invitations` (restrict)**, so purge ordering below applies.
4. **Audit:** the event-type CHECK gains `guardian_invitation_requested`, `guardian_invitation_issued`, `guardian_email_challenge_issued`, `guardian_email_verified`. No new metadata key (`audience` and `generation` are already allowed); no address, hash, code or token appears in any audit row, return value or error text.

## 4. Replaced functions (each with `nsi-body:m16b`, a `c_guard` entry at level 13, and rollback to the exact prior body)
- `intake_private.respondents_guard` (M16a body): adds `declared_unverified → email_code_verified` only when a **consumed** challenge exists for that respondent whose `email_hmac` and kid equal the respondent's; `staff_attested` still needs an attestation; `assurance_at` moves only with an allowed change; nothing else changes. `email_hmac` may still never go from null to a value or be changed once set.
- `intake_private.link_valid` (M12 body): guardian branch — a guardian invitation is valid only while the latest determination is minor and the request is open; everything else as M12. (Student branch byte-identical.)
- `intake_private.invitations_update_guard` (M12 body): recipient columns immutable.
- `public.intake_issue_invitation` (M12 body, **signature unchanged**; no second overload, which `assert_catalog` would flag): the only change is that its session revocation is `and s.audience = 'student'` (M12 revokes sessions of every audience on a student re-issue; with guardian sessions that is wrong). The staff revoke-all (`intake_revoke_invitations`) and the key-rotation revoke stay all-audience (a deliberate "stop everything"). `intake_next_invitation_generation` stays student-only.
- `intake_private.erase_client_impl` (M16a body) and `intake_private.purge_expired_impl` (M14 body), both under the restricted role (the M14 pattern).
  - **Erase order (complete):** completions, response revisions, responses, **challenges, pending requests (before invitations, `finalized_invitation_id` restrict), attestations**, respondents, determinations, request appointments, sessions, invitations, requests, designations, relationship state.
  - **Purge:** challenges expired and unconsumed more than 24 hours; unfinalized or superseded pending rows past expiry; **finalized pending rows whose invitation is purge-eligible are deleted before that invitation** (otherwise the invitation delete would raise 23503 and abort the whole purge for every studio); consumed challenges and attestations are **kept until erase** (they are the evidence behind the stronger assurance). The new tables enter the purge candidate union so their clients are try-locked with the same held-client pre-filter and ordered deletes (M14).
- `intake_private.audit_write`: unchanged (no new key). The audit event-type CHECK is replaced (M16a text plus the four new event types); `intake_private.assert_catalog` (level 13).

## 6. Tests
Suite: recipient bound at request and copied to the invitation; a respondent with a different hmac or kid cannot get or verify a challenge (same `invalid` word, no write); `same_as_student` and `recipient_link_set` only for authenticated staff; supersede of the open pending row, guardian respondent and draft on re-request; finalize re-checks (pending expired, superseded or finalized; determination no longer minor; request closed; generation scoped to guardian; student invitation and session untouched); verify (correct code consumes and promotes; wrong code increments and **commits** with `invalid`; fifth wrong code then `locked`; expired and superseded without increment; foreign challenge id does not increment; consumed cannot be reused; `already_done`); per-respondent issue cap from rows; new challenge supersedes the open one; guard allows only the evidence-based transitions; `email_hmac` still immutable; guardian link stops when the determination becomes adult; student re-issue no longer revokes a guardian session; erase of a client with pending rows, challenges, attestations and invitations succeeds in the stated order; purge deletes finalized pending rows before invitations and keeps consumed challenges and attestations; audit shape (client_ref, audience, generation, no personal values); catalog (inventory, markers, ACLs, `assert_catalog`). ## 9. Revision 2 (after the review of revision 1: NO-GO as written, CONDITIONAL GO once these changes are in; a diff check of this revision against the list is enough). This section governs where it conflicts with sections 0 to 8.

### 9.1 P0: bind the address the code is SENT to, not only the stored hash
The database cannot see the address a code is mailed to, and `intake_save_draft` takes `email` and `email_hmac` as independent fields. So `intake_issue_email_challenge` gains two parameters: `p_send_to_email_hmac text, p_send_to_kid smallint`. It returns `invalid` unless they equal the invitation's recipient **and** the respondent's stored hash and kid. App rule (e1): compute that HMAC in the same request handler, from the exact normalized address the code is then sent to; the send-to address is never read back from a client, and the only copy of the address (if the app needs one) is an app-encrypted value the database never sees. The "structural fix" is reworded: I3-4's session-bound save will set the respondent's `email` AND `email_hmac` from one server-side computation of the address staff recorded (the invitation carries only the hash, so the app keeps the address encrypted keyed by the pending id); it never copies a hash onto a respondent whose address it did not compute. Refused issues (`invalid`, `limited`) are counted in a database-computed bucket (per respondent, from challenge and refusal rows) so issue cannot become an unlimited "is it this address" oracle.

### 9.2 P1 changes
1. **Re-request stops the old link.** The request RPC, under the client lock, **revokes the current guardian invitations and guardian sessions immediately** (reason `resent`), supersedes the open pending row, the current unsubmitted guardian respondent and draft **and open challenges**. Finalize supersedes again any unsubmitted guardian respondent, draft and open challenge that appeared in the interval. Issue and verify require `challenge.invitation_id = session.invitation_id` and that the invitation is the latest guardian generation. The guard additionally requires the consumed challenge's invitation to be the latest live-or-used guardian generation for the request.
2. **Purge cannot abort on retained challenges.** The invitation purge (candidate union and delete) excludes invitations referenced by any challenge or finalized pending row (`and not exists (select 1 from intake_email_challenges c where c.invitation_id = x.id)` and the same for pending rows) **or** the references are deleted first in the same statement set; the eligible invitation set is computed once so pending rows and invitations work on exactly the same set under the purge limit. Consumed challenges and attestations remain until erase, so their invitations remain too.
3. **Finalize and request preconditions are exact.** Both require `status in ('invited','in_progress')` (a `pending` request has no pinned version and `link_valid` refuses it), `pinned_version_id is not null`, `request_has_live_target`, no submitted guardian response, `guardian_recipient_link_id is null`, and the latest determination minor. Finalize restates the M12 expiry bounds (1 hour to 30 days) and the 16-byte salt, 32-byte hash and 8-character `kid` checks, and returns the guardian generation. The request RPC **returns the next guardian generation** (`requested:<pending id>:<generation>`), so the app has the number finalize needs without a new helper.
4. **Rollback covers the schema.** Steps: refuse conditions first (any pending row, challenge, guardian-audience invitation or session, `email_code_verified` respondent, any new event type), table locks, drop `intake_email_challenges` then `intake_guardian_invitation_requests`, drop the iff CHECK and the two recipient columns, restore the exact M12 constraints under their exact names (`intake_invitations_audience_check` = `audience = 'student'`, `intake_invitations_issued_by_check` = `staff` or `reconciler`, `intake_sessions_audience_check`), restore the exact M12 `link_valid` and `invitations_update_guard`, the M16a `respondents_guard`, M12 `intake_issue_invitation`, M16a `erase_client_impl`, M14 `purge_expired_impl`, the M16a event-type CHECK and `assert_catalog`. The rollback test compares `pg_get_constraintdef` for each restored constraint (`assert_catalog` does not).
5. **Dependencies.** I3-4 must provide session-bound guardian **save and submit** (`intake_submit_response` is also service-role and not session-bound). App condition (e2): guardian-audience save and submit happen only from a guardian session's context. Until then M16b stays dark. P1-A rule 3 ("staff-minted never satisfies guardian consent") is stated as **not applying to guardian sessions** (rule 5 governs: the consent basis is the challenge or attestation row).

### 9.3 P2 changes
- **Single guardian respondent is enforced:** issue and verify return `invalid` unless exactly one non-superseded guardian respondent exists; a partial unique index `(request_id) where role = 'guardian' and superseded_at is null` is added (rollback drops it).
- **Staff revoke-all and select-recipient:** `intake_revoke_invitations` (replaced, marker m16b) also supersedes open pending rows; finalize refuses after a later `staff_revoked` row; `link_valid`'s guardian branch, finalize and issue require `guardian_recipient_link_id is null` (so `intake_select_guardian_recipient` ends the two-party path); the request RPC supersedes a respondent at any rank only when no consent is submitted and **audits the supersede of a verified respondent** (`guardian_invitation_requested` metadata `count`).
- **Verify cannot raise on the match path.** Every state check (respondent exists once, not superseded, rank 0, hash and kid equal to the challenge and to the bound recipient, invitation latest) happens **before** the increment; the consume and respondent update run after the compare and cannot fail by construction. The guard compares `new.email_hmac` (not null) with the challenge and refuses value to null (M16a allows it).
- **Replace `c_guard` entries, do not append:** `intake_issue_invitation|m16b|13`, `erase_client_impl|m16b|13`, `purge_expired_impl|m16b|13`, `respondents_guard|m16b|13`, `link_valid`, `invitations_update_guard`, `intake_revoke_invitations`. Insert guards are `security definer` (they read other tables); update guards are invoker.
- **`same_as_student`:** dropped from the database (the student respondent may not exist or may use another kid; consistent with parent 10.3 #9). It remains an app-side hint.
- **Guessing budget:** codes are 8 digits (derived by the TS side); per respondent at most 5 issues per 60 minutes and **10 per 24 hours**, 5 attempts per challenge, and a **lifetime cap of 50 challenges per guardian invitation**; beyond that `limited` until staff re-request. The bound on guesses over a 30-day link is recorded in the notes.
- **CHECKs:** `audience = 'guardian' or (recipient_email_hmac is null and recipient_email_hmac_kid is null)` is added next to the iff CHECK; the challenge insert guard adds tenant consistency (studio and client equal the request's); the pending update guard forbids a row being both finalized and superseded.
- **Authenticated request RPC accepts a staff-supplied hmac:** stated: a staff JWT could bypass app normalization; without the key that causes only a lockout (re-request), and the audit names the requester. Condition (a) is therefore "the app is the only normal producer", not an absolute.
- **Level and numbering:** level 13, marker `nsi-body:m16b`; the function count and fingerprint come from the generator run; the M16a precondition accepts the m16a marker (or m16a.x).

### 9.4 Open and not decided
Retention of consumed challenges and attestations (I6); creation of a guardian respondent by attestation (M16a returns `no_respondent`); the "completed while adult, later minor" case (I3-4); decline (M16c, O4). None of these blocks M16b SQL; I3-4 and email delivery block activation, not authoring.
