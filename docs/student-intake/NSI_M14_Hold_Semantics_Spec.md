# NSI M14 specification: hold semantics and purge liveness (revision 2, after the independent review; for local implementation only)

Status: **specification; the review is a conditional GO for LOCAL-ONLY implementation.** The migration is not applied anywhere and stays unapplied until the M14 bytes pass a delta review and a full-chain replay and the coordinator relays GO. Origin: the M13 delta review (P2-A..D). The first finding is a **safety defect that predates M13** and also affects client erasure. **None of it is on PROD** (PROD has no NSI objects); on shared DEV Gate A is closed and there is no data, so there is no live exposure. It blocks any purge cron, I4 wiring and Gate A, and is scheduled before the I3-3 implementation (M15).

## 0. Corrections to revision 1 (stated plainly)
1. **The STABLE-snapshot claim was wrong.** A micro-experiment (`sql-tests/concurrency/stable_snapshot_experiment_local.sh`, plain tables, no NSI objects, evidence `rehearsal/m14_baseline/stable_snapshot_experiment_2026-11-23.txt`) shows that a STABLE **or** VOLATILE security-definer function called from a volatile plpgsql BEFORE DELETE trigger **does** see a row committed by another session while the DELETE waited for a row lock: both variants refused the delete. So the R2 reproduction on M13 (purge deleted a held client's session) is caused by the `effective_at <= now()` predicate with a **direct-insert hold**, not by function volatility. Making the functions VOLATILE is therefore not part of the fix (optional defence in depth only, with a catalog volatility pin, not done).
2. **`effective_at` wording:** `effective_at` defaults to the **start time of the transaction that creates the hold**; it is informational (never settable through any RPC) and must never postpone protection.

## 1. The real invariant (to state, enforce and test)
**L1 (the per-client advisory lock `lock_client`) is held, before the hold check and until commit, by every destructive path; and every hold insert takes L1 first.** Then a hold either commits before the destructive transaction takes L1 (so its check sees it) or the hold creator waits until the destructive transaction commits. Enforcement in M14:
1. **Hold insert takes L1 for every writer, including direct inserts:** new BEFORE INSERT trigger `intake_legal_holds_05_lock` (function `intake_private.legal_hold_insert_guard`, security definer) calling `lock_client(studio_id, client_ref)`; a hold with no resolvable `client_ref` is refused (fail closed). L1 is re-entrant, so the RPC path (which already takes L1) is unaffected. Multi-row direct inserts must be in (studio, client) order (documented; the RPC inserts one row).
2. **`delete_guard` becomes lock-then-check:** resolve the subject (studio, client); if the subject **cannot be resolved the delete is refused (42501)**, the only exemption being `intake_rate_limits` (no studio, no client); `try_lock_client(studio, client)` and raise `55P03` if it is not obtained; **then**, in the next expression (a fresh snapshot), check holds.
3. **Hold checks ignore `effective_at`:** `client_has_active_hold` and `is_held` test only `released_at is null` (markers `nsi-body:m14`). Every caller is destructive-side, so this can only refuse more deletions, never fewer. They stay STABLE.
4. **Isolation guard:** `lock_client` and `try_lock_client` (the choke points for every writer) and `delete_guard` raise `55000` unless `current_setting('transaction_isolation') = 'read committed'` (PostgreSQL reports READ UNCOMMITTED as `read uncommitted`, so the string comparison REFUSES it with 55000, as it does REPEATABLE READ and SERIALIZABLE; only READ COMMITTED passes. This is the safe direction and is the shipped behavior; corrected from an earlier wording that said READ UNCOMMITTED was accepted, per the delta review finding 1). Plus an explicit guard at the top of `intake_erase_client`, `erase_client_impl` and `purge_expired_impl`. **I6 gate (recorded, not built):** `evidence_guard` and any retention-expiry job must take L1 and re-check holds at delete time under READ COMMITTED instead of trusting a stored `retention_state` (P2-7).
5. **Hold creation (P2-2):** `intake_create_legal_hold` re-resolves the scope **under L1**, refuses if the scope row is gone, and checks the erasure barrier for **all** scope types (today only client scope); re-creation after erasure stays refused.

## 2. Purge liveness (P2-C), fully specified
- **Eligible-since per client** = the minimum over that client's matching rows: for a session `least(absolute_expires_at, coalesce(revoked_at, 'infinity')) + 24 hours`; for an invitation `expires_at + 90 days` (only invitations with no remaining session). Candidates are the distinct clients ordered by `(eligible_since, key)` (key tiebreak: `studio_id:client_id`), group by client, at most 50 per call.
- **Pre-filter with the identical predicate as the delete-time check:** exclude clients having any active hold in `intake_legal_holds` by `client_ref` (all scopes), `NOT EXISTS` on the active-hold partial index; held clients are never counted against the bound.
- **Delete ordering aligned with candidate ordering** (eligible time, not `id`).
- **Liveness statement:** every client that is not held and whose rows are eligible is cleared within `ceil(N / 50)` calls (N eligible clients); held clients never consume the window; a client whose lock a writer holds is skipped and retried on a later call. The delete-time hold check stays as race protection (it raises `42501` from the guard in the race window rather than deleting).

## 3. Tests (same technique as C5/C7: held locks and explicit sleeps inside the TEST session only)
- **R1** erase transaction started before a hold committed (the defect, reproduced on M13): on M14 the erase refuses and every row remains.
- **R2a (RPC path):** a session holds L1 (a purge or erase in progress); `intake_create_legal_hold` **blocks until it commits**; assert ordering (the hold becomes visible only after the destructive transaction ended, and it then protects the remaining rows).
- **R2b (direct-insert bypass):** a direct superuser insert of a hold with a later `effective_at` than the purge statement start; the guard **raises 42501** and the row **remains**.
- **R3 isolation:** erase, purge, `lock_client`, `try_lock_client` and a direct delete under `REPEATABLE READ` raise `55000`; under READ COMMITTED they run; a hold-creation call under REPEATABLE READ also refuses (stale-snapshot erasure-barrier miss).
- **R4 starvation:** 55 held clients whose keys sort first plus 5 unheld clients: the first call clears all 5 and reports `clients_candidate = 5`.
- **R5 (strengthened C7):** the purge call succeeded (no error text) and `clients_locked < clients_candidate`.
- **R6 (P04 pair):** the minting-actor guard probe uses two different non-null actors.
- **Guard fail-closed:** a delete whose subject cannot be resolved is refused (temp-table trigger test); `intake_rate_limits` is allowed.
- **P2-2:** hold creation refuses a vanished scope row and an erased client for each scope type.
- **Mutation probes:** restore the `effective_at <= now()` predicate (R1 must fail); remove the guard's try-lock or hold check (R2b must fail); remove L1 from `intake_create_legal_hold` (R2a must fail); remove the hold-insert trigger (R2b-direct variant must fail); drop the isolation guards (R3 must fail, one probe per function); drop the candidate pre-filter (R4 must fail); drop `lock_client`/`try_lock_client` (C5/C7 must fail).

## 4. Catalog, migration label, rollback
- **Label:** all M14 inventory rows use level 10 (the presence loop covers 1..10, as for M12/M13); no new level.
- **Inventory:** the new function `intake_private.legal_hold_insert_guard` (security definer) and the new trigger `intake_legal_holds_05_lock`.
- **Markers `nsi-body:m14` in `c_guard`:** `client_has_active_hold`, `is_held`, `intake_erase_client`, `erase_client_impl`, `purge_expired_impl`, `intake_revoke_session`, `delete_guard`, `legal_hold_insert_guard`, `lock_client`, `try_lock_client`, `intake_create_legal_hold`. The erase and purge implementations are role-owned: replaced with the M13 pattern (temporary `grant create on schema intake_private`, `set local role intake_destructive`, restate ACL, `reset role`, revoke).
- **Header precondition:** the migration requires the M13 or M14 level and **refuses if any M15 object exists**.
- **Rollback:** refused when the retention gate is open, when **any** hold row exists (active or released), or when any m15+ marker is present; restores byte-for-byte: M2 `is_held` and `client_has_active_hold`, M3 `delete_guard`, M5 `intake_erase_client` and `intake_create_legal_hold`, M5 `lock_client` and the M13 `try_lock_client`... (as defined in M12), M12 `erase_client_impl`, M13 `purge_expired_impl`, `intake_revoke_session` and `assert_catalog`; drops the new trigger and function.
- `intake_revoke_session` audit row carries `client_ref` (nit); the dead m13 precondition branch in the M13 header is only a comment (M13 is not edited).

## Known limits accepted at the delta review (GO, no P0/P1; migration bytes unchanged: sha256 ae6bbf0b0d05bd46aed96eb284d0eb8ca53bf917f08af39692fa9415b7cef2d2)
1. **Isolation wording (low, fixed in text only).** READ UNCOMMITTED is refused (55000), see section 1.4. No code change.
2. **Purge liveness is for transient locks (low, ACCEPTED AS DOCUMENTED).** The 50-client window is filled before the try-lock, so 50 clients whose client lock is held persistently by long-lived writer transactions would occupy every window and starve the others. The liveness statement above therefore holds when client locks are transient, which every NSI writer guarantees (writers are short transactions; no NSI function holds the client lock across a request). Residual: an operator-held advisory lock, or a stuck session, on 50 eligible clients. Mitigation if it ever matters: oversample candidates (e.g. 200, lock up to 50) or pre-filter with a non-blocking probe; deferred because it changes M14 bytes and the pilot cannot reach the condition. Add an operations note: the purge result reports `clients_candidate` and `clients_locked`; a persistent gap between them is the alarm.
3. **Per-row hold predicate (info).** `client_has_active_hold` runs per candidate row before grouping; fine at pilot scale, revisit if the candidate union grows.
4. **All-or-nothing purge on a guard refusal (info).** A 42501 from `delete_guard` aborts the purge transaction; unreachable while every caller takes the client lock. The mutation probes keep the pre-filter and lock invariants covered.
5. **Carry-forwards.** Direct multi-row hold inserts must be ordered by (studio, client); evidence/retention expiry (I6) must take the client lock before deleting. Not built in M14.
